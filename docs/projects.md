# 专项

专项是一件要分几个话题、跨几天推进的事。管家把它交给一个**负责人**：一个不露面的话题，由它开话题、派活、跟进，做完了向你汇报。前半篇是使用者概览，后面各节是规则和实现；底座（记录、状态、负责人怎么跑、护栏）见[架构 · 专项](architecture.md#专项)，开关见[配置](configuration.md)。

## 使用者概览

**默认开不开。** 专项和下表前四个进阶开关、整理专项（只提议）、派出的事转成专项，不设变量就是开的，新装的和升级前注册的服务都一样。专项由管家开，私聊模式要是“管家”。关掉：`COVEY_PROJECTS=0`，按[改开关三步](configuration.md#改开关三步)重新注册服务；下表的开关都要专项开着，各自设成 `0`（整理专项和转成专项设 `off`）单独关：

| 开关 | 打开后多什么 |
| --- | --- |
| `COVEY_PROJECT_AUTOWAKE`（默认开） | 专项的话题一轮结束就叫醒负责人。关着时话题做完不叫醒它，回执留在收件箱，你下次找负责人时它一起读；负责人的规则和 `project_topic_start` 的说明也照实说不会被叫醒，专项没别的在动时照常按空闲天数收起 |
| `COVEY_PROJECT_ASK`（默认开） | 专项被护栏停住时发卡问你继续、收尾还是停（[专项停住后问主人](#专项停住后问主人)） |
| `COVEY_PROJECT_MEMORY`（默认开） | 专项的话题每轮带上专项记忆（长期约定、当前决定、待核对参考三段）和资料库，你答的问题一题记一条（[专项记忆与资料库](#专项记忆与资料库)） |
| `COVEY_PROJECT_TRIAGE`（默认开） | 专项的话题问的选择题先交给负责人（[专项的问题分流](#专项的问题分流)） |
| `COVEY_PROJECT_UPGRADE`（不设是 `butler`） | 管家可以把一个派发出去的话题转成专项（还要开着[派发卡](butler.md#派发卡)）；`auto` 再加来回到第 3 轮的话题，`off` 关 |
| `COVEY_PROJECT_TIDY`（不设是 `suggest`） | `suggest` 只提议、`auto` 直接建、`off` 关（[整理专项](#整理专项)） |

**专项怎么来。**

- 对管家说“开个专项做……”，管家直接开一个专项，你点名要收进来的已有话题一并挂进去。
- 在话题里说“开个专项”“把这个放进 X 专项”也行：话题把这件事交给管家，私聊顶层出一条“↪ T12 转给管家”，管家接着办，不用你再说一遍（[在话题里说开专项](#在话题里说开专项)）。
- 管家看出一个话题要长期跟进时把它转成专项（`COVEY_PROJECT_UPGRADE` 没设成 `off`）。
- 开了整理专项时，话题多了以后私聊来一张“建个专项？”提议卡，点「建专项」就建；能归进已有专项的话题自动归进。

**私聊里看到什么。**

- **专项卡**：聊天区一条新消息，第一行是负责人的头像行（专项名 · 负责人、状态：在做、等你、停住了、已停止、做完），有事等你时一条结论带写“要你定：…”，各话题在做什么（和看板一样的话题行），负责人现在在干什么，下面有补充、换配置、停止专项、不要专项。
- **负责人的汇报**：顶层的新消息，说话人写“专项「名」· 负责人”。负责人自己醒来的轮次默认不说话，只有该报的进展、派了活、停了话题、替你答了或转给你问题时才发。
- **负责人不发任务卡**：你引用专项卡说的、管家转给它的、网页上对它说的、它自己醒来的，负责人这一轮跑多久都不在私聊里发任务卡（过程卡）；它在做什么看专项卡的“负责人”一行，结论、汇报和没做完时的一句话照样是聊天区的新消息。
- **你在等的结果**：你和负责人说话的那一轮里它开的话题、加的话，那一轮话题做完（或停了），结论直接发到聊天区，和管家派出去的话题一样，不用你去问；你在聊天区引用成员话题的卡接着问的那一轮也一样；负责人不再转述同一件事（[主人在等的结果](#主人在等的结果)）。
- **问题卡**：专项的话题要你定的事，问题卡在话题串里和聊天区各一张，卡上写是哪个话题在问。
- **看板**：一个专项一格，它的话题不再单独列。
- 停住卡、提议卡、整理专项卡见下面各节。

**怎么用。**

- 引用专项卡或负责人的回答说话，就是对负责人说；新的事和某个专项是同一件事时，对管家说，管家会交给它的负责人。
- “停掉 T1”：管家转给负责人，负责人停掉那个话题。
- 专项卡上的「不要专项」把专项降为普通话题。
- 负责人用哪个模型：新建的专项照设置卡「配置」页“专项负责人”一段（没选就跟管家一样），开专项时你点名了（“负责人用 Codex”）就用点名的；已有的专项点专项卡上的「换配置」换（[负责人用哪个 Harness](#负责人用哪个-harness)）。
- 话题被归错了，点话题卡、状态卡上的「移出」。
- “整理一下专项”：马上整理一遍。
- “比较一下 A 和 B 两种做法”：负责人开两个只读话题，给同样的任务说明，尽量一家一个模型；两边都做完后汇总，写清采纳了哪边的哪部分、为什么，以及两边都没回答的问题（负责人规则里的一条，#37）。

## 专项卡

专项开着时，每个专项有一张卡：聊天区的一条新消息，不开串（飞书对已有串的消息，回复一律进串，所以不回复你那条消息）。它是负责人的卡（回复它就是对负责人说），所以没有标题栏，第一行是负责人的头像行，和负责人的回答一样。点击和引用它回复都按消息别名路由到专项的负责人话题，所以按钮是负责人话题的点击。**只有 `ProjectCards`（`app/project_cards.py`）写它**（规则 3）。

- **内容**（`cards/project_card.py` 的 `project_card`，element_id 都不超过 20 个字符）：
  - `speaker_row` 头像行（`cards/ui.py` 的 `speaker_row`）：负责人的头像（和它的回答同一张，`app/project_cards.py` 第一次用时上传、之后记住；没传上时只写名字）、“**专项名 · 负责人**”、状态标签，词和颜色都是 `core/look.py` 的（在做蓝、等你橙、做完灰）：护栏停住的（`core/projects.py` 的 `halted`）是红色“停住了 · 原因”（“停住了 · token 用完了”），你自己停的（停止专项、停住卡上的停）是灰色“已停止”。你那句话直接开的专项，标签后面灰字写“在办你 09:10 交代的事 ›”，整行点了回到你那句话；下面一行 `answer_words` 收着你那句话，点开看全文。
  - `pj_need`：有事等你时一条结论带（卡上唯一有底色的块）：小字“等你 · T12”（问的是哪个话题，负责人自己问的写“负责人”），大字“要你定：…”，整条点了打开问题卡。`pj_meta`（话题数、用时、token）、`pj_lead`（负责人现状 + 最近一句 note）。
  - 话题行 `pt_<话题前 6 位>_<状态字母>`：等你、停住了、可能卡住、在做的话题各一行，和看板的话题行一样（`cards/ui.py` 的 `topic_row`）：T 号头像、带颜色的状态词、标题、一句话（在做什么，或为什么停、停在哪）、灰字 Harness 和用时，整行点了打开它的话题串。失败、中断、被负责人停下的话题是“停住了”（红），超过 30 分钟没动静的是“可能卡住”；等你 → 停住了 → 可能卡住 → 在做，最多 8 行，其余一行 `pj_more`“还有 T…、T… N 个话题”；**状态变了元素 id 就换**。做完和你停的（已停止）收进一个折叠 `pj_ended`（“做完 3 个 · 已停止 1 个”，一行一个，T 号能点）。`pj_meta` 的话题数按同样的词分开数（“话题 4（等你 1 · 停住了 1 · 在做 2）”）。
  - `pj_triage`、`pj_lib` 两个收起的面板（分流记录、资料库，空就不画，资料库每行一个“删”）；`pj_mem` 是一行“记忆 · 规矩 N”（有待审核再加“（待审核 k）”；有网页时整行链到网页「记忆」里这个专项那一组，`/memory?scope=p:<专项 id>`），不数决定和资料（免得和资料库撞名），没有“删”按钮，旧卡片上的“删”点了只回“删除已下线”。
  - `pj_io` 灰框：输入是负责人自己的 Harness、模型、思考预算（取它最新任务，还没有任务时取它 topic.json 的绑定）；各话题用的 Harness 写在自己折叠面板的末行。
  - `pj_btns`：补充、换配置（`pj_switch`，换负责人的 Harness、模型和思考预算，见[负责人用哪个 Harness](#负责人用哪个-harness)）、停止专项、不要专项（停住了和已停止的没有停止，做完的没有按钮）。没有输入框：会重画的卡不放输入框，补充另发一张表单卡。
  - 体积 5–13 KB。各个开关全开、每份清单都满时会超过一张卡的容量（`CARD_NODES`、`CARD_BYTES`）：`project_card` 按 `FIT_STEPS` 一步步让折叠面板少画几行、话题少画几行（剩下的写成“另有 N 条”“还有 … N 个话题”），直到放得下；放得下时一个字不变。
- **读什么**：只读任务记录和问题（没有飞书调用，不拿锁）。话题的状态和一句话沿用派发卡（`app/dispatch_cards.py` 的 `status_of`）；记录字段 `lead_note`、`tokens_used`、`conclusion_message_id`（负责人收尾报告的消息）、`triage`、专项记忆（`projects/<id>/memory.json`，删掉的和风格行不画；卡上的“删”写墓碑，不真删）、`projects/<id>/library/`；空的不画。
- **刷新**：后台线程每秒看一遍，摘要变了且离上次写至少 2.5 秒才整卡 PUT；每次写前从 `reserve` 取 sequence 存进 `record["card"]`，失败按 2、4、8 … 最多 60 秒退避。摘要也存在记录里，重启不会为同一张卡再写一次。
- **做完**：专项 `done` 后卡缩成一行（`settled_card`，链到那条结论）。
  - 结论是 `conclusion_message_id`；没有就看收尾的那一轮：它结束了且在顶层发了回答，链到那条；结束了还没有回答的 id，再等 30 秒（`ANSWER_WAIT`），仍没有就缩、不带链接；还在跑就等它，最多 10 分钟。
  - `cancelled` 缩成“⏹ 专项已降为普通话题”。缩完记 `card.closed`，不再刷新。
  - 你之后又对专项说话（负责人话题、管家转来、网页），专项重新打开，`card.closed` 清掉，下一次刷新在原处画回整张卡。你只在专项的某个话题里说话不会重开已收尾的专项（那是对那个话题说的；`owner_said` 回执照写，等专项重开后负责人读到），收起的专项照旧展开。
- **14 天翻页**：CardKit 的卡实体 14 天后不能改。卡龄过第 12 天（`FLIP_AFTER`）新发一张卡（键里带代数；发不出去下次用同一个 `pending_card_id` 重试），记录、别名、Pin 改指新卡，旧卡缩成“已移到新卡 ›”，写不了 3 次就撤回。
- **按钮**：`bridge_project_steer`、`bridge_project_stop`、`bridge_project_downgrade`、`bridge_project_mem_del`、`bridge_project_lib_del` 在 `ACTIONS` 里，都不是 `bot_only`：没有一个新建任务，值带 `project_id` 和负责人的 `topic_id`，不带 `job_id`，所以任务进程不会收到。
  - 补充 = 负责人正在跑的那一轮的补充表单；负责人空闲时不新开一轮，回一句“引用这张卡回复”。
  - 停止专项 = 记录转 `paused`（停住），并停掉负责人和各话题里排队或在跑的任务：任务在活着的任务进程里，就把它卡上“停止”的点击转给任务进程；点击写的是话题自己的别名 `project-stop-<话题>`，没有任务卡的安静轮也路由得到。“不要专项”停负责人也走这里。
  - 不要专项调 `app/project_clicks.py` 的 `downgrade`（降级，见下）。
  - 删记忆、删资料只删自己那一行（资料只认 `library/` 里的文件名，不认路径）。
- **转成专项的卡**：派发卡转成专项时还是同一条消息、同一个 `card_id`，下一次刷新整卡换成专项卡，`pj_meta` 末尾多一句“由管家转成专项”或“来回 3 轮后转成专项”；同话题其余还活着的派发卡写成一行“已并入专项 ›”（`merged_card`）。
- **不要专项**：专项记 `cancelled`，卡缩成“⏹ 专项已降为普通话题”，负责人在跑的任务停掉，专项的话题变回普通话题；这条卡和并入的那几行以后被引用回复，回到原话题。
- **Pin**：看板的格是专项（`core/board_read.py` 的 `cells`）；在做钉专项卡，等你钉话题的问题卡，做完钉结束的那个话题的答案卡（没有就钉专项卡）；专项还没有卡时钉话题自己的卡。手上的事和早晚汇总的行用 `label_title`，格叫“专项 · 专项名”。

## 主人在等的结果

成员话题的一轮结束后，放置表里它的结论只留在自己的串里，顶层只收到它要你回答的问题（`core/placement.py` 的 `project_member` 行）；结束本身变成负责人收件箱里的 `thread_end` 回执（“T12 的任务 #41 做完：摘要（全文 路径）”：摘要先取检查点的阶段和交付，没有就取回复第一段不是标题的话，至多 300 字，`core/checkpoint.py` 的 `turn_summary`；全文见[专项记忆与资料库](#专项记忆与资料库)的来源三），叫醒负责人（`COVEY_PROJECT_AUTOWAKE` 开着），由负责人决定说不说。所以开着自动唤醒时，成员话题停住了归负责人：看板、手上的事、早晚汇总和网页的“要你处理”都不算它（专项卡上照样是停住了）；可能卡住照样算，它不叫醒谁。没开自动唤醒时回执不叫醒负责人，成员停住了照样算你的（`core/board_read.py` 的 `lead_handled`）。负责人醒来的轮次回复不发，只有它标了 report、汇报风格又放行的 note 才发：默认风格“只报里程碑”只放 `ask`、`milestone`、`finish`，报话题结果的 `thread` 被拦下；要你定的事记成 `ask`，任何风格（包括“只在需要主人定的时候说”）都放行。醒来的轮次里你中途插了话（在负责人话题里说、管家 `project_send` 转来、网页上说），这一轮就算你在场，回复照常发，叫醒次数也清零（任务记录的 `owner_present`）。你直接开的专项、你让管家转成专项的话题，负责人的第一轮也算你在场：`start` 回执带着你那条消息的 id（`app/projects.py` 的 `owner_message`；整理专项建的没有），叫醒轮的来源 `wake` 把它写进 `origin.message_id`，这一轮的说明换成“主人刚建了这个专项，在等你的第一轮回复”（`project_loop.OWNER_START_TEXT`），回复照常发，它派出的话题的结果引用你那条消息回带（`relay_targets.relay_quote`）。所以负责人当着你说“出结果后我发给你”，结果出来时它记了一条 `thread` 汇报，被风格拦住，你只能自己去问。

现在的规则：

- **哪一轮算你在等**：成员话题的这一轮，是负责人在**你在场的一轮**里交出去的：`project_topic_start` 开的、`project_topic_send` 加的话或给在跑那一轮的补充（`main-thread/opened/` 里那条请求记录的 `job_key` 是负责人的任务，消息号不是叫醒的 `lead-…`）；自动重试接着原来那一轮算。负责人叫醒自己那轮交出去的、你在成员话题串里直接说的，都不算。判断在 `app/relay_targets.py` 的 `awaited_target`。
- **你在聊天区直接追问的那一轮**：你在聊天区（或话题串以外的地方）回复、引用这个成员话题的卡（上一轮的回带、问题卡副本等，引用直达）接着问，开的那一轮也算你在等：它的任务记录有 `top_message`（`app/butler_reactions.py`，这条消息上会贴 OnIt、DONE），自动重试接着原来那一轮算；“你问”块是这条消息自己的话，回带也引用它。这样的消息在话题正在跑时作为补充送进那一轮（到达即补充），任务收下了（送达记录 `sent` 或 `read`，不是还没读、也不是任务结束时没读到），那一轮也回带，“你问”块是你那条补充；没收下的会重新排成自己的一轮，带着同一个 `top_message`，照上面回带。你在话题串里直接回复的，答案就在串里，照旧不回带。判断在 `app/relay_targets.py` 的 `asked_outside`。
- **怎么发**：这一轮做完或停了（不算等回答：问题照旧走问题卡和分流），任务进程按管家派出的话题那样把结论回带到聊天区顶层（`app/butler_relay.py`，每个任务只发一次，记录在 `main-thread/relays/`），“你问”块是你说的那句话。不经过负责人，也不看汇报风格，所以一定送到。
- **经管家转来的那一轮**：你在私聊里对管家说、管家用 `project_send` 转给负责人的那一轮，负责人没有自己的卡、消息号是 `main-…`，不是飞书消息；回带沿着请求记录往上找：负责人这一轮 → 管家转它的请求（`main-thread/opened/<token>.json` 的 `job_key`）→ 管家接你那句话的一轮，引用管家那张卡（没有就引用你那条消息），“你问”块是你对管家说的原话，不是管家转给负责人的说明。往上最多读 4 个任务（`HAND_HOPS`），读过的不再读，换了聊天的不算；链头是负责人叫醒自己的那一轮（`lead-…`）时照旧不回带（`app/relay_targets.py` 的 `relay_quote`、`_handed_up`）。
- **不推两次**：这一轮的 `thread_end` 回执记 `relayed: true`，负责人的状态包里这条回执后面写“结论已由 Bridge 直接发给主人，不要再转述”；负责人醒来那一轮读到的回执全是这种、它只报了 `thread` 或 `note` 时，回复照样不发（`app/project_loop.py` 的 `told_already`）。它据此有了新的里程碑判断（`milestone`、`finish`），或者又派了活、转了问题，照常发。
- **负责人的说法**：规则里告诉负责人，你在场时它交出去的活，对你说“T12 出结果会直接发到这里”，不要说“我发给你”。
- **话题收到的是负责人的话**：你在场的这一轮，负责人开的话题、加的话也只带负责人写的任务说明，不带你对负责人说的原话和补充（一轮里它常给几个话题派不同的活）；你发给负责人的附件（直接回它，或经管家 `project_send` 转来，管家把附件一起交给负责人），由负责人在 `attachments` 里点名转给哪个话题，不点名不转；话题卡、历史、串里那一行、网页都显示负责人的任务说明，标负责人；话题不挂在你那条消息下面（[交给话题的消息](butler.md#交给话题的消息)）。回带照上面引用你那条消息，“你问”块是你对负责人说的话。

## 专项可长可短

专项不分长期和临时：可长可短，没活放久了收起，有新的事再展开。

- **新的事自动归进已有专项**：管家每一轮的快照里多一栏“专项”（id、名字、状态——在做、停住、收起——和一句目标；做完和取消的不列）。管家规则（`app/prompts.py` 的 `PROJECT_RULE`）和 `project_send`、`projects_list` 的说明写清：新的事和某个专项是同一件事，就用 `project_send` 交给它的负责人（收起的随之重新展开）；拿不准就开普通话题；你说“这是 X 的事”就归进 X，不再判断。`COVEY_PROJECTS=0` 时规则和快照逐字不变。
- **空闲收起**：专项没有要做的事（负责人和各专项的话题都没有排队或在跑的任务、没有没读的回执；只剩等你回答的也算没事可做；`COVEY_PROJECT_AUTOWAKE=0` 时没读的回执不叫醒谁，也算没事可做），你也没提它，满 `COVEY_PROJECT_IDLE_DAYS` 天（默认 7）就收起：`paused` + `state_reason: idle`，专项卡缩成一行“收起 · N 天没有新的事”，再写“有新的事会自动展开”，不弹停住卡、不发问题卡。你对它说话、管家把新的事交给它时自动回到在做。试用：`COVEY_PROJECT_IDLE_DAYS=0.001`（约 86 秒）。
- **停掉专项里的一个话题**：对管家说“停掉 T1”，管家用 `project_send` 交给负责人，负责人用 `project_topic_stop`：停掉那个话题排队和在跑的任务，收掉它等你回答的问题（卡上写“负责人按你的意思停了这个话题”），还没点开始的启动卡也一并收掉；话题仍记在专项里、算结束，专项因此能收起或收尾。只能停本专项的话题。
- **同时在做的专项最多 50 个**（`core/projects.py` 的 `MAX_ACTIVE`；停住和收起的不算）：这是防失控的护栏，不是要你管的名额。满了以后再开（管家开、转成专项、整理专项的建和拆），先把最久没动静的一个收起腾位置（`app/project_loop.py` 的 `make_room`）：只挑同样没有要做的事（或只在等你回答）、至少一天没有动静的，记录的 `idle.by` 写 `room`，卡上照常“收起 · N 天没有新的事”，有新的事自动展开；新专项的回复里写“为腾位置收起了……”。一个也收不了（都在做事或一天内动过）才不开，回复里点名最久没动静的三个，收尾或停掉一个就能再开。整理专项的提议在腾不出位置时不发。
- **专项多了怎么看**：管家快照的“专项”一栏在做的排前，再是停住、收起、做完，各按最近有动静的在前，最多列 30 个，其余写“另有 N 个，用 projects_list 看”；`projects_list` 同样排序，停住和收起的列最近 30 个（更早的按名字也能 `project_send`）。看板的专项区先列等你、停住、在做的，前 8 个各一块，其余和收起的折成一行一个（“另有 N 个专项 · 收起的专项 M 个”）。
- **同时在做的话题不设上限**：负责人想开几个就开几个；几个话题都要部署时靠排队部署错开，不靠限制话题数。旧记录和 `project-style.json` 里留着的 `spawn` 照读不用。
- **停滞只管有活没动**：见架构里的护栏。
- **旧记录**：记录里已有的 `direction` 字段照读不画；环境里还设着 `COVEY_DIRECTIONS` 也不出错（不再读它）。

## 在话题里说开专项

话题看不到别的专项和话题，也没有开专项、收话题的工具；主人在话题里（包括引用它在私聊顶层的回带卡）说“开个专项”，话题只能请他再去对管家说一遍。现在由话题把这件事交给管家：管家看得到全部专项和话题，开新的还是归进已有的由它判断。不给话题专项清单让它自己判断：它还要一条开专项的新路，判断也只有清单、没有前后的对话，两处都能开专项就会开重。

- **谁能交**：专项开着且管家开着时，主人自己的一轮（他的飞书消息、网页上的话、他在问题卡或网页上自己答的题；管家或负责人转来的、替他答的题、叫醒、到点回来看、自动重试都不算，所以不会在管家和话题之间来回转）里，普通话题和专项的话题的消息在检查点文件后面多一段“要管家办的事”（`app/butler_asks.py` 的 `RULE`）；管家一家（含负责人）和代答话题没有。规则和[架构 · 话题转交管家](architecture.md#话题转交管家)的契约一致。
- **话题怎么交**：主人这一轮要的事只有管家能办（开专项、把这个话题收进某个专项、另开一个话题、交给别的话题）时，话题在检查点写 `ask_butler`：`{"ask":"要管家办什么，用主人的说法","why":"为什么要管家办"}`，回复里说交给管家了。主人只是问要不要开、或话题自己能做的，不写。
- **Bridge 怎么转**：这一轮结束、回复已授权（`done` 或 `waiting_user`）后，Bridge 先在 `butler-asks/<任务键>.json` 记下（每轮一次；同一个话题 7 天内同样的话不再转，后一轮照抄了检查点也不会转两次），再在私聊顶层发一条机器人的文字消息，三行：“↪ T12 转给管家”“你在 T12 说：<主人原话>”“T12 的理解：<ask>”，然后在这条消息上给管家排一轮（轮次来源 `handover`：主人说的、Bridge 记的；排在管家在跑的那一轮后面，不当补充），管家的回答挂在这条消息下面。
- **管家怎么办**：管家规则多一条（`app/prompts.py` 的 `ASKED_RULE`）：以主人原话为准；开专项时把 T12 放进 `topic_start` 的 `topics`；快照或 `projects_list` 里已有做同一件事的专项，就 `project_send` 交给它，并把 T12 放进 `project_send` 新加的 `topics` 直接收进去（`by: butler`，归入记录写“管家收进”，负责人收到 `joined` 回执；在跑的不打断）；两个以上对得上就先问主人；不再转回话题，也不请主人再说一遍。
- **转不了**：管家没开（或它的 Harness 不可用）、消息没发出去、管家那一轮没排上时，话题串里一行“⚠️ 这件事没能交给管家……”，请主人直接对管家说；可能已发出去的不重发（规则 1）。自动重试那一轮写了的也不转，串里说一句。Bridge 停着时结束的那一轮不补转（同代发草稿）。

## 专项记忆与资料库

**记忆**不受开关影响：负责人的 `project_remember`、`project_style`、状态包、专项卡和卡上的“删”都经 `core/project_memory.py`，读写同一个文件 `projects/<id>/memory.json`。旧版留在专项记录 `memory` 字段里的条目照常读出来、和文件合并显示，下一次写入搬进文件。

- **谁写的**（条目的 `source`）由写进来的那条路定，不看模型怎么说：负责人的 `project_remember`、`project_style` 是 `lead`；话题里你说了“以后……”、模型引了你的原话记下的是 `owner`（记忆开着，`app/memory_collect.py`；负责人话题里你说的也记进这个专项、算 `owner`，记忆自己长读，`app/memory_learn.py`，这时负责人的 `project_remember` 只记它自己的总结）；和负责人记的某条正文相同时，就地把那一条确认成你的；你答问题卡记的是 `owner_answer`；你在分流记录上点“不对”纠正的是 `owner_fix`。给了别的值一律记成 `lead`。
- **来源**（`core/memory.py` 的 `describe`，含义见[架构 · 参与者、交付与来源](architecture.md#参与者交付与来源)）：每条读出来是谁说的 `asserted_by`、谁写下的 `recorded_by`、出处 `origin`、来源等级 `level`。没纠正过的条目按 `source` 读：`owner`、`owner_answer`、`owner_fix` 是你说的、Bridge 写下的；其余是负责人说的、负责人写下的。`level` 只由 `core/turn_source.py` 的 `provenance` 算：你说的、而且出处是 Bridge 收进来的（消息 id `message_id`、问题卡的标识 `question`）才是 `owner`，其余都是 `agent`；工具参数和模型写的东西里给了 `level` 或 `asserted_by` 也不认。“你说的 / 它总结的”跟着 `asserted_by` 走，只是标签；你说的但没有出处的旧条目（改成一题一条之前记下的问答）标“你说的（无出处）”，规则里写明它条件可能不全。
- **出处**（`origin`）：知道的才写，你的消息 `message_id`、原问题（标识 `question`、第几题 `index`、题目 id `item`）、话题 `topic`、任务 `job`、你的原话 `quote`。
- **三层**（`layer`，名词见[名词表](glossary.md)）：`rule` 长期约定、`decision` 当前决定（问答、你的纠正，负责人记的决定也在这一层）、`history` 历史记录；`valid` 是 `active`、`done`、`superseded`（带 `superseded_by`）或作废的 `void`，做完和被替代的进历史记录；`applies` 是适用范围和条件。
- **每轮怎么带**（`core/memory.py` 的 `PARTS`）：你说的长期约定、你说的当前决定，和**待核对参考**（不是你说的，负责人整理的口径：和你的话冲突时让路，不能单独作为替你答题的依据）三段各自取舍；历史记录不每轮带。当前决定只管那道题问的范围（哪一版、哪一批、什么目标），换了批次、目标或扩大范围不算你已经同意。
- **负责人的状态包**（开着记忆时，`app/project_lead.py` 的 `store_memory`）：和专项的话题读同一个存储、同样的名字：“规矩”（你定的在前，负责人记的标“负责人记的”，没有出处的你的旧条目标“无出处”）、“主人的决定”（这个专项在用的，新的在前、一题一条）、“和这一轮相关的资料”，每行开头 `〔〕` 里是短码。字数是负责人自己的三段：规矩 1000、决定 1000、资料 800 字，哪段用不完就让给放不下的（规矩、决定、资料依次，资料借到后封顶 1000 字，和原来一样），不压成话题的 600 字决定和 5 条资料；规矩放不下的只列标题（你定的一条不丢），决定放不下的写“另有 N 条”。资料按交给它的话题问题和主人这一轮的话现查（都没有时按专项名和目标），每轮现说，不算进“专项记忆没变”的版本。负责人话题自己的规矩块只带全局，专项的东西只走状态包。派活时，主人刚拍板的关键决定要写进交给话题的话里（别的话题问出来的决定，话题不会每轮都带）。记忆关着时仍按下面的三段读。
- **旁边的文件**：出处、纠正、层和有效性写在 `projects/<id>/memory-meta.json`（条目 id 对它的这些字段），`memory.json` 的格式和以前一样，旧版本改写它也丢不掉这些。
- **纠正**（`core/project_memory.py` 的 `fix`；网页的 `memory_fix` 已下线，旧版记下的照常读）：`scope` 改适用范围（写 `applies`），`once` 只限当次（变成当前决定，适用“只限当次”），`confirm` 确认长期（变成长期约定，`asserted_by` 是你、`recorded_by` 是 Bridge、出处是这次操作的消息 id，所以等级是 `owner`）。只认你：调用方先核对点击或网页操作是你的，模型的话进不来；每次纠正记在条目的 `fixes` 里。
- **负责人查记忆**（`memory_search`，和管家同一个工具）：状态包只带一部分记忆，负责人要找以前定过什么、某条记过没有时用它查；只查本专项和本专项话题的（规矩、决定、资料），全局的、别的专项的、普通话题的都不读，点名别的专项或不属于本专项的话题直接拒绝。在 Antigravity 上它按需加载，不占负责人的预载。
- **负责人改记忆**（`project_memory_revise`，一个工具三个 `op`）：`update` 改一条的正文或种类，改之前的原文留在 meta 的 `fixes`（`what` 为 `edit`，带 `was`、`why`、任务）；`supersede` 用新条（`text`）或已有的一条（`by`，合并重复）替代旧条，旧条标 `superseded`、写 `superseded_by`，进历史、不再每轮带，仍可查；`retire` 把一条收进历史（`done`，不是墓碑，主人删的墓碑仍是另一回事）。口径变了用它们，不再追加一条“XXX 作废”。状态包里每条记忆开头的〔〕是它的 id。
- **改记忆的边界**：主人的长期约定（`asserted_by` 是主人、层为 `rule`）和他明确留下的限制（种类 `constraint`）负责人不能改、替代、作废，要改请问主人；主人的当前决定（问答记下的）不许改正文，办完了可以 `retire`，只能被主人更新的答复（`by` 指向那条）替代；负责人自己记的随便改。判断在记录锁内做，被拒时说明原因。写进主人删掉过的文字同样被拒。
- **快照不进记忆**：发版号、现网第几代、集群瞬时余量、某一刻的进度、谁在做哪件（“T12 负责…”）、几号前交付这类过后就过时的话，`project_remember` 和 `project_memory_revise` 会拒绝（`app/project_tools.py` 的 `SNAPSHOT`，只认明显的几种写法；`project_remember` 还经 `core/memory_gate.py` 的 `write`，“今天、目前”这类时间词和“现网第 N 代”也拒），回执让它写进项目简报（开了协作时 `project_goal` 的 `background`）或 `project_note`。
- **负责人记规矩**（`project_remember`）：`kind` 只收 rule、note（旧的 constraint、decision、fact 直接写 `memory.json` 的路已删）；负责人记的规矩已占满专项名额（`core/memory_review.py` 的 `RULE_CAPS`：10 条 / 1,000 字）时拒写，回执让它先用 `project_memory_revise` 合并（supersede）或改成资料（update 写 kind fact）。记下一条新规矩的那一轮，它的卡上多一行“负责人记下了：… · 管这个专项”带「不对」（任务记录的 `lead_notes`）。`project_memory_revise` 的每次改动也进记忆的“记录”。

专项和 `COVEY_PROJECT_MEMORY` 都开着（默认）时再多三件事：

- **话题开工带上专项记忆**：专项的话题每一轮都带上专项记忆，新会话在规则里、原则之后，续接的会话在每一轮的提醒里（内容由 `app/project_context.py` 的 `memory_view` 取）；新会话后面跟资料库索引（至多 2 KB）。专项取消后、代答话题、普通话题都不带。
  - 三段各自限额，按字数算，一条要么整条带、要么不带：长期约定 1000 字、当前决定 1000 字、待核对参考 800 字（`core/memory.py` 的 `PART_LIMITS`）。长期约定和当前决定新的先带；待核对参考先带决定和约束、再带事实和联系人，各自新的先带。哪一段用不完，剩下的字数按长期约定、当前决定、待核对参考的顺序让给各段放不下的（`SPARE_ORDER`），一段自己用的那部分从不让出去：主人的当前决定先于负责人的待核对参考借到空余，待核对参考借到后总共也不超过 1000 字（`REFERENCE_CAP`），空着的规则字数不会倒灌给它、挤掉主人的决定。
  - 放不下的写一行“这一轮放不下、没有带上的：当前决定 N 条”，条目还在文件里。
  - `COVEY_MEMORY` 开着（默认）时这些行在统一的记忆块里，每行“`- M12 · 管这个专项 · 当前决定 · 你说的：…`”，块后面多两句规则说三段各是什么；关着时在“专项记忆”块里按段列，每段一个小标题，每行“`- [kind] 文字`”。当前决定后面带答题的日期，有适用范围的带“（适用：…）”。
- **一个读口**：专项的话题这一轮、负责人的状态包（新会话和续接的每一轮都带）和网页工作台都经 `core/memory.py` 的 `project_view` 读，条目、分段和取舍都一样，末尾一行“专项记忆版本 xxxxxxxx”（`core/project_memory.py` 的 `version`，增删一条就变，三处是同一个值）。续接的会话还会看到“上一轮之后作废、不再适用的”几条（这个话题上一轮开始之后删掉的），上一轮之后新记的标“（新）”；新会话没读过旧的，不列作废。
- **你答问题卡，一题记一条决定**：专项的话题或负责人发出的问题卡，你提交回答后，每道答了的题记一条 `kind=decision`、`source=owner_answer`：“主人答：题目→回答”，题目和回答都完整；合起来超过 600 字时先截题目，回答至少留 190 字。
  - 条目 id 是问题记录的标识加题号（如 `0123456789abcdef-2`）：同一份回答只记一次，你删掉的那条不会再记回来。
  - 整份问题记录（每道题、选项和说明、背景、每题的回答、补充说明）原样存进 `projects/<id>/answers/<标识>.json`，条目的出处指向它，题目被截了也能查回原文。
  - 反馈、没答的题、全部跳过的不记。
  - 题面（题目 id、标题和题目）按条目 id 点了别的专项的记忆（比如在这个专项的话题里迁移、核对那个专项的记忆，问“〔a1b2c3〕这条以后怎么算”）：这道题是在处理那个专项的条目，答案落在那一条上，不是这个专项的决定，照样记一条，但一记下就是历史记录（`valid` 为 `done`），不每轮带，查记忆能查到。只点了别的专项的 id 或名字（“试点选哪个？（另一个专项 a1b2c3d4e5f6）”）照常记成当前决定。只有题面里有像条目 id 的词时才读别的专项的记忆；读不了就照常记。
  - 开了问题分流时，负责人替你答的那一条**不记**：它是负责人的回答，只在“分流记录”和决定日志里；你自己答的（负责人转给你的、3 分钟超时转出的）照常记。
- **资料库**：`projects/<id>/library/` 放文件，`library.json` 放索引（`core/project_library.py`）。
  - 来源一，你回复或引用专项卡带的文件：消息进负责人话题时复制进来、记 sha256（同内容只一条；单个文件超过 25 MiB 或总量超过 200 MiB 的不复制，只记原来的路径）。
  - 来源二，专项的话题每轮的产物（检查点的 `artifacts`）和 `delivery`：Bridge 在任务进程结束后只记路径、链接或一行交付，不复制（规则 8：任务进程不写专项的东西）。
  - 来源三，成员话题每一轮结束（做完、停住、停止）时的回复全文：不管多短，Bridge 都写到 `<state>/result-files/<任务键>.md`（任务记录的 `result_file_path`；回复太长、任务进程已经当文件发过的，就是那个文件，不重写），登记一条“T12 #41 结论全文”（来源 `result`）。只是留底、没发出去的这份带 `result_file_kept`，不算这一轮的产物，卡片和网页不列它。来源话题开了脱敏（或它的设置读不出来）时这条带 `redacted`，只有开了脱敏的话题的索引里有它。
  - 索引不超过 2 KB（最新的在前，超了写“另有 N 条”），进两处：负责人新会话的状态包和专项的话题的第一轮。负责人续接的会话不再带整份索引，只带上一轮开始以来新增的“资料库新增 N 条”，最多 5 行（最新的在前，多了最后一行写“另有 N 条”，`project_lead.library_added`）。结论全文只列最新 3 条，免得把你发的文件挤出去；每行写话题的 T 号；交付一行按字段截：提交号各 7 位、最多 3 个再写“+N”，部署 40 字，验收 60 字，截处加“…”。设备上的话题读不到本机的文件。
  - 专项卡的“资料库”面板列索引，每行有“删”（删索引、同时删复制的文件）；索引没有登记的旧文件照旧按文件名列、按文件名删。

**网页工作台**：专项条目的 `memory` 每条在原有的 `id`、`text`、`kind`、`source`、`at`、`said_by`、`origin.at` 之外，按[网页 · 协作与三层记忆](web.md#协作与三层记忆契约开发中)多 `asserted_by`、`recorded_by`、`level`、`layer`（风格行算 `rule`，`kind` 是 `style`）、`applies`、`valid`、`superseded_by`，另有 `by`（owner、lead）、`part`（这一轮带它的那段：rule、decision、reference，历史记录和风格行没有）、`ref`（`project:<专项>:<id>`，和任务记录的 `memory_ids` 一样）、`carried`（专项的话题下一轮带不带它；来自开了脱敏的话题的条目只有开了脱敏的话题带，按它们算）；`origin` 里另有知道的出处 `message_id`、`question`、`item`、`index`、`topic`（和它的 `topic_number`）、`job`、`quote`；来自开了脱敏的话题的条目带 `redacted`。专项另带 `memory_version`。`said_by` 跟着 `asserted_by`，旧网页照旧能用。代码在 `app/web_collect.py` 的 `memory_row`。

**限额**：

- 一条至多 200 字（问答的一条至多 600 字）。活条目超过 120 条或文件超过 64 KB 时，按这个顺序删最旧的：墓碑、问答（`owner_answer`、`owner_fix`；原问题在 `answers/` 里留着）、负责人记的事实和联系人、负责人记的其他条目、你自己的话；风格行不删。
- 删掉的活条目连同删的时间和它在 `memory-meta.json` 里的那些字段写进 `projects/<id>/memory-archive.json`（留最近 300 条），不是直接丢掉；这个文件读不出来时这次写入失败，记忆保持原样。
- 资料库超过 100 条时先删最旧的话题产物和交付，只剩你发的文件时才删最旧的；单个专项文件超过 200 MiB 的 `trim` 也是话题的文件在前。
- 复制资料先写到 `library/` 下的临时文件（`.incoming-*`），对副本算 sha256 和大小、在专项的锁里判上限，再改名。
- `memory.json`、`memory-meta.json`、`library.json` 写之前读不出来（权限、IO 错误）就让这次写失败，不当成空文件覆盖；文件在但解析不了，先改名留底 `<名字>.bad-<时间>`、日志写一行，再按空的继续。

**和旧版本**：改成一题一条之前的版本读 `memory.json` 照常，超过 200 字的读成前 200 字；它写的时候按它的 40 条、6 KB 删条目。`memory-meta.json`、`answers/`、`memory-archive.json` 它不读也不写，所以出处和纠正都还在；连 `memory-meta.json` 都没了时，问答条目的出处从条目 id 读回来。之前记下的“主人答：…；…”一条多题的旧条目照旧读，算你说的当前决定，没有出处（`level` 是 `agent`），等存量迁移从原问题找回出处；真实记忆文件不在读的时候改。

**整理记忆**（`COVEY_MEMORY` 开着就每天一次，[管家 · 记忆](butler.md#记忆)）：只理资料和决定（`memory.json` 的行和 `decisions.jsonl` 的决定），30 天没用过的（只认 `memory_used`、`show`、问前查重命中）、问的事已经办完的（对某一次部署、合并的同意）、说的是别的专项的，只按规则收进历史记录（`memory.json` 的 `valid` 记成 `done`，`core/project_memory.py` 的 `settle`；`decisions.jsonl` 的记成办完），不再每轮带，晚间汇总卡上「撤销」放回去；规矩一条不收，负责人记的、旧版负责人写的限制也一样。不再调模型判“被新回答替代”，也不再提炼新约定。收起的条目还在文件里，查记忆（`bin/covey_memory.py`）照样查得到。

**维护**（`core/maintenance_rules.py`）：专项做完 30 天后删资料库里的文件、索引留着；已结束（做完、已取消）的专项记忆条目 180 天后删，在做和停住的专项不动；`memory-meta.json`、`answers/`、`memory-archive.json` 随专项目录一起删；`projects/` 不进备份。

## 专项的问题分流

专项和 `COVEY_PROJECT_TRIAGE` 都开着（默认）时，专项的话题问的选择题先交给负责人（`app/triage.py`、`core/triage.py`、`core/project_gates.py`）。关着时问题卡的发法、重投、恢复和没有这个功能时一样，问题记录里没有 `triage` 字段，负责人没有那两个工具。

- **谁交给负责人**：以下全部成立才交：
  - 开关开着；问题是专项的话题（`topic.json` 的 `project.role` 是 `thread`）问的，专项是 `active`；
  - 问题挡着这一轮（`blocking`）；
  - **每一道题都有选项**（有一道自由文字就直接给你）；
  - 题目、标题、选项文字里没有硬闸词。
  - 题目的类别不是照常要问主人的五类或主人说过要自己定的（`core/ask_kinds.py` 的 `question_kind` 在 `MUST_OWNER` 里：先按题面、选项和 `context` 的词判，命中五类就是那一类，声明成 `blocked`、`other` 也不降），这类题 0 秒直接给你；
  - 负责人接得住（`project_loop.lead_free`：负责人话题没有在跑或排队的轮，只停在自己 `project_ask` 的问题上等你不算；没被叫醒护栏停住；不在限额等待里）。接不住的直接给你，卡上不写“已交负责人”。
  - `Triage.route(ctx, job, record)` 在两个发卡的口子前调：原生的活问题和检查点、暂停的问题；它出任何错都按“给你”走。
- **扣住是什么样**：问题记录加 `triage: {state: held, at, deadline: 现在+180 秒, project, receipt}`，`status` 仍是 `pending`，`display_pending` 仍是真，所以所有“待回答的问题”的列表都看不到它，也没有你能点的卡。话题的任务卡上那一行写“已交负责人”。`state` 只有 `held → answered_by_lead | escalated`（`TRIAGE_TRANSITIONS`），都是终态。
- **扣住的问题不算没投出去**：任务记录的 `question_delivery_ok` 是真，所以 `undelivered_jobs` 不重投，恢复判定（`core/recovery.py` 的 `classify`）和问题卡已发出时一样。Bridge 重启时 `recover_question_delivery` 跳过扣住的问题，由 `sweep` 照常接着数 180 秒。任务进程只写自己这道题的记录，扣住时不发卡也不碰收件箱，活问题的任务进程照常等答案。`tests/test_project_triage.py` 的 `HeldDeliveryTest`、`HeldLiveQuestionTest` 逐条验证。
- **回执和 3 分钟**：Bridge 的 `ProjectLoop` 每 10 秒扫一遍扣住的问题（`sweep`）：没有回执的，往专项收件箱写一条 `question` 回执（这种回执不用 `COVEY_PROJECT_AUTOWAKE` 也唤醒负责人；题目记录的 `triage.receipt` 记着它的 id）；到了 `deadline`、专项不再 `active` 的，发给你。问题一转给你（不管是谁转的），那条回执就标成已处理（回执的 `done`，`project_lead.settle_receipt`），不再为它叫醒负责人，还没读的负责人轮次也不再拿到它。平时只看还在等回答的扣住问题，加上上一次看时负责人的回答正在送的那几道（按名字重读）；进程起来后的第一遍和之后每 10 分钟（`FULL_SWEEP`）才看所有状态的问题：`questions/` 动辄上千条，每 10 秒全看一遍会占掉这条线程大半的时间。负责人的状态包里“交给你的话题问题”一段有每道题的 id、题目、选项和还剩几秒（`app/triage_view.py`）。
- **负责人的两个工具**（只在开关开着时列给负责人）：
  - `project_answer(thread, answers)`：每题都要答，答案是选项原文，多选给数组；走 `Questions.submit_answer`，效果和你点“提交回答”一样，补充说明是“（负责人按专项记忆替主人答的）”；要写 `evidence`，见[分流的依据](#分流的依据)。提交前先把 `display_pending` 记成假并写 `answering`；提交失败就把问题转给你。
  - `project_escalate(thread, why[, context, recommend, if_not])`：问题卡马上按原来的口子发给你（话题串里一张，私聊顶层一份副本），卡上多一行“负责人转给你的理由：…”；写了 `context`（背景一句话，最多 120 字）卡上理由下面多一行灰字“背景：…”，写了 `recommend`（推荐的选项原文）多一行“负责人推荐：…”，再写 `if_not`（不选它的代价）就跟在后面一行；三个都不写，卡跟以前一样（到期按推荐执行不做，只是写给你看）。这三项记在题目的 `triage` 里，任务卡上的那一行换成“转给你了”；卡发不出去时任务记录记 `question_delivery_ok: false`，你那边是平常的“重新投递”。
- **转给你的活问题由任务进程发卡**：原生的活问题（Claude 的 AskUserQuestion，轮还没结束、任务进程在等答案）转给你时（负责人转、3 分钟超时、专项停了、你在话题里说话），Bridge 不自己发卡：活问题的后端控制和这一轮到提问为止写过的内容（进展说明和正在写的正文）只在任务进程里，Bridge 手上的 `RemoteControl` 两样都没有。`triage.show` 往任务进程的 inbox 写 `show_question`（`runner_ipc.show_in_runner`，最多等 20 秒确认），任务进程 `Questions.show_handed_on` 发问题卡、改任务卡那一行，再在私聊顶层发副本，副本上方带这一轮写过的内容，和没被扣过的问题一样。旧版本的任务进程不认这条消息、不回确认，按发不出去处理（任务记录 `question_delivery_ok: false`）。任务就在 Bridge 里跑时照样在本进程发。扣住期间私聊顶层不发任何东西（`NativeQuestions.mirror` 跳过扣住的问题）。任务结束时（停止、失败、做完）它没发出卡的问题（扣住的、卡没送到的）也随 `cancel_questions` 撤回；任务已经不在、却还挂着的活问题，在你往这个话题发下一条消息前撤回（`Questions.retire_orphaned_live_questions`），不再让每条消息都收到“原结果或问题控件尚未送达”。任务还在等、卡却没发出去的活问题（任务进程 20 秒没确认，或卡发失败），任务记录不记成失败（轮还在跑，只记 `question_delivery_ok: false`）；分流的巡检每 60 秒再让任务进程发一次卡，最多 5 次（`RESHOW_EVERY`、`RESHOW_TRIES`，次数记在题目的 `triage` 里）；你往这个话题发消息时也先再试一次，发出去了你这条就当回答或补充，还是发不出去就回一句“问题卡没发出来，可以先停止这个任务”（`triage.reshow`）。
- **转给你的检查点问题发不出卡会自动补发**：任务已经结束、问的是检查点问题（话题里那张问题卡，不是活问题）时，转给你的那一刻卡没发出去（飞书没接住、结果还没送达等），`triage.escalate` 在 bridge.log 记一行“question triage escalation card not sent”和原因，任务记录记 `question_delivery_ok: false`、`failed`。以前这之后只有你点话题任务卡的重试才会再发；现在分流的巡检（每 10 秒一遍）会把这类“转给你、卡没发出去、还是 `pending`”的问题（`triage.stranded`）按 `RESHOW_EVERY` 每 60 秒再发一次，最多 `RESHOW_TRIES`（5）次，次数记在题目的 `triage` 里（`reshows`、`reshown_at`），每次在 bridge.log 记一行（`card again … try=N ok=…`，失败的原因在前一行 `card not sent`，只有短 token 和原因，不含题面）。补发成功时，因为这道问题被记成失败的任务回到“等你回答”（`triage.mend`，和重新投递成功后一样）。5 次都没发出去：bridge.log 记一行 `card gave up`，任务记录保持失败，手上的事看板把它列在“停住了”，话题任务卡上有“重试”，你往话题发消息时回“请先重新投递”；点重试走原来的重新投递，不再另发通知。分流开关关着时不补发。
- **负责人的回答要确认**：`project_answer` 提交时任务进程还活着，答案只是写进它的收件箱，问题记录仍是 `pending`。这时分流状态保持 `held`，工具回“还没确认收到”；`sweep` 看到问题记录已落地才改成 `answered_by_lead`；`answering` 超过 90 秒（`ANSWERING`）仍是 `pending` 就转给你（理由“负责人的回答没有送到”）。这 90 秒里 `sweep` 对这道题所有分支都不动。
- **硬闸**（`core/project_gates.py`，只用标准库）：查题目、标题、选项的标签和说明、题目的 `context`，命中就直接给你：
  - 五类（部署、删除、花钱、对外发送、占机器）的词只有一份，在 `core/ask_kinds.py`（问题去重 `app/question_dedup.py` 的五类也读它）：原来去重的五类词和硬闸词表取并集，再补 Wave 0 验收没拦住的说法（“重启 Bridge/服务”、“推到现网”、“通知张三”这类点名的通知、`deployment`/`deploying`/`deleted`/`released` 这类英文词形、`reset --hard`）。中文词在任何位置都算；英文按词干（`deploy` 也拦 `deployment`、`redeploy`），短词要整词，中英文挨着写（“要deploy吗”）也认。单独出现多是别的意思的写法按搭配收：stable 只认通道、分支或“推/合/升 stable”（不是 stable 排序），“覆盖”只认覆盖别人、远端、线上、现有这类（不是覆盖检查、覆盖率），“通知”后面跟卡片、样式、栏这类时不算，“买家”“常驻内存”不算。否定句（“先不部署”）照样命中：宁多问一次。
  - 题目声明的类别（检查点 `questions[].kind`，见执行约定）只升不降：题面说到五类的按那一类算，声明成 `blocked`、`other` 也不降；题面什么都没说、但声明的是五类之一或 `owner_asked`（主人明说要他定的）也直接给你（`ask_kinds.question_kind`，命中词记成声明的类别）。
  - 五类以外留在硬闸自己的 `EXTRA_*`：额度、配额、“扣 … shared/dedicated/配额/额度/quota”、停用、排空、批一份、强制、密钥、密码、令牌，英文整词 `quota`、`sudo`、`password`、`secret`、`api key`。
  - 占机器、建服务这类按动作写的式子（卡上的命中词是匹配到的原文）：“占 N 台/张/卡/个节点”、“新建/创建/建 N 个 … 服务/集群/实例/资源池”（“建议”“重建”“搭建”不算）、扩缩容/扩容/缩容/缩到 0、“申请/释放/归还/退还/租 … 卡/机器/资源/节点”、`scale up/down/out/in`、“提交/起/拉起 … 训练/作业”、下载 N GB/TB。“卡”“服务”“资源”单独出现在很多不要资源的问题里，所以不收单字。
  - 词表宁多勿漏：多一次命中只是你多看一张本来就会看到的卡，漏的靠负责人自己判断和 3 分钟超时兜底，答错了到专项话题里直接说。五类的完整说法是执行约定里的 `ASK_KINDS`（`core/checkpoint.py`，就是 `core/ask_kinds.py` 的 `LONG`），硬闸只是它的词面兜底。
- **你看得到**：负责人替你答的每一条、每一次转给你，都是专项卡“分流记录”里的一行（最多 40 条）；答的那行以前带一个“不对”按钮，现在拿掉了（`bridge_project_triage_wrong`、`bridge_project_triage_fix` 留在按钮表里，点旧卡上的回一句“已下线，要纠正到专项话题里直接说”，不做任何事）；纠正就在那个专项话题里说，负责人照常读到。
  - 以前用「不对」纠正时记下的 `source=owner_fix` 专项记忆照旧读（算你说的），不再有新的。
- **你在话题里说话**：话题里有交给负责人的问题时，你在这个话题发消息先把这些问题转给你（理由“你在这个话题里说话了”；负责人的回答正在送的不转），然后这条消息照“话题里有一张待答问题卡”处理：只有一道题时是回答，几道题时是补充说明。
- **开关关掉后**：没人处理的扣住问题一律给你。`sweep` 在分流关着时把它们都转出去（理由“问题分流已关闭”）；`ProjectLoop` 只在专项开着时跑，所以 Bridge 启动时在 `recover_question_delivery` 之后无条件调一次 `triage.settle_closed`。已知限制：任务进程的环境开着分流而 Bridge 关着时，任务进程在 Bridge 启动之后新扣住的问题要等下一次 Bridge 重启才转给你。
- **和停住的配合**：`COVEY_PROJECT_ASK` 开着时 token 停住会请专项的话题里在做的任务停下。这时还扣着的检查点问题，下一次扫发现专项不再“在做”，转给你，只转一次；正在等答案的活问题，它的任务被请停，后端随任务撤回问题，不转（你点继续后由负责人重新把活交给话题，话题会再问）。

### 分流的依据

`project_answer` 要写 `evidence`，开不开协作（`COVEY_COLLAB`）都一样（W0-2：原来关着协作时不核对，负责人能没有依据就替主人答）：至多 6 条依据，每条是专项记忆条目的 id（状态包里专项记忆每行开头 `〔〕` 里的短码），或主人在这个专项里的原话 `msg:<消息 id>`（开着分流时，状态包多一段“主人在专项里说过的话”，列负责人话题里主人最近 5 句和它们的消息 id）。Bridge 逐条核对（`app/triage.py` 的 `grounds`），不看模型怎么描述它：

- 条目要在这个专项的记忆里，不在就当是编的；风格行不算；删掉的（作废）、做完或被替代的（进了历史记录）、只限当次的都拒绝。
- 主人原话：消息 id 是 Bridge 收进来的主人消息（飞书 `om_…` 或网页 `web-…`），在负责人话题或专项的话题里，来源是主人的话（不是协作轮、转交），发送者经 `app/access.py` 的 `owner_turn` 核对是主人。
- 至少一条是主人的话（`level` 为 `owner`：你定的规矩、决定里有出处的条目，或主人原话）；只有负责人记的或没有出处的旧条目时拒绝，回复让它用 `project_escalate` 转给主人，不要换个说法再答。答的是另一道题的决定只能一起列，不能单独作依据。
- 主人在网页「记一条」写的，出处是那次网页操作（`web-<操作号>`，`app/web_memory.py` 的 `web_origin`），算主人的话；在网页上「改」一条不改它原来的出处，负责人记的改了还是负责人记的。
- 被答的话题没开脱敏时，来自开了脱敏的话题的条目、主人在开了脱敏的话题里的原话都不当依据（不然它们的前几十个字会写进这个话题的回答）；只给了这些时拒绝。
- 有一条不对就整次拒绝，什么都不提交，问题仍扣在负责人手上（3 分钟没处理照旧转给主人）。

通过后，回答的补充说明写成“（负责人替主人答的，依据：<短码> 你定的·决定「…」）”（另有“你定的·规矩”“负责人记的·资料”“主人原话”），分流记录那一行开头写“答了（依据 你定的·决定）：”，行里另存 `evidence`（每条的 `ref`、`kind`、`level`、`layer`、`part`），主人照旧可以点“不对”。没传 `evidence` 时整次拒绝，什么都不提交。

## 专项停住后问主人

`COVEY_PROJECT_ASK` 开着时，护栏停住专项（`state_reason` 是 `tokens`、`wakes`、`stalled`，见[架构 · 专项](architecture.md#专项)），`ProjectLoop.pause` 在同一次写记录里加一份 `pause_ask`：`{reason, why, at, choice, halted, card}`。`ProjectCards` 看到它，在专项卡所在的位置发一张**停住卡**（`cards/project_card.py` 的 `ask_card`）：

- 卡头专项名 + 红色“停住了”标签（护栏停的算停住了，见 [UI 规范](ui.md#3-状态词表)；橙色只给等你和可能卡住）。
- `pa_why` 一句话写为什么停（`project_loop.pause_words`）：“token 用到上限 1000 万”（只在设了 `COVEY_PROJECT_BUDGET` 时有，默认没有 token 上限）、“负责人连续 6 轮叫醒都没派活、没提问，也没记进展”、“负责人一小时内有 12 轮叫醒没派活、没提问，也没记进展”、“负责人一小时内叫醒了 60 次”、“62 分钟没有进展”。
- `pa_note` 写在做的话题怎么样了；三个按钮 `pa_go` 继续、`pa_wrap` 收尾、`pa_stop` 停。

**三个按钮**：`bridge_project_ask_continue`、`bridge_project_ask_finish`（`bot_only`：它们让负责人再跑一轮）、`bridge_project_ask_stop`（不是 `bot_only`，和停止专项一样），`handler` 都是 `controls.project_ask`。点击先在记录锁里记选择（只有专项还因这个原因停着、这张卡是当前这次停住的卡、还没选过才算数；否则回一句“选择已经做过了”“这是之前一次停住的卡”等，什么都不改），再做事：

- **继续**：专项回到 `active`，唤醒计数清零；`tokens` 停住再给一份预算（`token_floor`）；给负责人一条 `owner_choice` 回执，它永远唤醒负责人。
- **收尾**：同样把专项重新开起来，回执要负责人总结做完了什么、还有什么没做完，用 `project_note` 标 report 告诉你，然后调 `project_finish`（还有话题在做时它会拒绝，等它们结束再收尾）。负责人的规则要它把话题说的“做完”当作话题自己的说法：收尾前对照完成标准抽查关键产物和检查点的提交、部署、自检，只提了合并请求、合了没部署的不算做完。
- **停**：记录仍是 `paused`，`state_reason` 改成“主人停止”，并停掉负责人和各话题里排队或在跑的任务；之后你在负责人话题里说话把它开起来时，照样给一份新预算，不会马上又停。

其余规则：

- **在做的话题**：`tokens` 停住时同时请专项的话题里排队、在跑的任务停下（把卡上“停止”的点击转给任务进程），数记进 `pause_ask.halted`，卡上写“在做的 N 个话题已请它们停下”；`wakes` 停住不停它们，卡上写“不受影响”；`stalled` 本来就没有。
- **点了以后**：这张卡整卡写成一行（“你选了继续 / 收尾 / 停”），专项卡下一次刷新自然变成在做或停住。专项被别处处理了（你在负责人话题里直接说话、负责人收尾）而没点，这张卡缩成“已在别处处理”。每张卡的写入用它自己的 sequence（`pause_ask.card`）。
- **试用**：设 `COVEY_PROJECT_BUDGET=<小数>` 一会儿就停住；`COVEY_PROJECT_STALL_SECONDS=60` 并保持 `COVEY_PROJECT_AUTOWAKE` 开着，一个有任务排队或有没读的回执、却没有动静的专项约两分钟后停住（没有要做的事、或只在等你回答的专项不会停滞）。唤醒次数的上限不能调。

## 负责人问主人与外发三通道

负责人对主人说话只有三条路（`app/project_tools.py`、`app/project_loop.py`，WAVE12 C4）：

- **提问走 `project_ask`**：要主人定的事（范围、取舍、部署这一批、要不要停，以及照常要问的那几类）都用它问。题目写进负责人这一轮自己的检查点（`core/jobs.py` 的 `checkpoint_file`，带 `origin: project_ask`），这一轮结束时和别的话题的检查点问题一样出问题卡：进“等你”、网页能答、超长按节点预算拆。任何汇报风格都发。一次最多 4 题；负责人之前问了还没答的题（同一个负责人话题、`origin` 是 `project_ask`、还 `pending`）会原样并进这张新卡（id 不变，同 id 的新题顶替旧题），超过 4 题就拒绝、要它先精简；新卡发出后旧卡照常收起（`questions.fold_older_questions`）。问题记录带 `origin: project_ask`；负责人停在这种题上等主人时不算“忙”，成员的回执照常叫醒它、分流照常交给它（`project_loop.lead_busy`）。W0-2 的 `project_note(kind="ask")` 这一版还认，按一道自由题转给 `project_ask`，下一版去掉。
- **进展走 `project_note`**：标 `report` 且按风格该报的（`project_lead.reportable`），叫醒负责人的轮里由 Bridge 把笔记原文以“专项「名」负责人：”发出（`project_loop.report_out`）。
- **回复正文只在主人在场的轮发**（`project_loop.present`）：主人发来的、管家转来的、叫醒的轮里主人中途插了话。叫醒的轮回复不发；开了话题、加了话这类动作不再让整段回复外发，专项记录的 `acted` 只记这一轮做了什么（`{job, whats, at}`）。

负责人的轮不写检查点：规则里检查点契约换成一行“不写检查点、要定的用 project_ask”（`app/runs.py` 的 `LEAD_RULE`），也不告诉它检查点文件在哪。

## 部署攒批与部署授权

专项里几个话题同时改代码时，怎么部署先看主人的记忆（`app/project_lead.py` 的 `TOOL_RULES`、`core/checkpoint.py` 的 `MEMBER_DEPLOY_RULE`）。主人自己说过改完就部署（“测试过了就直接部署”这类长期约定；负责人或整理时总结出来的不算），话题合进主干、部署前的检查过了就自己部署到主人的服务；负责人不攒批问、也不派部署，“合进待部署”里还列着的就是合了没部署成的，它去看为什么。主人没说过时攒批，不再每合一个就问一次主人要不要部署：

- 专项的话题合进主干后不自己部署、也不单独问主人，检查点的 `delivery` 写提交、`deployed` 留空。
- 负责人每一轮的“专项状态”多一段“合进待部署”（`waiting_deploys`）：成员话题已结束、写了提交、没说部署过的轮次，每轮一行（话题、提交、有没有自检、什么时候合进）。哪个话题的某一轮写了部署过（`deployed` 有字、不是“未部署”“待部署”这类），它开始之前结束的轮次都算部署了（部署取的是当时的主干），不再列。
- 该合的都合了、主人要用了，或攒了半天，负责人用 `project_ask` 一次问主人要不要部署这一批：`kind` 写 `deploy`，`deploy` 写提交、话题和目标，同意的那项可以标 `grants_approval`；题目的说明里列话题、提交和各自的自检。
- **授权凭证**（`app/project_approvals.py`）：主人本人（点卡、网页、在话题里打字；管家代答、负责人替答都不算）答了这道题、选的是同意（选项自己的 `grants_approval` 优先，没写就按选项文字的肯定否定判断；多选里有否定的不算），Bridge 在专项记录的 `approvals` 里记一条（`A1`、`A2`……，最近 20 条）：`state` 为 `active`，72 小时内有效，`used_by` 记谁用过。负责人接着的那一轮会读到凭证号，状态包里也列着还有效的凭证。之后同一批提交的部署题主人答了不部署，凭证撤销（`revoked`）。
- 负责人派部署时用 `project_topic_send`（或 `project_topic_start`）带 `approval`。Bridge 核对：是这个专项的、还 `active`、任务说明里点到的提交都在这一批里（写了话题清单的还要是那几个话题之一）；不对就拒绝、什么都不发。核对过的在交接说明开头的 `[Bridge 说明]` 段末尾加一句“主人 MM-DD HH:MM 在问题卡上同意部署这一批：提交 …；目标 …（凭证 A1）”，凭证随即记为用过（`consumed`，一个凭证只派一次；同一个工具请求重放不算第二次）。主人同意之后又在专项里说过话的，工具回话多一句提醒，不拦。
- 话题只认这一句：负责人自己写的任务说明、补充里任何以 `[Bridge` 开头的行，交接时都改写成 `〔负责人写的〕[Bridge…`（`project_tools.unforged`），成员规则写明只认开头 Bridge 的附注。
- 部署的公司习惯（网页同发、同一服务排队、别人的机器、稳定通道、回滚照常问主人）不写在核心里：扩展设置 `deploy_notes`（`core/extensions.py`）接在成员部署规则后面，只读话题不带。
- 要从一种换到另一种，改记忆就行（在记忆里说一句、或删掉那条约定），不用改配置。

## 负责人只读

负责人只拆、派、跟进、收尾，不自己动手：它这一轮只能读文件、搜索和用 Bridge 工具（开话题、给话题加话、记一笔……），改文件、执行会改东西的命令、联网都会被拒（`core/harness.py` 的 `LEAD`，`app/project_lead.py` 的 `held`）。负责人跑在哪个 Harness 上见[负责人用哪个 Harness](#负责人用哪个-harness)，每个 Harness 用自己的办法守住：

| Harness | 怎么守住只读 |
| --- | --- |
| Claude Code | 自带工具只给 `Read`、`Grep`、`Glob`，Bridge 工具照常（`--tools`，和以前一样） |
| Codex | 线程和每一轮都在只读沙箱里（`read-only`，`sandboxPolicy: readOnly`）：能跑只读的命令，写文件、联网被沙箱拒。只读沙箱里 MCP 工具默认要批准、批准策略又是从不问，所以给 Bridge 工具单独设成直接批准（`mcp_servers.bridge.default_tools_approval_mode = "approve"`）。接着上一轮时在一个不带你的规则、hook、插件和记忆的 `CODEX_HOME` 里跑，和群成员只读的一轮一样（`ReadingHome`）；开新线程的那一轮在你的 `CODEX_HOME` 里，执行规则里 allow 的命令那时仍在沙箱外执行（[harnesses.md 执行权限](harnesses.md#执行权限)） |
| Antigravity | 这一轮带上只对这次运行生效的拒绝规则（`--settings`，不写进你的设置，`backends/agy/bridge.py` 的 `READ_ONLY_SETTINGS`）：写文件（新建和改已有的都算）、执行命令、读网址都被拒；读文件、搜索和 Bridge 工具照常（agy 1.5.14 实测） |
| DeepSeek Harness（dsh） | Bridge 工具经 dsh 自带的 `@deepseek-ai/dsh-mcp-client` 接进来（补丁里 `insert` 一行，`backends/dsh/bridge.py` 的 `mcp_rows`）；这一轮用 dsh 的 `read-only` 权限预设，`--approval-policy never`（没有人可问，提权一律拒）。写文件、改文件、提权都被拒；dsh 的只读沙箱要 bwrap 或 Landlock，这台机器上用不了，所以 bash 整个被拒（连只读命令也不行），读文件、搜索和 Bridge 工具照常（dsh 0.2.2-rc.5 加本地假模型实测） |
| 没接 Bridge 工具的（扩展里没声明 `bridge_tools` 的） | 当不了负责人：这一轮不启动，任务卡上说为什么（`app/tool_limits.py` 的 `refusal`） |

负责人开话题（`project_topic_start`）和管家一样可以带 `local: false`：只解读外部资料、写报告、用不上本机仓库和文件的话题，规则里不给仓库地图，各 Harness 不加载主目录的说明文件，你自己的 `~/.codex/AGENTS.md`、`~/.gemini/config/GEMINI.md` 照样加载（[管家 · 外部话题](butler.md#外部话题)）。

这一轮已经有更严的限制时（群成员只读、代答、协作咨询）照那个；只看不改（`look`）的一轮让位给负责人的。负责人话题的专项记录没了时这一轮照样只读，只是没有 Bridge 工具。实测记录见 Codex 的 C8 检查（`tests/test_collab_c8.py`）和 `tests/test_butler_harness.py`。

## 负责人用哪个 Harness

负责人和管家、话题一样能单独选 Harness、模型和思考预算（`app/lead_harness.py`）。只列能接 Bridge 工具的（核心的 Claude Code、Codex、Antigravity、DeepSeek Harness 都能，和管家能选的一样：负责人靠这些工具派话题，并在上面守住只读）；扩展里的 Harness 看它自己有没有声明 `bridge_tools`。

- **新建的专项**（`app/projects.py` 的 `step_lead`，按这个顺序取第一个能用的）：
  1. 管家开专项时你点名了负责人用哪个（`topic_start` 带 `project` 时的 `harness`、`model`、`effort` 是负责人的，记在专项记录的 `origin.lead`；点名的接不了 Bridge 工具时这次不开，回复说清楚）。话题用什么模型写进专项的说明，负责人开话题时照办。
  2. 设置卡「配置」页的“专项负责人”一段（专项开着才有，存在 `main-thread.json` 的 `lead`）：第一项“跟管家一样”，选了 Harness 再选供应商、模型、思考预算。网页设置页同一段。
  3. 都没有时跟管家一样：管家这时的 Harness、模型和预算（管家还没在这个私聊跑过一轮时，照它现在会用的）。
  
  选的 Harness 这台机器没启用、接不了 Bridge 工具，或者管家开着脱敏而它不能脱敏（负责人的脱敏跟管家），就落到下一项，不会让负责人的每一轮都跑不起来。日志一行 `project lead bound … harness=<名字> from=call|settings|butler`。
- **已有的专项**：专项卡上点「换配置」，回复专项卡出一张换配置卡（`app/harness_switch.py`，记录里带 `lead`）：只列能当负责人的模型，没有工作区和运行方式两行（负责人在原来的工作区里读），能开关脱敏（选了不能脱敏的模型时同普通话题，确认前问一句）。确认更换和话题的换配置是同一个重绑（`app/binding.py` 的 `switch_topic`）：绑定版本加一，新 Harness 的会话指针清空，负责人旧绑定下没答的问题作废；负责人下一轮（醒来的或你说的）开新会话，状态包整份重读，最近几轮对话和交接一起带上。负责人有一轮在排队或在跑时不换，卡上写“负责人还有一轮在排队或在做：等它做完再点确认更换”，卡一直有效。换了以后专项卡的输入框写新的 Harness 和模型（`app/project_facts.py` 的 `rebound`：换配置之后还没跑过一轮时读负责人的 `topic.json`）。
- **网页**：负责人的对话下面也有配置栏，和话题的换配置一样，只是只列能当负责人的模型、不能换工作区（数据约定 v36，见 [web.md](web.md#网页发回的操作)）；负责人那一轮没成功时的“换个模型”就是打开它。
- 负责人跑不起来（Harness 后来被停用，或换到了接不了工具的）时，这一轮不启动，说明里写“点专项卡上的「换配置」，换成能接 Bridge 工具的 Harness”。管家换 Harness 不影响已有的负责人。

## 负责人对照目标跟进

`COVEY_COLLAB=1`（[多参与者协作](architecture.md#多参与者协作开发中默认关)的开关，默认关）时，负责人对专项的目标负责，而不只是收发消息：维护完成标准、发现漏项、安排依赖、检查证据够不够、协调返工。关着时下面这些都没有，负责人的规则、状态包、工具清单和收尾都和原来逐字一样。

- **目标检查表**（`core/project_checklist.py`，记在专项记录的 `checklist`：`{items, closed, next, at, job}`）：负责人用 `project_checklist` 把完成标准拆成条目，没满足的（`open`、`blocked`）同时至多 20 条，连满足的一共至多 100 条，每条 `{id, criterion, topic, needs, evidence, gap, state}`：完成标准、交付它的话题（要是这个专项的话题）、依赖哪几条、证据在哪、还缺什么。可选的还有 `title`（短标题，24 字）、`waiting_on`、`done_at`、`topics`，见下面的「项目简报」。状态 `open` 没满足、`done` 满足（要写 `evidence`）、`blocked` 卡住（写 `needs` 或 `gap`）、`dropped` 主人说不做了（`gap` 写主人怎么说的，`evidence` 写他的依据：`msg:<消息 id>` 是他在这个专项里说的话，`ask:<问题 token>` 是他本人答过的题，Bridge 在他回答负责人的 `project_ask` 后面写着这一行；停住卡上选“收尾”是 `ask:pause-<n>`，回执里写着。Bridge 逐条核对，核不上就整次不写，`app/project_tools.py` 的 `dropped_bases`；以前标的 `dropped` 不追溯）。id 是 `c1`、`c2`……按写入顺序给，不复用；条目不能删、只能标 `dropped`，收尾时看得到哪些没做。一次调用的改动在记录锁里先整体校验再写，有一处不对整次不写。不是通用项目管理：没有日期，交付的只是话题，没有单独的历史。
- **项目简报**（`core/project_actions.py`，记在专项记录的 `lead_background` 和 `actions`；网页专项页的「简报」标签，见[网页工作台](web.md#专项条目)）：把目标说成背景加几个动作，每个动作带着它的条目和话题。全是可选的，旧记录照常读；没写的专项网页退回按检查表显示。
  - **背景**：`project_goal` 多一个可选的 `background`（至多 300 字，`lead_background: {text, at, job}`），目标还是 `text`，两个至少给一个。
  - **动作**：`project_checklist` 多一个 `actions` 参数，把目标拆成 3 到 8 个，每个 `{id, title, note, items, topics, state, at, job}`：名字（30 字）、负责人写的一句现状 `note`（80 字）、它的检查表条目 id、它的话题、`open` 或 `dropped`（不做了，收起、不删）。id 是 `a1`、`a2`……按写入顺序给，不复用；没标 `dropped` 的至多 10 个。新加的不写 id，改的写 id、只写要改的键；`items`、`topics` 整组替换，所以改之前先不带参数调一次 `project_checklist` 看现在的；`topics` 收 T 号或 topic_id，要是本专项的话题（同条目的 `topic`）；引用的条目要在检查表里，同一次调用里刚加的也行。条目和动作在同一把记录锁里先整体校验、先条目后动作，有一处不对整次都不写。
  - **动作的状态不存，现算**（Python 的 `project_actions.state` 和网页同一套规则，按这个顺序）：条目的下一步在主人手上（`waiting_on` 写了 `owner`；没写过时按缺口文字里的“只差主人”“等主人”这类推断），或有话题在等主人，是“等你”；有话题在跑，是“在做”；有条目且都满足（`done`、`dropped`），是“做完”；条目没满足、话题都结束了，是“待核对”（话题说做完只是它的说法，负责人核对后改条目）；还没有话题，是“将要做”。没有条目的动作不会是“做完”。话题一变状态它马上跟着变，负责人只写条目和 `note`。
  - **条目多的字段**：`title`（24 字，页面和任务图上用）；`waiting_on`（写 `owner` 要在 `gap` 里写要主人做什么；写 `none` 是“不是主人的”，记成空串，旧的写法空串照收；工具的枚举里不放空串，Gemini 不收空的枚举值，agy 上的负责人会整轮 400；没写过读成未定）；`done_at`（`apply` 在条目转成 `done` 时记，转回去清，它才是完成的时刻，`at` 只是最后改动）；`topics`（也参与这一条的话题，至多 6 个，主要的那个仍是 `topic`；`topics_of` 是两者去重的全部。一个话题可以在几个条目、几个动作里）。
  - **开话题时带上位置**：`project_topic_start`、`project_topic_send` 多可选的 `action`（如 `a3`）和 `item`（如 `c9`）。先核对 id，不对就拒绝、不开话题（动作已经 `dropped` 也拒绝）；话题开出来或收进来之后，在记录锁里把它加进动作的 `topics` 和条目的 `topics`；只给 `item` 时，也加进每个含这一条的动作。已经在里面的不重复，放不下的（动作 30 个话题，条目 6 个）不加并在回复里说。协作没开时带这几个参数直接拒绝。话题自己的提示词不变，话题这一侧没有新规则和工具。
  - **状态包里的“简报”段**（放在“目标检查表”前，开着协作时才有）。为省 token 只放最少的字：背景只在新会话里写一次，截 120 字；每个动作一行，如 `a3 链路监控 · 待核对 · 没满足 c9 · 现状：今晚回看`，做完的只写 `a1 仓库搭建 · 做完`，不逐个列话题（上面的话题清单已有）；最后一行“还没挂到条目上的话题：T75、T76”至多 8 个，其余写个数；不做了的动作只在标题行记个数。没写简报时只一句请负责人写。动作的状态、位置和影响、任务图都在网页和 Bridge 里现算，不让模型写，也不进提示词；不新增工具，只给现有的几个加可选参数，描述写得短（协作关着时工具清单、规则、状态包一个字不变）。
- **协作缺口**：汇总方续接轮写的 `collab_gap` 回执（叫醒负责人）留在收件箱里，读过也算没处理，直到负责人用 `project_checklist` 的 `close_gaps` 写明怎么处理的（`closed`：缺口 id → `{how, at, job}`；缺口 id 是 `g` 加回执 id 摘要的 6 位）。
- **状态包**（新会话和续接的每一轮都带，负责人被咨询时的 `read_only_pack` 也带）：话题清单后面先是一段“简报”（见下面的「项目简报」），然后是“目标检查表”，每条一行（id、状态、标准、交付话题和它现在的状态、依赖、证据、缺口；续接的会话里满足和不做了的折成一行 id，“满足或不做了：c1、c2（续接的会话里只列 id）”），再列要核对的：标了满足、依赖的却还没满足（可能冲突或漏了前置结果），交付话题已经结束、这一条还没满足（话题说做完只是它的说法）；然后是“没处理的协作缺口”。还没有检查表时一句话请负责人写。
- **规则**（`app/project_lead.py` 的 `COLLAB_RULES`）：第一轮写检查表，目标变了再改；收到 `thread_end` 或 `collab_gap` 时对照检查表查漏项、冲突和依赖，有漏项就用 `project_topic_send` 让原话题返工或 `project_topic_start` 开新话题，并在检查表写明缺口和由谁补；核对过证据才标 done；需要主人定范围、顺序或取舍时合成一个问题；向主人汇报只说新的东西（“3 条标准只覆盖了 2 条，缺原版基线对照，还不能收尾”），不把话题或汇总方的结论换个说法再发一遍；另有两句讲简报：第一轮写背景并把目标拆成 3 到 8 个动作（每个写清条目、话题和一句现状），开话题、给话题加话时带 `action` 或 `item`，主人在对话里要改简报就照改，动作的状态由 Bridge 算、不用负责人写。
- **收尾门禁**（`app/project_tools.py` 的 `checklist_gate`）：检查表还有 `open`、`blocked` 的条目，或有没处理的协作缺口，`project_finish` 拒绝，逐条列出没满足的条目和缺口，写下一步（返工、补证据、带依据的 `dropped`、`close_gaps`，要主人定的合成一个问题用 `project_ask`）。没写检查表的专项只受缺口约束。它排在原来两道之后：整理专项的 `finish_gate`、还有话题在做。收尾成功时回复列出主人说不做的条目，请负责人在汇报里写明。主人在停住卡上点“收尾”时，`owner_choice` 回执多一句：没满足的条目标 `dropped`（写“主人选了收尾，没做完：…”，依据写回执里给的 `ask:pause-<n>`），缺口同样关掉，不要标成 done。
- **收件箱分组**（`inbox_block`）：先看（协作缺口带 ⚠️、扣住的问题、主人在停住卡上的选择、开工、主人在话题里说的话），再是话题的交付和结束（`thread_end`；它交付的检查表条目还没满足时跟一句，写出满足后直接解锁了哪些条目：“满足后 c15 可开始、c16 还在等 c4”，只算下一步，不算更后面的），然后是其他，最后是协作咨询的回执（`collab_answered`：只供参考，不叫醒，列最新 3 条，其余写条数）。回执里的话题写 T 号（`add_receipt` 写回执时就记下 `label`，协作关着时也一样）。
- **回执合批**（`app/project_loop.py` 的 `settling`）：普通回执（话题结束、主人在话题里说话、停滞提醒等）等到最新一条到了 `COVEY_PROJECT_BATCH_SECONDS` 秒（默认 20）还没有新的才叫醒负责人，最早一条最多等 4 倍，几个话题前后脚结束只跑一轮；开工、主人在停住卡上的选择马上叫醒；扣住的问题、协作缺口短合批：最新一条到了 5 秒（`QUICK_SECONDS`）没有新的就叫醒，最早一条最多等 20 秒，协作关着也这样（扣住的问题有 180 秒，够用）。`collab_answered` 不叫醒，也不参与计时。设 `0` 不攒。
- **不重复转述**（`told_already`）：负责人醒来那一轮读到的回执全是已回带给主人的 `thread_end` 和协作咨询的回执、它只记了 `thread` 或 `note` 汇报时，回复不发；有了新的判断（`milestone`、`finish`）、派了活或转了问题照常发。
- **咨询轮的用量**（`consult_tokens`）：协作咨询轮（在协助方的咨询通道里跑）结束后，它的 token 记进协作记录里汇总方所在的专项；汇总方不在专项里时，记进被问的协助方所在的专项（负责人话题要核对是负责人）。按任务键只记一次（`token_jobs`），所以互相咨询绕不过 `COVEY_PROJECT_BUDGET`。咨询轮仍不写 `thread_end`、不进资料库。

## 整理专项

`COVEY_PROJECT_TIDY` 是 `suggest`（不设就是）或 `auto`、专项也开着时（[配置](configuration.md#整理专项)），专项靠一个机制自己长出来，不只在管家开话题那一刻判断一次。你看到的样子见[使用 · 整理专项](usage.md#整理专项)。

### 话题要点

`core/topic_gist.py`。每个普通话题和专项的话题，由它自己的模型在检查点里写 `topic_gist`：本质、现在的目标（要做成什么，不写进度和状态，做完了照抄原来的目标：网页把它当“目标”）、涉及、相关话题、和上次比变了什么。只在话题还没有要点、或这一轮让目标或涉及的范围变了时写；没写的轮次 Bridge 沿用上一份，追问一句不再多一次写检查点。

- 规则（`core/checkpoint.py` 的 `TOPIC_GIST_RULE`）和这个话题现在的要点放在每一轮消息里检查点文件那句后面，不进话题的规则；管家和负责人的话题没有。
- 没变就不写；变了整份重写，本质要读完整段对话再写，不写标题里第一件具体的事、不写所在的环节。一次也没写过的话题，整理专项第一次遇到它时照旧用一次只读调用补写（`app/project_sorter.py` 的 `backfill`）。
- Bridge 的 `project_tidy` 后台线程每 20 秒读一次刚结束的轮次，把写了的要点存进 `topics/<id>/gist.json`（`essence_at`、最近 5 个本质 `essences`），没写的轮次不动它。第一次启动只设游标，不回头读旧轮次。

### 什么时候整理

- **定时**：早晚汇总的时间点（`COVEY_DIGEST_TIMES`，自己记 `last_slot`，和汇总卡分开发）。
- **没有实时归并**（已删）：以前新话题、要点变了、每轮结束都会单独问一次模型，一个月四百多次调用只归进 4 个话题；现在新话题、新专项该收进来的话题都等下一次定时或手动整理。旧版本夜里扣下的提议卡（`held`）由 `ProposalCards.release` 在夜里过完后发。
- **手动**：对管家说“整理一下专项”（工具 `projects_tidy`，`scope` 可以是一个词或专项 id）；「看板」卡的专项区（只在你的私聊里）；网页发件箱的 `tidy`。同一时间只跑一次（`busy`）。
- 聊天里的话题少于 5 个（`COVEY_PROJECT_TIDY_MIN_TOPICS`）时两个时机都不跑，手动的回一句“话题还不多”。
- 辅助模型选了「不用模型」时定时整理不跑（整理靠模型判断，没有只按规则的整理，卡上只会写没整理成），手动的整理卡写为什么。

### 自动收话题

归进已有专项一律自动、不用点：每次定时或手动整理时，判断把握 ≥ 0.85 的归进直接做；提议卡只管要你点头的事（建新专项、合并、拆开、改名、移出）。以前每轮结束、专项刚建好时的单独判断（规则 `by_rule`、`turn_judge`、`sweep`）随实时归并一起删了。

- 管家开专项时说要收的话题、负责人用 `project_topic_send` 给专项外普通话题加话时（先收进再加话），都走同一个 `join_topic`；话题卡、状态卡同样多一行“已归进专项「X」 · 移出”。
- 目标话题的模型走的网关每日额度正用完时，`project_topic_send` 不发，告诉负责人几点恢复、先换配置（[每日额度用完](harnesses.md#每日额度用完)）。
- **撤回**：点“移出”（话题卡、状态卡、专项卡的“归入记录”上都有），话题记 `never_auto`，整理和负责人加话都不再把它收进专项。
- **在哪看**：专项卡的“归入记录”折叠块（专项记录的 `joins`，最近 30 条）：每行时间、T 号和标题、谁收进的、为什么，移出后写“已移出”；负责人收件箱的 `joined` 回执写同样的来源。

### 读什么、谁判断

`app/project_sorter.py`。

- 看哪些话题（`app/tidy_facts.py` 的 `recent_topics`）：最近 7 天（`COVEY_PROJECT_TIDY_DAYS`）有过一轮的，和在做、停住的专项的话题，最多 40 个，最近动过的在前。不在专项里的优先：专项自己的话题最多占 12 个（`MEMBER_TOPICS`，取它们最近动过的；别的不够 28 个时才多占），因为整理要分的是还没归属的话题，专项的话题留着是为了移出和拆开，专项那一行里也列着它们的本质。只整理一个词或一个专项（`scope`）时不分，照最近的取。
- 每个话题送什么（`topic_row`）：有要点的（补过要点之后每个都有）只送要点（本质、目标、涉及、相关话题，不送“变了什么”）、你的话里提到的别的话题的 T 号（`refs`，要点的相关话题里没有的，最近的在前，最多 6 个）和最近一轮结论的开头（`now`，60 字）：你说过的话和各轮结论要点已经说成几行，拿不准的它会要全文。没有要点的才送你在这个话题里说过的话（每轮的请求，合计 1200 字，留开头和最近的）和每轮结论的第一段（最近 6 段）。都带工作区、仓库、所在专项、开了几天、你说了几次。另有已有专项的名字、目标、状态和它的话题的本质；你以前给的理由（`lessons`）。
- 判断经[辅助模型](configuration.md#辅助模型)（`app/assist.py`），一次调用，做法同 `app/track_judge.py`（没有工具、MCP、hook 和保存的会话，过了上限整组进程杀掉）。判断和补要点用辅助模型那一节的模型和思考预算，和分流、记忆自己长同一套：默认跟随管家（管家在 Antigravity 的 gemini-4-neon、xhigh 上，就用 gemini-4-neon、xhigh，不悄悄换低一档），点名了就用点名的；模型和预算的先后见[配置 · 辅助模型](configuration.md#辅助模型)。判断失败时整理卡写原因（三家的报错按正式轮次的口径分类）、用的是谁和下一步：被官方内容安全拦了给「换辅助模型」，登录失效、额度用完给「换辅助模型」「看诊断」，超时和限流才说“可以过一会儿再试”；网页的整理面板显示进度和同样的原因，带「去设置」。补话题要点遇到模型那边的问题（登录、额度、断连、超时、没有可用的）时不把话题标成“读不了”，整理在这里停下。
- 拿不准时它可以先回 `{"read":[…]}` 要最多 3 个话题的全文（每轮请求合计 4000 字，结论每段加长到 600 字、合计 2000 字，都留开头和最近的），再判断一次。
- 脱敏的话题不送给模型，在结果里单独写明。
- **补要点**：整理（定时、手动）先给没有要点的老话题补：一个话题单独一次只读调用（`GIST_SYSTEM`，读你说过的话合计 6000 字、留开头和最近的，和最近 6 轮结论的第一段），一次读 3 个（`app/tidy_run.py` 的 `READS_AT_ONCE`：跟管家的高档预算读一个要一两分钟），整理卡上显示“正在读 T42（12/40）”。一个读到“没有模型能读”（登录、额度这类）后，别的不再开始，已经在读的到上限为止。读不了的（被官方内容安全拒绝、超时、回答看不懂）只标 `unreadable` 跳过，整理照常做完，卡上写“N 个话题读不了，没参与这次整理”；它有了新的一轮之后的整理会再试。
- **取名**：取本质，对象 + 要达成的事，12 个字以内，不带编号和日期（`core/project_proposals.py` 的 `clean_name` 会去掉 T 号、日期、“第 N 轮”并截到 12 个字）；不取标题里第一件具体的事、不取所在的环节。例：“修第 64 题的审批流程”“优化生成流程的下一环节”两个话题本质都是优化同一套提示词，按标题归成“某环节提效”是错的。
- **判断的硬规则**（`project_sorter.parse`）：新建和拆开至少两个话题（`MIN_CREATE`），新建要有目标；提示词要求专项有终点，不按大主题塞筐，长期值守不建。

### 判断之后

- **归进已有专项**（`app/project_members.py` 的 `join_topic`，把握 ≥ 0.85 才直接归）：
  - 话题 `topic.json` 写上 `project`（角色 `thread`），进专项记录的 `threads`，所以看板和 Pin 把它并进专项那一格；负责人收件箱收到一条 `joined` 回执；收起的专项随之展开。
  - 话题卡、状态卡上多一行“已归进专项「X」 · 移出”；两张都没有的话题，在它的话题串里发一张只有这一行的小卡。
  - 之后管家对这个话题说话要经负责人（`project_send`）。
- **移出**（`leave_topic`）：话题变回普通话题，负责人收到 `left` 回执，话题标记 `never_auto`：以后整理不再自动把它归进任何专项（你点「好」的除外）。回复里带一个可选的输入框“为什么不对”。
- **建新专项**：发一张提议卡到私聊（`cards/project_proposal.py` 的 `proposal_card`）。
  - 归在一起的话题全列出来，每个一行 T 号（点了打开那个话题）、标题、做了几天几轮，下面一行“在做：话题要点的本质；现在：最新一轮结论的第一句”；只有一个话题时开头写“这个话题推了很久，像是一件要长期做的事”。
  - 发卡前先给还没要点的话题补要点，判断和卡片都按本质而不是标题；下面是“为什么提”、专项名和目标、建了以后有什么变化；你的第一张提议卡多一句专项是什么。
  - 卡底是一张表单：哪些话题（下拉多选，提议的话题已勾上，后面是最近的其他话题；不在里面的话题填 T 号）、专项名（已填好，可以直接改），按钮「建专项」「不管了」。勾掉、加上的话题照建，填的 T 号不是这个私聊最近的话题就不加，建好后的卡上写明。没改名就算直接建，改了名记 `name_by: owner`，整理以后不改这个名字。
  - 更早发出的卡还是「建专项」「改个名再建」「不用」「以后别提议」四个按钮，点了照旧。
  - 「建专项」走 `Projects.gather`（步骤 `GATHER_STEPS`：记录、负责人、专项卡、每个话题成为专项的话题、开工回执列出接手的话题），专项 id 由提议 id 定，重复点找到同一个。
  - 「不管了」（旧卡的「不用」）记下这组话题，之后同类提议要多出至少 2 个相关话题才会再提（`declined_like`）。「以后别提议」关掉提议（你说“开个专项”管家照样开）。
  - 连着 5 次直接点「建专项」（没改名），下一张提议卡问一句“以后这种直接建？”，点了以后新建也直接做（同 `auto`），专项卡上的「不要专项」就是撤回。
- **整理专项卡**（定时、手动，`tidy_card`）：先发出来写“正在整理”，补完要点、判断完原地换成结果。
  - “已经做了”：把握很高的归进、收起空闲专项（没有在跑和等回答的任务才收）。
  - 新建不在整理卡上定：每个新建发一张提议卡，整理卡的“新专项的提议”只列名字；判断出的新建和一张还在等你定的提议是同一组话题时，列在“还在等你定”下。整理完把只有一个话题、还开着的旧提议作废（`expire_alone`，卡上写“已过时”）。
  - 开着的提议（两个以上话题）也列在看板的专项区，「建专项」「不管了」在看板上点就定，改的是提议自己的卡，再把看板原地重画；管家的 `projects_list` 同样写出还在等你定的提议。
  - “要你定的”：最多 5 条合并、拆开、改名、移出，每条一块（`suggestion_block`）：标签和粗体的动作（“拆出新专项「X」”“把 T12 移出「X」”）、灰字来源、原因、目标、话题一行一个（超过 4 个先列 3 个，其余折成“还有 N 个话题”），底下是写着动作的按钮和「不用」；定了的换成一行灰字结果。卡顶的结论带写“要你定 · 整理专项 / N 条建议”；标题栏的橙色“N 条建议”和它一样只数还没定的（加上新专项的提议和还在等你定的），都定了换成绿色“整理好了”，结论带写“这次的建议都定好了”。
  - 卡上和网页上点同一条，靠提议记录锁里的认领（`claim`：只有还开着才拿走）只办一次。
  - 读不了的话题在卡上逐个列出原因（`UNREADABLE_WORDS`），未编号的话题用你说的第一句话称呼。
  - 合并把后面几个专项的话题移进第一个，那几个专项取消（原因 `merged`，专项卡缩成“专项已并入另一个专项”）；拆开把选中的话题移出、另建一个专项；改名不碰你取的名字。
- **你写的理由**：在「不用」「移出」下写的理由记进 `projects/tidy/state.json` 的 `lessons`（最近 30 条），之后每次判断都带上，以它为准。

### 提议跟着归入走

话题已经归进专项后，提到它的提议卡不再挂在看板上。

- 整理专项的线程每一轮（`TICK` 秒，`follow`）看一遍开着的提议，不管话题是怎么进的专项。
- 新建提议去掉已归进专项的话题后，还剩两个以上的，卡原地换成剩下的话题，卡上写“T12、T15 已归进专项「X」，这张卡只剩下面 N 个话题”。
- 剩不到两个的作废（`expired`）：卡换成“专项提议 · 已过时”，写明哪些话题归进了哪个专项。还开着的归进提议，话题已在专项里的也作废。和一张更新的、还在等你定的提议是同一组话题（或其中一部分）的卡也作废（`unrepeat`，写“和提议「Y」是同一件事，留那一张”）。之前发出的卡再点，只把卡重画成已过时。
- 新提议先去掉已在专项里的话题，剩不到两个就不提。和一张还在等你定的提议大面重叠（共有的话题至少占较小那组的一半，`overlapping`）时不另发卡：多出的话题补进那张卡（卡上写“又发现 T… 也是这件事，补进来了”）。
- 看板的专项区、管家的 `projects_list` 和整理卡的“还在等你定”读同一张单子（`core/project_proposals.py` 的 `waiting`）。
- 关于某个专项的提议（拆开、合并、移出、改名、收起，`follow_project`）：提到的专项结束或被并走了就作废；拆开提议的话题有的已经不在源专项里，剩两个以上的只拆剩下的，剩不到两个的作废；移出提议的话题已不在那个专项的作废。这些提议列在整理卡的行上，行原地重画（`redraw_row`）。

### 跨专项

不会把 A、B 两个专项的话题加散话题拼成一个新专项。

- 判断的硬规则不让拼：新建只收不在专项里的话题，拆开只从一个专项里拿、不拿光，合并是整个专项合并；自动归进也只收不在专项里的话题。
- 点「好」拆开时再核一遍：只搬还在源专项里的话题（移出过的、别的提议先搬走的留在原处，结果里写明没带上），剩不到两个就不拆；源专项负责人收到的回执写话题拆去了哪个新专项（合并写“随合并转进专项「X」”）。
- 专项被拆开或移出拿走最后一个话题、又没有在跑和等回答的任务时马上收起（`fold_if_empty`），你再在里面说话会展开。
- 提议卡上勾选或填 T 号时，已在别的专项里的话题不收，结果写“T… 已在专项「X」里，没加”，全是这种就不建。

### 别处

- **巡检**：“我本来想找你的事”（巡逻）已下线，见[已下线的功能与旧配置](legacy.md#已下线的功能)。
- **网页**：推送的话题多 `gist`，发件箱认 `tidy`、`tidy_decide`（见[网页工作台](web.md)）。
- **记录**：`<state>/projects/tidy/`：`state.json`（游标、定时、你的偏好 `prefs`、理由；旧版本排队的实时判断 `queue` 下次读要点时清掉）、`proposals/<id>.json`（每条提议和你的决定，状态 `open → accepted → done|failed`，或 `declined`、`never`）、`topics/<话题>.json`（`never_auto`、归进过哪里；旧版本记的实时时机 `fired`、`judged_*` 不再读）、`runs/<run>.json`（每次整理的卡和结果）。持记录锁时不调模型、不发飞书。
- **开关关着**：没有后台线程，每轮消息里没有话题要点那段，管家没有 `projects_tidy`，设置卡没有这一行，网页不推 `gist`、发件箱的 `tidy` 回 failed，巡检照旧按词判断。

## 汇报风格的默认值

负责人用 `project_style` 改风格时，整份风格（`report`、`detail`）也记进 `<state>/project-style.json`；之后转成专项、直接开的新专项的记录从这份风格开始（`Projects.seed_style`），负责人的规则和状态包里就是它。已有的专项不动，负责人随时还能改。
