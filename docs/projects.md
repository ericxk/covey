# 专项

专项是一件要分几个话题、跨几天推进的事。管家把它交给一个**负责人**：一个不露面的话题，由它开话题、派活、跟进，做完了向你汇报。前半篇是使用者概览，后面各节是规则和实现；底座（记录、状态、负责人怎么跑、护栏）见[架构 · 专项](architecture.md#专项第-2-期开发中默认关)，开关见[配置](configuration.md)。

## 使用者概览

**默认开不开。** 代码里不设是关；`./install` 新装的服务写上 `COVEY_PROJECTS=1` 和 `COVEY_PROJECT_TIDY=suggest`（整理专项只提议），所以装好就有。专项由管家开，私聊模式要是“管家”。关掉：`COVEY_PROJECTS=0` 重新注册服务。进阶开关都要 `COVEY_PROJECTS=1`：

| 开关 | 打开后多什么 |
| --- | --- |
| `COVEY_PROJECT_AUTOWAKE=1` | 专项的话题一轮结束就叫醒负责人 |
| `COVEY_PROJECT_ASK=1` | 专项被护栏停住时发卡问你继续、收尾还是停（[专项停住后问主人](#专项停住后问主人)） |
| `COVEY_PROJECT_MEMORY=1` | 专项的话题开工带上专项记忆和资料库（[专项记忆与资料库](#专项记忆与资料库)） |
| `COVEY_PROJECT_TRIAGE=1` | 专项的话题问的选择题先交给负责人（[专项的问题分流](#专项的问题分流)） |
| `COVEY_PROJECT_UPGRADE=butler` | 管家可以把一个派发出去的话题转成专项（还要开[派发卡](butler.md#派发卡开关默认关)） |
| `COVEY_PROJECT_TIDY` | `suggest` 只提议、`auto` 直接建、`off` 关（[整理专项](#整理专项)） |
| `COVEY_PROJECT_STYLE_KEEP=1` | 负责人改过的汇报风格成为新专项的默认（[汇报风格的默认值](#汇报风格的默认值)） |

**专项怎么来。**

- 对管家说“开个专项做……”，管家直接开一个专项，你点名要收进来的已有话题一并挂进去。
- 管家看出一个话题要长期跟进时把它转成专项（要 `COVEY_PROJECT_UPGRADE=butler`）。
- 开了整理专项时，话题多了以后私聊来一张“建个专项？”提议卡，点「建专项」就建；能归进已有专项的话题自动归进。

**私聊里看到什么。**

- **专项卡**：聊天区一条新消息，专项名、状态（在做、等你、停住、做完），各话题在做什么，负责人现在在干什么，下面有补充、停止专项、不要专项。
- **负责人的汇报**：顶层的新消息，说话人写“专项「名」· 负责人”。负责人自己醒来的轮次默认不说话，只有该报的进展、派了活、停了话题、替你答了或转给你问题时才发。
- **你在等的结果**：你和负责人说话的那一轮里它开的话题、加的话，那一轮话题做完（或停了），结论直接发到聊天区，和管家派出去的话题一样，不用你去问；负责人不再转述同一件事（[主人在等的结果](#主人在等的结果)）。
- **问题卡**：专项的话题要你定的事，问题卡在话题串里和聊天区各一张，卡上写是哪个话题在问。
- **看板**：一个专项一格，它的话题不再单独列。
- 停住卡、提议卡、整理专项卡见下面各节。

**怎么用。**

- 引用专项卡或负责人的回答说话，就是对负责人说；新的事和某个专项是同一件事时，对管家说，管家会交给它的负责人。
- “停掉 T1”：管家转给负责人，负责人停掉那个话题。
- 专项卡上的「不要专项」把专项降为普通话题。
- 话题被归错了，点话题卡、状态卡上的「移出」。
- “整理一下专项”：马上整理一遍。
- “比较一下 A 和 B 两种做法”：负责人开两个只读话题，给同样的任务说明，尽量一家一个模型；两边都做完后汇总，写清采纳了哪边的哪部分、为什么，以及两边都没回答的问题（负责人规则里的一条，#37）。

## 专项卡

`COVEY_PROJECTS=1` 时，每个专项有一张卡：聊天区的一条新消息，不开串（飞书对已有串的消息，回复一律进串，所以不回复你那条消息；你那句话直接开的专项，顶上带“你问”块）。点击和引用它回复都按消息别名路由到专项的负责人话题，所以按钮是负责人话题的点击。**只有 `ProjectCards`（`app/project_cards.py`）写它**（规则 3）。

- **内容**（`cards/project_card.py` 的 `project_card`，element_id 都不超过 20 个字符）：
  - 卡头 = 专项名 + 状态标签（在做、等你、停住、做完）。
  - `pj_need`“需要你”（摘要 + 打开问题卡 ›）、`pj_meta`（话题数、用时、token）、`pj_lead`（负责人现状 + 最近一句 note）。
  - 话题折叠面板 `pt_<话题前 6 位>_<状态字母>`：在做和等你的展开、做完的收起，**状态变了元素 id 就换**（客户端对同一个 id 改 `expanded` 不一定重画）；等你的排最前、做完的最后，最多 8 个，其余一行 `pj_more`“更早 N 条”。
  - `pj_triage`、`pj_mem`、`pj_lib` 三个收起的面板（分流记录、专项记忆、资料库，空就不画，后两个每行一个“删”）。
  - `pj_io` 灰框：输入是负责人自己的 Harness、模型、思考预算（取它最新任务，还没有任务时取它 topic.json 的绑定）；各话题用的 Harness 写在自己折叠面板的末行。
  - `pj_btns`：补充、停止专项、不要专项（停住的没有停止，做完的没有按钮）。没有输入框：会重画的卡不放输入框，补充另发一张表单卡。
  - 体积 5–13 KB。各个开关全开、每份清单都满时会超过一张卡的容量（`CARD_NODES`、`CARD_BYTES`）：`project_card` 按 `FIT_STEPS` 一步步让折叠面板少画几行、话题少画几个（剩下的写成“另有 N 条”“更早 N 条已收起”），直到放得下；放得下时一个字不变。
- **读什么**：只读任务记录和问题（没有飞书调用，不拿锁）。话题的状态和一句话沿用派发卡（`app/dispatch_cards.py` 的 `status_of`）；记录字段 `lead_note`、`tokens_used`、`conclusion_message_id`（负责人收尾报告的消息）、`triage`、专项记忆（`projects/<id>/memory.json`，删掉的和风格行不画；卡上的“删”写墓碑，不真删）、`projects/<id>/library/`；空的不画。
- **刷新**：后台线程每秒看一遍，摘要变了且离上次写至少 2.5 秒才整卡 PUT；每次写前从 `reserve` 取 sequence 存进 `record["card"]`，失败按 2、4、8 … 最多 60 秒退避。摘要也存在记录里，重启不会为同一张卡再写一次。
- **做完**：专项 `done` 后卡缩成一行（`settled_card`，链到那条结论）。
  - 结论是 `conclusion_message_id`；没有就看收尾的那一轮：它结束了且在顶层发了回答，链到那条；结束了还没有回答的 id，再等 30 秒（`ANSWER_WAIT`），仍没有就缩、不带链接；还在跑就等它，最多 10 分钟。
  - `cancelled` 缩成“⏹ 专项已降为普通话题”。缩完记 `card.closed`，不再刷新。
  - 你之后又在专项里说话（负责人话题、专项的话题、管家转来、网页），专项重新打开，`card.closed` 清掉，下一次刷新在原处画回整张卡。
- **14 天翻页**：CardKit 的卡实体 14 天后不能改。卡龄过第 12 天（`FLIP_AFTER`）新发一张卡（键里带代数；发不出去下次用同一个 `pending_card_id` 重试），记录、别名、Pin 改指新卡，旧卡缩成“已移到新卡 ›”，写不了 3 次就撤回。
- **按钮**：`bridge_project_steer`、`bridge_project_stop`、`bridge_project_downgrade`、`bridge_project_mem_del`、`bridge_project_lib_del` 在 `ACTIONS` 里，都不是 `bot_only`：没有一个新建任务，值带 `project_id` 和负责人的 `topic_id`，不带 `job_id`，所以任务进程不会收到。
  - 补充 = 负责人正在跑的那一轮的补充表单；负责人空闲时不新开一轮，回一句“引用这张卡回复”。
  - 停止专项 = 记录转 `paused`（停住），并停掉负责人和各话题里排队或在跑的任务：任务在活着的任务进程里，就把它卡上“停止”的点击转给任务进程；点击写的是话题自己的别名 `project-stop-<话题>`，没有任务卡的安静轮也路由得到。“不要专项”停负责人也走这里。
  - 不要专项调 `app/project_clicks.py` 的 `downgrade`（降级，见下）。
  - 删记忆、删资料只删自己那一行（资料只认 `library/` 里的文件名，不认路径）。
- **转成专项的卡**：派发卡转成专项时还是同一条消息、同一个 `card_id`，下一次刷新整卡换成专项卡，`pj_meta` 末尾多一句“由管家转成专项”或“来回 3 轮后转成专项”；同话题其余还活着的派发卡写成一行“已并入专项 ›”（`merged_card`）。
- **不要专项**：专项记 `cancelled`，卡缩成“⏹ 专项已降为普通话题”，负责人在跑的任务停掉，专项的话题变回普通话题；这条卡和并入的那几行以后被引用回复，回到原话题。
- **Pin**：看板的格是专项（`core/board_read.py` 的 `cells`）；在做钉专项卡，等你钉话题的问题卡，做完钉结束的那个话题的答案卡（没有就钉专项卡）；专项还没有卡时钉话题自己的卡。手上的事和早晚汇总的行用 `label_title`，格叫“专项 · 专项名”。

## 主人在等的结果

成员话题的一轮结束后，放置表里它的结论只留在自己的串里，顶层只收到它要你回答的问题（`core/placement.py` 的 `project_member` 行）；结束本身变成负责人收件箱里的 `thread_end` 回执，叫醒负责人（`COVEY_PROJECT_AUTOWAKE=1`），由负责人决定说不说。负责人醒来的轮次回复不发，只有它标了 report、汇报风格又放行的 note 才发：默认风格“只报里程碑”只放 `milestone`、`finish`，报话题结果的 `thread` 被拦下。所以负责人当着你说“出结果后我发给你”，结果出来时它记了一条 `thread` 汇报，被风格拦住，你只能自己去问。

现在的规则：

- **哪一轮算你在等**：成员话题的这一轮，是负责人在**你在场的一轮**里交出去的：`project_topic_start` 开的、`project_topic_send` 加的话或给在跑那一轮的补充（`main-thread/opened/` 里那条请求记录的 `job_key` 是负责人的任务，消息号不是叫醒的 `lead-…`）；自动重试接着原来那一轮算。负责人叫醒自己那轮交出去的、你直接在成员话题里说的，都不算。判断在 `app/relay_targets.py` 的 `awaited_target`。
- **怎么发**：这一轮做完或停了（不算等回答：问题照旧走问题卡和分流），任务进程按管家派出的话题那样把结论回带到聊天区顶层（`app/butler_relay.py`，每个任务只发一次，记录在 `main-thread/relays/`），“你问”块是你对负责人说的那句话。不经过负责人，也不看汇报风格，所以一定送到。
- **不推两次**：这一轮的 `thread_end` 回执记 `relayed: true`，负责人的状态包里这条回执后面写“结论已由 Bridge 直接发给主人，不要再转述”；负责人醒来那一轮读到的回执全是这种、它只报了 `thread` 或 `note` 时，回复照样不发（`app/project_loop.py` 的 `told_already`）。它据此有了新的里程碑判断（`milestone`、`finish`），或者又派了活、转了问题，照常发。
- **负责人的说法**：规则里告诉负责人，你在场时它交出去的活，对你说“T12 出结果会直接发到这里”，不要说“我发给你”。

## 专项可长可短

专项不分长期和临时：可长可短，没活放久了收起，有新的事再展开。

- **新的事自动归进已有专项**：管家每一轮的快照里多一栏“专项”（id、名字、状态——在做、停住、收起——和一句目标；做完和取消的不列）。管家规则（`app/prompts.py` 的 `PROJECT_RULE`）和 `project_send`、`projects_list` 的说明写清：新的事和某个专项是同一件事，就用 `project_send` 交给它的负责人（收起的随之重新展开）；拿不准就开普通话题；你说“这是 X 的事”就归进 X，不再判断。没开 `COVEY_PROJECTS` 时规则和快照逐字不变。
- **空闲收起**：专项没有要做的事（负责人和各专项的话题都没有排队或在跑的任务、没有没读的回执；只剩等你回答的也算没事可做），你也没提它，满 `COVEY_PROJECT_IDLE_DAYS` 天（默认 7）就收起：`paused` + `state_reason: idle`，专项卡缩成一行“收起 · N 天没有新的事”，再写“有新的事会自动展开”，不弹停住卡、不发问题卡。你对它说话、管家把新的事交给它时自动回到在做。试用：`COVEY_PROJECT_IDLE_DAYS=0.001`（约 86 秒）。
- **停掉专项里的一个话题**：对管家说“停掉 T1”，管家用 `project_send` 交给负责人，负责人用 `project_topic_stop`：停掉那个话题排队和在跑的任务，收掉它等你回答的问题（卡上写“负责人按你的意思停了这个话题”），还没点开始的启动卡也一并收掉；话题仍记在专项里、算结束，专项因此能收起或收尾。只能停本专项的话题。
- **同时在做的话题不设上限**：负责人想开几个就开几个；几个话题都要部署时靠排队部署错开，不靠限制话题数。旧记录和 `project-style.json` 里留着的 `spawn` 照读不用。
- **停滞只管有活没动**：见架构里的护栏。
- **旧记录**：记录里已有的 `direction` 字段照读不画；环境里还设着 `COVEY_DIRECTIONS` 也不出错（不再读它）。

## 专项记忆与资料库

**记忆**不受开关影响：负责人的 `project_remember`、`project_style`、状态包、专项卡和卡上的“删”都经 `core/project_memory.py`，读写同一个文件 `projects/<id>/memory.json`。旧版留在专项记录 `memory` 字段里的条目照常读出来、和文件合并显示，下一次写入搬进文件。

`COVEY_PROJECTS=1` 且 `COVEY_PROJECT_MEMORY=1` 时再多三件事：

- **话题开工带上专项记忆**：专项的话题（不含负责人，它有自己的状态包）的新会话，规则里在原则之后多一块“专项记忆”（至多 3000 字，超了先丢最旧的），后面跟资料库索引（至多 2 KB）；续接的会话每一轮的提醒里只带记忆（内容由 `app/project_context.py` 的 `block` 取）。专项取消后、代答话题、普通话题都不带。
- **你答问题卡记一条决定**：专项的话题或负责人发出的问题卡，你提交回答后记一条 `kind=decision`、`source=owner_answer`：“主人答：题目→回答”（每题题目至多 70 字、回答至多 50 字，合起来不超过 200 字）。反馈、全部跳过的不记。
  - 开了问题分流时，负责人替你答的那一条**不记**：它是负责人的回答，只在“分流记录”和决定日志里；你自己答的（负责人转给你的、3 分钟超时转出的）照常记。
  - 你在分流记录上点“不对”纠正后，同一句话也记成一条 `kind=decision`、`source=owner_fix` 的记忆。
- **资料库**：`projects/<id>/library/` 放文件，`library.json` 放索引（`core/project_library.py`）。
  - 来源一，你回复或引用专项卡带的文件：消息进负责人话题时复制进来、记 sha256（同内容只一条；单个文件超过 25 MiB 或总量超过 200 MiB 的不复制，只记原来的路径）。
  - 来源二，专项的话题每轮的产物（检查点的 `artifacts`）和 `delivery`：Bridge 在任务进程结束后只记路径、链接或一行交付，不复制（规则 8：任务进程不写专项的东西）。
  - 索引不超过 2 KB（最新的在前，超了写“另有 N 条”），进两处：负责人的状态包和专项的话题的第一轮。设备上的话题读不到本机的文件。
  - 专项卡的“资料库”面板列索引，每行有“删”（删索引、同时删复制的文件）；索引没有登记的旧文件照旧按文件名列、按文件名删。

**限额**：

- 记忆超过 40 条或 6 KB 时先删墓碑，再删最旧的 `source=owner_answer`，最后才删最旧的其他条目（负责人记的约束和决定排在最后；风格行不删）。
- 资料库超过 100 条时先删最旧的话题产物和交付，只剩你发的文件时才删最旧的；单个专项文件超过 200 MiB 的 `trim` 也是话题的文件在前。
- 复制资料先写到 `library/` 下的临时文件（`.incoming-*`），对副本算 sha256 和大小、在专项的锁里判上限，再改名。
- `memory.json`、`library.json` 写之前读不出来（权限、IO 错误）就让这次写失败，不当成空文件覆盖；文件在但解析不了，先改名留底 `<名字>.bad-<时间>`、日志写一行，再按空的继续。

**维护**（`core/maintenance_rules.py`）：专项做完 30 天后删资料库里的文件、索引留着；已结束（做完、已取消）的专项记忆条目 180 天后删，在做和停住的专项不动；`projects/` 不进备份。

## 专项的问题分流

`COVEY_PROJECTS=1` 且 `COVEY_PROJECT_TRIAGE=1` 时，专项的话题问的选择题先交给负责人（`app/triage.py`、`core/triage.py`、`core/project_gates.py`）。关着时问题卡的发法、重投、恢复和没有这个功能时一样，问题记录里没有 `triage` 字段，负责人没有那两个工具。

- **谁交给负责人**：以下全部成立才交：
  - 开关开着；问题是专项的话题（`topic.json` 的 `project.role` 是 `thread`）问的，专项是 `active`；
  - 问题挡着这一轮（`blocking`）；
  - **每一道题都有选项**（有一道自由文字就直接给你）；
  - 题目、标题、选项文字里没有硬闸词。
  - `Triage.route(ctx, job, record)` 在两个发卡的口子前调：原生的活问题和检查点、暂停的问题；它出任何错都按“给你”走。
- **扣住是什么样**：问题记录加 `triage: {state: held, at, deadline: 现在+180 秒, project, receipt}`，`status` 仍是 `pending`，`display_pending` 仍是真，所以所有“待回答的问题”的列表都看不到它，也没有你能点的卡。话题的任务卡上那一行写“已交负责人”。`state` 只有 `held → answered_by_lead | escalated`（`TRIAGE_TRANSITIONS`），都是终态。
- **扣住的问题不算没投出去**：任务记录的 `question_delivery_ok` 是真，所以 `undelivered_jobs` 不重投，恢复判定（`core/recovery.py` 的 `classify`）和问题卡已发出时一样。Bridge 重启时 `recover_question_delivery` 跳过扣住的问题，由 `sweep` 照常接着数 180 秒。任务进程只写自己这道题的记录，扣住时不发卡也不碰收件箱，活问题的任务进程照常等答案。`tests/test_project_triage.py` 的 `HeldDeliveryTest`、`HeldLiveQuestionTest` 逐条验证。
- **回执和 3 分钟**：Bridge 的 `ProjectLoop` 每 10 秒扫一遍扣住的问题（`sweep`）：没有回执的，往专项收件箱写一条 `question` 回执（这种回执不用 `COVEY_PROJECT_AUTOWAKE` 也唤醒负责人）；到了 `deadline`、专项不再 `active` 的，发给你。负责人的状态包里“交给你的话题问题”一段有每道题的 id、题目、选项和还剩几秒（`app/triage_view.py`）。
- **负责人的两个工具**（只在开关开着时列给负责人）：
  - `project_answer(thread, answers)`：每题都要答，答案是选项原文，多选给数组；走 `Questions.submit_answer`，效果和你点“提交回答”一样，补充说明是“（负责人按专项记忆替主人答的）”。提交前先把 `display_pending` 记成假并写 `answering`；提交失败就把问题转给你。
  - `project_escalate(thread, why[, context, recommend, if_not])`：问题卡马上按原来的口子发给你（话题串里一张，私聊顶层一份副本），卡上多一行“负责人转给你的理由：…”；写了 `context`（背景一句话，最多 120 字）卡上理由下面多一行灰字“背景：…”，写了 `recommend`（推荐的选项原文）多一行“负责人推荐：…”，再写 `if_not`（不选它的代价）就跟在后面一行；三个都不写，卡跟以前一样（到期按推荐执行不做，只是写给你看）。这三项记在题目的 `triage` 里，任务卡上的那一行换成“转给你了”；卡发不出去时任务记录记 `question_delivery_ok: false`，你那边是平常的“重新投递”。
- **转给你的活问题由任务进程发卡**：原生的活问题（Claude 的 AskUserQuestion，轮还没结束、任务进程在等答案）转给你时（负责人转、3 分钟超时、专项停了、你在话题里说话），Bridge 不自己发卡：活问题的后端控制和这一轮到提问为止写过的内容（进展说明和正在写的正文）只在任务进程里，Bridge 手上的 `RemoteControl` 两样都没有。`triage.show` 往任务进程的 inbox 写 `show_question`（`runner_ipc.show_in_runner`，最多等 20 秒确认），任务进程 `Questions.show_handed_on` 发问题卡、改任务卡那一行，再在私聊顶层发副本，副本上方带这一轮写过的内容，和没被扣过的问题一样。旧版本的任务进程不认这条消息、不回确认，按发不出去处理（任务记录 `question_delivery_ok: false`）。任务就在 Bridge 里跑时照样在本进程发。扣住期间私聊顶层不发任何东西（`NativeQuestions.mirror` 跳过扣住的问题）。任务结束时（停止、失败、做完）它没发出卡的问题（扣住的、卡没送到的）也随 `cancel_questions` 撤回；任务已经不在、却还挂着的活问题，在你往这个话题发下一条消息前撤回（`Questions.retire_orphaned_live_questions`），不再让每条消息都收到“原结果或问题控件尚未送达”。任务还在等、卡却没发出去的活问题（任务进程 20 秒没确认，或卡发失败），任务记录不记成失败（轮还在跑，只记 `question_delivery_ok: false`）；分流的巡检每 60 秒再让任务进程发一次卡，最多 5 次（`RESHOW_EVERY`、`RESHOW_TRIES`，次数记在题目的 `triage` 里）；你往这个话题发消息时也先再试一次，发出去了你这条就当回答或补充，还是发不出去就回一句“问题卡没发出来，可以先停止这个任务”（`triage.reshow`）。
- **负责人的回答要确认**：`project_answer` 提交时任务进程还活着，答案只是写进它的收件箱，问题记录仍是 `pending`。这时分流状态保持 `held`，工具回“还没确认收到”；`sweep` 看到问题记录已落地才改成 `answered_by_lead`；`answering` 超过 90 秒（`ANSWERING`）仍是 `pending` 就转给你（理由“负责人的回答没有送到”）。这 90 秒里 `sweep` 对这道题所有分支都不动。
- **硬闸**（`core/project_gates.py`，只用标准库）：一份词表，查题目、标题、选项的标签和说明，命中就直接给你：
  - 中文：部署、发布、上线、下线、发给、对外、转账、付费、付款、购买、充值、花钱、额度、扣费、删除、清空、覆盖原/掉/现有/画板/文档、停用、排空、批一份、不可逆、无法恢复、强制、生产环境、线上环境/服务、到线上、密钥、密码、令牌；
  - 英文整词：`rm`、`force`、`deploy`、`release`、`publish`、`delete`、`drop`、`truncate`、`purge`、`wipe`、`destroy`、`prod`、`production`、`sudo`、`password`、`secret`、`api key`、`payment`、`billing`。
  - 词表宁多勿漏：多一次命中只是你多看一张本来就会看到的卡。“线上”“token”“预算”“清理”“回滚”这类在问题里多是别的意思的词不在表里，漏的靠负责人自己判断、3 分钟超时和“不对”兜底。
- **你看得到**：负责人替你答的每一条、每一次转给你，都是专项卡“分流记录”里的一行（最多 40 条）；答的那行带一个“不对”按钮（`bridge_project_triage_wrong`）。
  - 点了发一张只有一个输入框的小表单卡（`cards/triage_card.py`；专项卡会重画，不放输入框）。
  - 提交（`bridge_project_triage_fix`，`bot_only`）后：这句话作为一条消息排进那个话题（消息 id `triage-fix-<题的 token>`），写进专项的决定日志（负责人每一轮看最近 10 条），那一行之后显示“已纠正”；表单卡整卡换成“已纠正”的卡，再提交会被拒。
  - 开了 `COVEY_PROJECT_MEMORY` 时，纠正还记成一条 `source=owner_fix` 的专项记忆。
- **你在话题里说话**：话题里有交给负责人的问题时，你在这个话题发消息先把这些问题转给你（理由“你在这个话题里说话了”；负责人的回答正在送的不转），然后这条消息照“话题里有一张待答问题卡”处理：只有一道题时是回答，几道题时是补充说明。
- **开关关掉后**：没人处理的扣住问题一律给你。`sweep` 在分流关着时把它们都转出去（理由“问题分流已关闭”）；`ProjectLoop` 只在 `COVEY_PROJECTS=1` 时跑，所以 Bridge 启动时在 `recover_question_delivery` 之后无条件调一次 `triage.settle_closed`。已知限制：任务进程的环境开着分流而 Bridge 关着时，任务进程在 Bridge 启动之后新扣住的问题要等下一次 Bridge 重启才转给你。
- **和停住的配合**：`COVEY_PROJECT_ASK=1` 时 token 停住会请专项的话题里在做的任务停下。这时还扣着的检查点问题，下一次扫发现专项不再“在做”，转给你，只转一次；正在等答案的活问题，它的任务被请停，后端随任务撤回问题，不转（你点继续后由负责人重新把活交给话题，话题会再问）。

## 专项停住后问主人

`COVEY_PROJECT_ASK=1` 时，护栏停住专项（`state_reason` 是 `tokens`、`wakes`、`stalled`，见[架构 · 专项](architecture.md#专项第-2-期开发中默认关)），`ProjectLoop.pause` 在同一次写记录里加一份 `pause_ask`：`{reason, why, at, choice, halted, card}`。`ProjectCards` 看到它，在专项卡所在的位置发一张**停住卡**（`cards/project_card.py` 的 `ask_card`）：

- 卡头专项名 + 红色“停住了”标签（护栏停的算停住了，见 [UI 规范](ui.md#3-状态词表)；橙色只给等你和可能卡住）。
- `pa_why` 一句话写为什么停（`project_loop.pause_words`）：“token 用到上限 1000 万”（只在设了 `COVEY_PROJECT_BUDGET` 时有，默认没有 token 上限）、“负责人连续叫醒 30 次没有你的消息”、“负责人一小时内叫醒了 12 次”、“62 分钟没有进展”。
- `pa_note` 写在做的话题怎么样了；三个按钮 `pa_go` 继续、`pa_wrap` 收尾、`pa_stop` 停。

**三个按钮**：`bridge_project_ask_continue`、`bridge_project_ask_finish`（`bot_only`：它们让负责人再跑一轮）、`bridge_project_ask_stop`（不是 `bot_only`，和停止专项一样），`handler` 都是 `controls.project_ask`。点击先在记录锁里记选择（只有专项还因这个原因停着、这张卡是当前这次停住的卡、还没选过才算数；否则回一句“选择已经做过了”“这是之前一次停住的卡”等，什么都不改），再做事：

- **继续**：专项回到 `active`，唤醒计数清零；`tokens` 停住再给一份预算（`token_floor`）；给负责人一条 `owner_choice` 回执，它永远唤醒负责人。
- **收尾**：同样把专项重新开起来，回执要负责人总结做完了什么、还有什么没做完，用 `project_note` 标 report 告诉你，然后调 `project_finish`（还有话题在做时它会拒绝，等它们结束再收尾）。负责人的规则要它把话题说的“做完”当作话题自己的说法：收尾前对照完成标准抽查关键产物和检查点的提交、部署、自检，只提了合并请求、合了没部署的不算做完。
- **停**：记录仍是 `paused`，`state_reason` 改成“主人停止”，并停掉负责人和各话题里排队或在跑的任务；之后你在负责人话题里说话把它开起来时，照样给一份新预算，不会马上又停。

其余规则：

- **在做的话题**：`tokens` 停住时同时请专项的话题里排队、在跑的任务停下（把卡上“停止”的点击转给任务进程），数记进 `pause_ask.halted`，卡上写“在做的 N 个话题已请它们停下”；`wakes` 停住不停它们，卡上写“不受影响”；`stalled` 本来就没有。
- **点了以后**：这张卡整卡写成一行（“你选了继续 / 收尾 / 停”），专项卡下一次刷新自然变成在做或停住。专项被别处处理了（你在负责人话题里直接说话、负责人收尾）而没点，这张卡缩成“已在别处处理”。每张卡的写入用它自己的 sequence（`pause_ask.card`）。
- **试用**：设 `COVEY_PROJECT_BUDGET=<小数>` 一会儿就停住；`COVEY_PROJECT_STALL_SECONDS=60` 并开 `COVEY_PROJECT_AUTOWAKE=1`，一个有任务排队或有没读的回执、却没有动静的专项约两分钟后停住（没有要做的事、或只在等你回答的专项不会停滞）。唤醒次数的上限不能调。

## 整理专项

`COVEY_PROJECT_TIDY=suggest`（或 `auto`）且 `COVEY_PROJECTS=1` 时（[配置](configuration.md#整理专项)），专项靠一个机制自己长出来，不只在管家开话题那一刻判断一次。代码里不设就是关；`./install` 新装的服务写上 `suggest`。你看到的样子见[使用 · 整理专项](usage.md#整理专项)。

### 话题要点

`core/topic_gist.py`。每个普通话题和专项的话题，由它自己的模型在检查点里写 `topic_gist`：本质、现在的目标（要做成什么，不写进度和状态，做完了照抄原来的目标：网页把它当“目标”）、涉及、相关话题、和上次比变了什么。只在话题还没有要点、或这一轮让目标或涉及的范围变了时写；没写的轮次 Bridge 沿用上一份，追问一句不再多一次写检查点。

- 规则（`core/checkpoint.py` 的 `TOPIC_GIST_RULE`）和这个话题现在的要点放在每一轮消息里检查点文件那句后面，不进话题的规则；管家和负责人的话题没有。
- 没变就不写；变了整份重写，本质要读完整段对话再写，不写标题里第一件具体的事、不写所在的环节。一次也没写过的话题，整理专项第一次遇到它时照旧用一次只读调用补写（`app/project_sorter.py` 的 `backfill`）。
- Bridge 的 `project_tidy` 后台线程每 20 秒读一次刚结束的轮次，把写了的要点存进 `topics/<id>/gist.json`（`essence_at`、最近 5 个本质 `essences`），没写的轮次不动它。第一次启动只设游标，不回头读旧轮次。

### 什么时候整理

- **实时**（`ProjectTidy.realtime`，只看这一个话题，对照已有专项和最近 7 天动过的话题）：
  - 开了新话题、它的第一轮结束（要点有了以后）；
  - 要点的“本质”变了（换说法不算：去掉空白标点后字对的重合 ≥ 0.6 算没变，`same_essence`）；
  - 话题跨进第 3 天又有一轮结束，或你在里面说到第 15 句（这两个每个话题一次）；
  - 你发起的每一轮结束（只归进已有专项，见下面“自动收话题”）。
  - 专项的话题和负责人不做实时判断。
- **定时**：早晚汇总的时间点（`COVEY_DIGEST_TIMES`，自己记 `last_slot`，和汇总卡分开发）。
- **夜里攒到早上**：实时判断在夜里（`core/quiet_hours.py`：`COVEY_QUIET_HOURS`，没设时是早晚汇总最后一个时间到第一个时间）提议的新专项，提议卡先不发，记 `held`，夜里过完由 `ProposalCards.release` 发；其间看板照样列着它，可以直接在看板上定。定时和手动整理的提议卡照常马上发。
- **手动**：对管家说“整理一下专项”（工具 `projects_tidy`，`scope` 可以是一个词或专项 id）；「看板」卡的专项区（只在你的私聊里）；网页发件箱的 `tidy`。同一时间只跑一次（`busy`）。
- 聊天里的话题少于 5 个（`COVEY_PROJECT_TIDY_MIN_TOPICS`）时三个时机都不跑，手动的回一句“话题还不多”（“自动收话题”只归进已有专项，不受它限制）。

### 自动收话题

专项随你的提问自动变化，不靠手动管理，也不用点「整理」：归进已有专项一律自动、不用点；提议卡只管要你点头的事（建新专项、合并、拆开、改名、移出）。

- **规则**（每次实时判断先跑，`ProjectTidy.by_rule`）：话题要点的“相关话题”里点了某个在做专项的话题，而且只点了这一个专项的，算候选：小模型只读这一个话题对照这一个专项（`rule_confirm`，一次调用），把握 ≥ 0.85 才归，`joins` 里记 `by: rule`。“相关话题”只说明这个话题提到过它们，不说明是同一件事。判过了，这一轮就不再跑下面的每轮判断。
- **你每说一轮**（原因 `turn`）：普通话题里你发起的一轮结束后，先跑规则；判不出时，小模型只读这一个话题对照在做的专项（`turn_judge`，一次调用），把握 ≥ 0.85 才归；话题要点和上次判断时一样就不调。这里不提议建新专项。
- **专项刚建好**（直接开专项、整理专项的建专项，`queue_sweep` → `sweep`）：把最近 7 天动过、不在任何专项里的话题（规则指向别的专项的除外）一次调用对照这个专项判断，把握够的归进来。
- 管家开专项时说要收的话题、负责人用 `project_topic_send` 给专项外普通话题加话时（先收进再加话），都走同一个 `join_topic`；话题卡、状态卡同样多一行“已归进专项「X」 · 移出”。
- **撤回**：点“移出”（话题卡、状态卡、专项卡的“归入记录”上都有），话题记 `never_auto`，规则、每轮判断、建专项后的扫描和负责人加话都不再把它收进专项。
- **在哪看**：专项卡的“归入记录”折叠块（专项记录的 `joins`，最近 30 条）：每行时间、T 号和标题、谁收进的、为什么，移出后写“已移出”；负责人收件箱的 `joined` 回执写同样的来源。

### 读什么、谁判断

`app/project_sorter.py`。

- 每个话题的要点，加你在这个话题里说过的话的全文（每轮的请求，合计 1200 字，留开头和最近的）、每轮结论的第一段（最近 6 段）、工作区、所在专项、开了几天、你说了几次；已有专项的名字、目标、状态和它的话题的本质；你以前给的理由（`lessons`）。
- 判断用 `COVEY_PROJECT_TIDY_MODEL`（默认 Sonnet：要读整段对话说出本质，Haiku 不够），做法同 `app/track_judge.py`（没有工具、MCP、hook 和保存的会话，过了上限整组进程杀掉），一次调用。
- 拿不准时它可以先回 `{"read":[…]}` 要最多 3 个话题的全文（每轮请求和结论加长到 12000 字），再判断一次。
- 脱敏的话题不送给模型，在结果里单独写明。
- **补要点**：整理（定时、手动）先给没有要点的老话题补：一个话题单独一次只读调用（`GIST_SYSTEM`），整理卡上显示“正在读 T42（12/40）”。读不了的（被官方内容安全拒绝、超时、回答看不懂）只标 `unreadable` 跳过，整理照常做完，卡上写“N 个话题读不了，没参与这次整理”；它有了新的一轮之后的整理会再试。
- **取名**：取本质，对象 + 要达成的事，12 个字以内，不带编号和日期（`core/project_proposals.py` 的 `clean_name` 会去掉 T 号、日期、“第 N 轮”并截到 12 个字）；不取标题里第一件具体的事、不取所在的环节。例：“修第 64 题的审批流程”“优化生成流程的下一环节”两个话题本质都是优化同一套提示词，按标题归成“某环节提效”是错的。
- **判断的硬规则**（`project_sorter.parse`）：新建和拆开至少两个话题（`MIN_CREATE`），新建要有目标；提示词要求专项有终点，不按大主题塞筐，长期值守不建。

### 判断之后

- **归进已有专项**（`app/project_members.py` 的 `join_topic`，把握 ≥ 0.85 才直接归）：
  - 话题 `topic.json` 写上 `project`（角色 `thread`），进专项记录的 `threads`，所以看板和 Pin 把它并进专项那一格；负责人收件箱收到一条 `joined` 回执；收起的专项随之展开。
  - 话题卡、状态卡上多一行“已归进专项「X」 · 移出”；两张都没有的话题，在它的话题串里发一张只有这一行的小卡。
  - 之后管家对这个话题说话要经负责人（`project_send`）。
- **移出**（`leave_topic`）：话题变回普通话题，负责人收到 `left` 回执，话题标记 `never_auto`：以后整理不再自动把它归进任何专项（你点「好」的除外）。回复里带一个可选的输入框“为什么不对”。
- **建新专项**：发一张提议卡到私聊（`cards/project_proposal.py` 的 `proposal_card`）。
  - 归在一起的话题全列出来，每个一行 T 号（点了打开那个话题）、标题、做了几天几轮，下面一行“在做：话题要点的本质；现在：最新一轮结论的第一句”；只有一个话题时开头写“这个话题推了很久，像是一件要长期做的事”。
  - 发卡前先给还没要点的话题补要点，判断和卡片都按本质而不是标题；下面是“为什么提”、专项名和目标、建了以后有什么变化；你的第一张提议卡多一句专项是什么。
  - 卡底是一张表单：哪些话题（下拉多选，提议的话题已勾上，后面是最近的其他话题；不在里面的话题填 T 号）、专项名（已填好，可以直接改），按钮「建专项」「不管了」。勾掉、加上的话题照建，填的 T 号不是这个私聊最近的话题就不加，建好后的卡上写明。没改名就算直接建，改了名记 `name_by: owner`，整理以后不改这个名字。
  - 更早发出的卡还是「建专项」「改个名再建」「不用」「以后别提议」四个按钮，点了照旧。
  - 「建专项」走 `Projects.gather`（步骤 `GATHER_STEPS`：记录、负责人、专项卡、每个话题成为专项的话题、开工回执列出接手的话题），专项 id 由提议 id 定，重复点找到同一个。
  - 「不管了」（旧卡的「不用」）记下这组话题，之后同类提议要多出至少 2 个相关话题才会再提（`declined_like`）。「以后别提议」关掉提议（你说“开个专项”管家照样开）。
  - 连着 5 次直接点「建专项」（没改名），下一张提议卡问一句“以后这种直接建？”，点了以后新建也直接做（同 `auto`），专项卡上的「不要专项」就是撤回。
- **整理专项卡**（定时、手动，`tidy_card`）：先发出来写“正在整理”，补完要点、判断完原地换成结果。
  - “已经做了”：把握很高的归进、收起空闲专项（没有在跑和等回答的任务才收）。
  - 新建不在整理卡上定：每个新建发一张提议卡，整理卡的“新专项的提议”只列名字；判断出的新建和一张还在等你定的提议是同一组话题时，列在“还在等你定”下。整理完把只有一个话题、还开着的旧提议作废（`expire_alone`，卡上写“已过时”）。
  - 开着的提议（两个以上话题）也列在看板的专项区，「建专项」「不管了」在看板上点就定，改的是提议自己的卡，再把看板原地重画；管家的 `projects_list` 同样写出还在等你定的提议。
  - “要你定的”：最多 5 条合并、拆开、改名、移出，每条一块（`suggestion_block`）：标签和粗体的动作（“拆出新专项「X」”“把 T12 移出「X」”）、灰字来源、原因、目标、话题一行一个（超过 4 个先列 3 个，其余折成“还有 N 个话题”），底下是写着动作的按钮和「不用」；定了的换成一行灰字结果。卡顶的结论带写“要你定 · 整理专项 / N 条建议”。
  - 卡上和网页上点同一条，靠提议记录锁里的认领（`claim`：只有还开着才拿走）只办一次。
  - 读不了的话题在卡上逐个列出原因（`UNREADABLE_WORDS`），未编号的话题用你说的第一句话称呼。
  - 合并把后面几个专项的话题移进第一个，那几个专项取消（原因 `merged`，专项卡缩成“专项已并入另一个专项”）；拆开把选中的话题移出、另建一个专项；改名不碰你取的名字。
- **你写的理由**：在「不用」「移出」下写的理由记进 `projects/tidy/state.json` 的 `lessons`（最近 30 条），之后每次判断都带上，以它为准。

### 提议跟着归入走

话题已经归进专项后，提到它的提议卡不再挂在看板上。

- 整理专项的线程每一轮（`TICK` 秒，`follow`）看一遍开着的提议，不管话题是怎么进的专项。
- 新建提议去掉已归进专项的话题后，还剩两个以上的，卡原地换成剩下的话题，卡上写“T12、T15 已归进专项「X」，这张卡只剩下面 N 个话题”。
- 剩不到两个的作废（`expired`）：卡换成“专项提议 · 已过时”，写明哪些话题归进了哪个专项。还开着的归进提议，话题已在专项里的也作废。和一张更新的、还在等你定的提议是同一组话题（或其中一部分）的卡也作废（`unrepeat`，写“和提议「Y」是同一件事，留那一张”）。之前发出的卡再点，只把卡重画成已过时。
- 新提议先去掉已在专项里的话题，剩不到两个就不提。和一张还在等你定的提议大面重叠（共有的话题至少占较小那组的一半，`overlapping`）时不另发卡：多出的话题补进那张卡（卡上写“又发现 T… 也是这件事，补进来了”）。
- 看板的专项区、管家的 `projects_list` 和整理卡的“还在等你定”读同一张单子（`core/project_proposals.py` 的 `waiting`）。
- 关于某个专项的提议（拆开、合并、移出、改名、收起，`follow_project`）：提到的专项结束或被并走了就作废；拆开提议的话题有的已经不在源专项里，剩两个以上的只拆剩下的，剩不到两个的作废；移出提议的话题已不在那个专项的作废。这些提议列在整理卡的行上，行原地重画（`redraw_row`）。

### 跨专项

不会把 A、B 两个专项的话题加散话题拼成一个新专项。

- 判断的硬规则不让拼：新建只收不在专项里的话题，拆开只从一个专项里拿、不拿光，合并是整个专项合并；自动归进也只收不在专项里的话题。
- 点「好」拆开时再核一遍：只搬还在源专项里的话题（移出过的、别的提议先搬走的留在原处，结果里写明没带上），剩不到两个就不拆；源专项负责人收到的回执写话题拆去了哪个新专项（合并写“随合并转进专项「X」”）。
- 专项被拆开或移出拿走最后一个话题、又没有在跑和等回答的任务时马上收起（`fold_if_empty`），你再在里面说话会展开。
- 提议卡上勾选或填 T 号时，已在别的专项里的话题不收，结果写“T… 已在专项「X」里，没加”，全是这种就不建。

### 别处

- **巡检**：开着整理专项时，[我本来想找你的事](butler.md#我本来想找你的事开关默认关只记不打扰)不再自己按标题的词判断“几个话题像同一件事”和“话题可能属于某个专项”，改读整理专项还开着的建专项提议（`app/patrol_rules.py` 的 `tidied`）。
- **网页**：推送的话题多 `gist`，发件箱认 `tidy`、`tidy_decide`（见[网页工作台](web.md)）。
- **记录**：`<state>/projects/tidy/`：`state.json`（游标、定时、你的偏好 `prefs`、理由、排队的实时判断）、`proposals/<id>.json`（每条提议和你的决定，状态 `open → accepted → done|failed`，或 `declined`、`never`）、`topics/<话题>.json`（`never_auto`、归进过哪里、哪些时机已经触发过）、`runs/<run>.json`（每次整理的卡和结果）。持记录锁时不调模型、不发飞书。
- **开关关着**：没有后台线程，每轮消息里没有话题要点那段，管家没有 `projects_tidy`，设置卡没有这一行，网页不推 `gist`、发件箱的 `tidy` 回 failed，巡检照旧按词判断。

## 汇报风格的默认值

`COVEY_PROJECT_STYLE_KEEP=1` 时，负责人用 `project_style` 改风格时，整份风格（`report`、`detail`）也记进 `<state>/project-style.json`；之后转成专项、直接开的新专项的记录从这份风格开始（`Projects.seed_style`），负责人的规则和状态包里就是它。已有的专项不动，负责人随时还能改。
