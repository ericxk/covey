# 云文件系统上的本机运行锁

`COVEY_LOCK_ROOT` 把互斥锁文件显式移到本机的运行目录。所有记录、会话所有权、保存的回复、配置、日志和轮换后的日志都留在原来的持久路径。没有自动回退：不设这个变量时，Bridge 照旧对原文件用 `flock`，锁不受支持的错误也照旧抛出。

这个模式只支持**一台写入主机，上面可以有多个协作的进程**，不是分布式锁。所有碰同一份持久状态的进程都必须在这台主机上运行，看到同一个运行文件系统和同样的规范云路径，并使用完全相同的设置。各自挂载私有 `/dev/shm` 的不同容器之间不互斥；解析到不同路径的挂载别名之间也不互斥。

## 配置

在 Linux 写入主机上，用内存文件系统里只属于本用户的目录：

```bash
export COVEY_LOCK_ROOT="/dev/shm/lark-bridge-locks-$(id -u)"
```

- Bridge 以权限 `0700` 创建最后一级目录，它的上级目录必须已经存在。已有目录必须属于当前有效用户，权限正好是 `0700`。
- 运行文件必须是普通文件、只有一个硬链接、属于该用户、权限 `0600`。
- 运行目录路径或锁文件里有符号链接、上级目录可被他人写入、相对路径、空值，都拒绝。`/dev/shm` 这类带 sticky 位的共享上级目录允许。
- 设置无效时绝不回退到云上的锁。运维要自己选一个本机、`flock` 可用的内存文件系统；代码不会从目录名推断持久性或文件系统是否支持。

Manager、服务注册和管理命令、Bridge、任务进程、网页服务和后端进程都要设这个变量。Manager 的服务清单本来就会保留这个不含凭据的 `COVEY_*` 设置。

上述任一进程在运行时，不要改这个变量，也不要替换目录。在云上锁和运行锁之间切换前，先停下并排空所有写入方，包括旧 release 的任务进程：新旧两种锁模式混用时互不排斥。

锁文件名是原锁路径规范化后的 SHA-256 加 `.lock`。映射覆盖记录和卡片的旁路锁文件、会话状态、原生会话守卫、保存的结果、Manager 配置、日志轮换、飞书网页服务，以及扩展后端的会话租约（见公司扩展 README 的 扩展 Harness 诊断一节）。日志轮换只移走互斥锁，复制和截断仍作用在原日志的 inode 上。

持有锁的最后一个描述符关闭时，内核释放这把锁，进程退出或被 SIGKILL 也一样。锁文件保持为空并被复用，没有常驻的打开描述符登记表。在线维护从不删除运行锁（运行锁模式下也不删旧的旁路锁文件），因为等待者可能还拿着旧 inode。**不要运行在线清理锁文件的程序。** 空文件会一直累积到重启；只有所有写入方都停下后才能手工删除。重启后目录和锁会重建，不丢持久记录。
