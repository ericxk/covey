# 管家

管家是私聊里一个常驻的会话（设置卡的私聊模式选“管家”时），没选 Harness 时跑在 Claude Code 上，这台机器没启用 Claude Code 时依次跑在启用了的 Codex、Antigravity 上（再没有时用 DeepSeek Harness）；也可以在设置卡「配置」页的“管家”一段换。主人在私聊**顶层**发的消息都交给它：能直接答的自己答，要干活的开话题或转给已有话题，主人说“T12 选 A”时替主人答选择题。用户视角见[使用指南 · 管家](usage.md#管家)，部署开关见[配置](configuration.md)。

管家交给负责人跟进的长期的事见[专项](projects.md)，网页上的工作台见[网页工作台](web.md)。这篇讲管家是什么、由哪几块组成、一轮怎么走；放置表的每一格、工具通道的协议、各功能的记录和刷新方式等改代码时才查的细节在[管家的实现细节](butler-internals.md)，标题和这里一一对应。

## 组成

- **私聊模式开关**：`core/butler.py` 的 `enabled`（见「私聊模式」），设置在 `core/butler_settings.py`。
- **管家会话**：`app/butler.py` 把顶层消息交给管家话题，每轮带规则、快照和 MCP 配置（见「会话」）。
- **MCP 工具**：会话里的 stdio MCP 服务 `core/butler_mcp.py`（入口 `bin/covey_butler_mcp.py`），清单 `core/butler_tool_specs.py`。
- **请求通道**：`core/butler_requests.py`，一次调用一个请求文件，由 Bridge 进程里的 `app/butler_tools.py` 执行（见「工具通道」）。

各模块的职责见 [AGENTS.md 的代码地图](../AGENTS.md#代码地图)和[架构 · 代码位置](architecture.md#代码位置)。

## 私聊模式

`core/butler.py` 的 `enabled` 是唯一的判断，各处都问它。两层：

1. **部署允许**（`available`）：`COVEY_BUTLER=0` 时不允许：管家的后台线程不起，菜单键不认，设置卡「配置」页没有管家一段。其他值都允许。
2. **主人选的模式**（`agent_mode`）：`main-thread.json` 的 `mode`，`agent` 是管家，`topics` 是纯话题。主人在设置卡「配置」页“管家”一段里的“私聊顶层的消息”一行切换（选“每条直接开一个话题”要再点“确定改”），保存即生效；Bridge 和任务进程每次 stat 一下，变了才重读。保存时同时写 `enabled` 给旧版本。

**默认值只写一次**：Bridge 启动、处理事件之前（`Butler.settle` → `settle_mode`），文件里没有 `mode` 就写：状态目录里没有任务也没有话题时写管家；否则 `COVEY_BUTLER=1` 且设置没关的写管家，其余写纯话题。之后只看 `mode`。

**纯话题**下和没有管家时一样：顶层每条消息开一个话题；引用管家以前的卡当作新消息开话题（`core/topics.py` 的 `context_for_topic`），引用“交给一个话题”的管家卡照旧进那个话题；正在跑的管家那一轮跑完，按 `BUTLER_OFF` 收尾；会话和记录留着；管家开过的话题不再回带、不再放顶层问题卡副本。群聊两种模式都没有管家。

管家的 Harness 是设置里的 `harness`，只能选能接 Bridge 工具的（`core/harness.py` 的 `bridge_tools`：Claude Code、本机上的 Codex、Antigravity 和 DeepSeek Harness；扩展里的 Harness 看它自己声明没有；见[换 Harness](#换-harness)）。没选（空）时跟着启用了的走（`app/butler_harness.py`）：启用了 Claude Code 就用它，和以前一样；没启用时用启用了的、能接工具的第一个：先 Codex、再 Antigravity，然后才轮到 DeepSeek Harness（`FALLBACKS`）。设置卡和网页设置页上画的是它现在用的那个，不写进文件，以后装上 Claude Code 就回到 Claude Code。没选 Harness 时记下的模型和预算是 Claude Code 的（设置卡把 Claude Code 存成空），换到别的 Harness 上时用它自己的默认模型（`model_of`）；在设置卡上给 Codex 或 Antigravity 选模型时，Harness 一起记下。选了的 Harness 没启用或接不了工具时不替换：私聊消息照旧开话题，Bridge 启动日志写一行 `main thread is on but its Harness <名字> is not enabled or cannot take the Bridge tools`；没选、也没有一个启用了的能接工具时写 `main thread is on but no enabled Harness can take the Bridge tools (Claude Code, Codex, Antigravity or DeepSeek Harness)`。新部署私聊里的[欢迎卡](usage.md#第一次使用)（`app/welcome.py` 的 `butler_state`）也当面说：没有管家时写为什么（管家用的 Harness 没启用或接不了工具；`COVEY_BUTLER=0`；私聊模式是纯话题；或它刚才没起来）和怎么补（装好并登录 Claude Code、Codex 或 Antigravity 中的一个再运行一次 `./install`，选过别的 Harness 的在设置卡「配置」页的“管家”一段换成启用了的；纯话题时在同一页改回交给管家），并说明每条消息会开一个话题、先出启动卡；有管家时说明你的话下面出现表情就是收到了，有东西要给你看时才发卡（一轮跑过 90 秒才发任务卡，见[提问不开串](#提问不开串)）。

## 和话题的不同

不同都在 `core/butler.py` 的 `Traits` 表里。调用处只查表，不比较 topic id，也不比较 `Traits.name`（`tests/test_butler_contract.py` 的 `NoNameComparisonTest` 检查）。

- **判断**：`is_butler_topic(topic_id, chat_id)`，和开关无关。
- **查表**：`traits(topic_id, chat_id)`；任务、记录、topic.json 用 `traits_of`；只有上下文时用 `core/topics.py` 的 `topic_traits`。
- **行**：`TOPIC`、`BUTLER`（开关开着）、`BUTLER_OFF`（开关已关：结构上的不同照旧，会话上的取消）。

`BUTLER` 一行概括起来：管家不占 T 号，没有换配置和回退，卡片点击不能指向它，不进看板和手上的事，不回带；每轮带规则、快照和工具，按阈值压缩；回答可以写在任务卡上，任务卡是分档卡。每个字段的取值和读者见[实现细节 · Traits 表](butler-internals.md#traits-表)。

## 一轮怎么走

### 路由

`app/card_routing.py` 在启用的扩展的 `handle_event` 之后调 `Butler.handle_event`，主人身份来自 `Runtime.access`（规则 11）。消息的 `root_id`、`thread_id`、`parent_id` 按别名查话题：查到别的话题交给它；查到管家留在管家；都没填是管家的新一轮；填了但谁也不认识就照旧开话题。

管家话题的 `topic.json` 带 `main_thread: true`（字段名沿用旧名，不改），没有根消息和 `topic_number`。每条消息都同步设置：模型和预算下一轮生效；换工作区要等没有任务在跑，并开新会话。

- **补充**：有任务没结束时，新消息用 `deliver_steer` 并进最新一轮，不发回执卡；可能已送达的不重发（规则 6）。
- **收尾时发来的消息**：确定这一轮没读到的补充，自动排成管家的新一轮；不确定的说一句。
- **等主人的话**：没有自己文字的消息（卡片、合并转发、图片、文件、只有链接）等 30 秒（`HOLD_SECONDS`），这期间主人的文字并进请求并立即开工。

三种情况的做法见[实现细节 · 路由的细节](butler-internals.md#路由的细节)。

**挂住的请求不再堵住后面的话**（`app/unstick.py`）：管家的一轮在等模型回应时没有任何动静，而你后来的话还在等它（补充没被读到，或开了[同时做几件事](#同时做几件事)时排在这一路后面）：满 3 分钟，在每条等着的消息下说一句它在等哪一轮、已经多久没动静；满 10 分钟（`COVEY_BUTLER_HUNG_MINUTES`，`0` 关）停下这一轮，记成失败（“模型请求长时间没有回应，Bridge 停下了这一轮”，可检查并继续），你后来的话各自作为新一轮接着跑。在等命令、等你回答、请求在重试或排队等空位的不算没动静；普通话题不自动停，卡上有停止和看看。负责人的轮一样。

### 直答与转交

规则在 `app/prompts.py` 的 `butler_rules`（`AREA_OPENING`、`AREA_RULE`），放在每轮用户消息开头：

- 只读、一两分钟能做完的，管家自己做、直接答；只问已有结果的用 `topic_read` 读了自己答。
- 改代码或文件、要跑几分钟以上、几件事并行、主人说开话题的，交给话题：新的事 `topic_start`，同一件事 `topic_send`；两个以上话题都对得上时用 AskUserQuestion 让主人选。
- 交出去后只说一句放到了哪，不报进度和结论（结论由 Bridge 回带，进度看 Pin）。
- 写给主人的话当他没看过别处：提到话题写它在做的事、T 号放括号里，话题里的数字和结论直接写进回复。
- 怎么做由管家定（先查什么、交给哪个话题、失败了换办法）；做什么、不可逆的、对外可见的、花钱的由主人定，问的时候先说倾向。
- 一轮结束后管家不会自己醒来：没有在跑的话题会把结果带回来时不说“稍后”“等下”，没答完的派进话题。
- **提醒一次**：管家这一轮自己调满 6 次 Bridge 以外的工具时，Claude Code 的 `PostToolUse` hook 提醒它一次把剩下的交给话题、说一句放到了哪里就结束（`app/prompts.py` 的 `TOOL_NUDGE_TEXT`，`backends/claude/hooks.py`）；主人这句话说了“你直接做”“别开话题”“就在这儿做”的不提醒。管家派出的子 Agent 调不了 Bridge 工具（[Harness 说明 · Claude Code](harnesses.md#claude-code)）。
- “写给人看的话（含工具说明）用主人的语言”只在每轮的桥接规则或续接提醒里说一次（`app/prompts.py` 的 `LANGUAGE_RULE`），管家规则不再重复。
- 主人问 Covey 本身怎么用（看板在哪、怎么开记忆），先读运行中这份代码自己的 `docs/quickstart.md`（[五分钟上手](quickstart.md)，规则里写的是它的绝对路径，`USAGE_RULE`）再答。

**直接开工**：管家开的话题一律直接开工（运行方式是独立 worktree 的除外，它出预填好的启动卡，由卡建 worktree）。以前的“开工三档”（设置 `start`）和“记住的工作区”（`trusted`）已下线（[legacy.md](legacy.md)）：main-thread.json 里的旧字段读时忽略、不再写回，设置卡和网页不再有这两项。

判为只读（`readonly`）又直接开工的，第一轮的任务说明末尾写“这一轮只读”（`app/tool_limits.py` 的 `LOOK_NOTE`；请求记录的计划里记 `read_only`，任务记录也记），并且照 Harness 能做到的限住（`TOOL_LIMIT` 的 `look`）：Claude Code 没有改文件的工具（Edit、Write、NotebookEdit，子 Agent 也没有；命令行还在，给只读的命令用），Codex 在只读沙箱里跑（命令能跑，写不了文件、上不了网），别的 Harness 只有那句话。只管这一轮：主人之后在话题里说的话、点重试或检查并继续，照常跑；等启动卡、主人点了开始的也照常。

### 管家规则

`COVEY_BUTLER_RULES` 开着（默认）时，[直答与转交](#直答与转交)的前两条换成 `app/prompts.py` 的 `BUTLER_RULES`（两条），让管家只快答和分派，这样它接得住主人的连问；`topic_start` 的工具说明里同样的话也换了；其余规则不动；设成 `0` 就回到只读的自己做完、超过一两分钟交给话题的老说法。

- **快答**：不用工具，或只用一两次只读的查询（看一眼文件或日志、查一项配置、`topic_read`、`topics_list`），几秒内能答完，直接答、不开话题。
- **派出去**：要查一圈、要跑命令、要改代码或文件、要联网或多步操作、预计超过半分钟的；拿不准也派。新的事 `topic_start`，和已有话题是同一件事 `topic_send`。
- **派出去后说什么**：一句话，放到哪个 T 号，如“放到 T42「标题」里做”；快照里有预计才报时间，不写进度和结论（`AREA_RULE`）。
- **例外**：主人明确说“你直接做”“别开话题”“就在这儿做”时，这一轮自己做完再答。
- **兜底**：自己干了 90 秒的一轮照旧出卡（`CARD_AFTER`），不另设变量。
- **打开和关掉**：见[配置 · 管家规则](configuration.md#管家规则)。关着时规则和提示词和原来逐字节相同。

规则每轮重新拼，重新注册后管家的下一轮就用新规则；续接会话里新旧规则怎么共存见[实现细节 · 管家规则什么时候生效](butler-internals.md#管家规则什么时候生效)。

### 同时做几件事

默认开，`COVEY_BUTLER_TRACKS=0` 关（[配置](configuration.md#环境变量与选项一览)）。管家这一轮在做事时，主人的下一句不被挡在后面：管家变成一个**话题家族**，现在的管家话题之外再有固定 4 路，每路是管家会话的一个分叉，各自跑一轮普通的管家任务。`COVEY_BUTLER_TRACKS_MAX` 是同时在跑的件数上限（默认 3，取值 2 到 4），到了上限的新事排在最空的那一路后面。

- 新的一句先按规则分流（引用了哪件事就给哪件），判不出时问小模型：并进某件在做的事、另起一件，或停止。
- 说“停”“别做了”停掉对应的那件，不建任务、不进模型。
- 管家的下一轮开头带上别的几路这段时间答了什么，所以管家记得住。
- 开了又关：几路的话题留在盘上，这时它们是普通话题，回答、引用老卡照样能接着用。

分流、表情、停止和账本的细节见[实现细节 · 同时做几件事的细节](butler-internals.md#同时做几件事的细节)，底座和运行时见[架构 · 管家同时做几件事](architecture.md#管家同时做几件事)。

### 提问不开串

话题挂在提问下面时，管家这一轮默认不发卡（`(AREA, BUTLER)` 格子的 `Row.quiet`）：

- 主人那条消息加表情 OnIt；跑过 `CARD_AFTER`（90 秒）还没结束才发任务卡，进主人那句话的话题串，卡的第一行是管家的头像行。结束时表情换成 DONE（自己答的）、Get（交给话题）或 CrossMark（失败、被拒）。
- 专项负责人的轮一律不发任务卡（`task_card` 格是 NONE）：你引用专项卡说的、管家转给它的、网页上对它说的、它自己醒来的都一样，跑多久都不发，负责人在做什么看专项卡；答复、汇报和没做完的通知照样是聊天区新消息。
- 答案、结论、问题卡副本和通知都是聊天区新消息，第一行是头像行，写谁对你哪句话做了什么（说话人：管家“**管家** 回你 12:31「原话…」”，话题“**T12 标题**”加状态标签和“做完了你 09:12 交代的事”，负责人“**专项名 · 负责人**”，各有自己的头像，不用彩色标题栏）。
- 引用这些消息说话，交给发出它的话题、负责人或管家；引用手上的事、早晚汇总卡或发在私聊顶层的告警（节点告警、内存看门狗）也交给管家（`Butler.app_for`；告警发出时记进 `top-notices.json`，`app/pins.py` 的 `remember_notice`），不在它上面另开话题、等你点开始。
- 只做了交接的一轮不发答案，Get 就是回执；转给已有话题的，再在主人那条消息下回一张“→ T12「标题」 ›”的小卡（这次转交发了[派发卡](#派发卡)的话题不回）。
- 要主人定的事写进检查点的问题，进“等你”，不只在回复末尾问一句。

表情、说话人的句式、没卡时的失败通知、重试和续接见[实现细节 · 提问不开串的细节](butler-internals.md#提问不开串的细节)。

### 一次请求一张卡

`app/butler_reply.py`。回答先照旧经 `verified_reply` 保存、授权（规则 5）。

- **开了或转了话题**（`main-thread/opened/` 里这一轮成功的记录，`core/butler_opened.py` 的 `kind_of`）：写在任务卡上，每个话题一行（“↪ 开了 **T14**「标题」”“↪ 转给 **T13**「标题」：note”），模型的话折进“详情”。
- **自己答的**：按放置表 `answer` 作为聊天区新消息发（`app/answer_delivery.py`）。
- **退回单独发**：没完成、要以文件发、超过卡片字数或写卡失败时，单独发回答卡（重投只发保存的正文）。
- **没人跟进的推迟**（#25）：做完的一轮，回答里有推迟的话（“稍后”“等下”“我去查”，`core/turn_words.py` 的 `defers`，提了 T 号的不算）、这一轮又没有成功开、分叉或转交任何话题时，显示的答案下面加一行 `UNFOLLOWED`（`unfollowed`）；只改显示，保存的回复和重投不变。

状态行的写法、停止和被拒、分档卡见[实现细节 · 一次请求一张卡的细节](butler-internals.md#一次请求一张卡的细节)。

## 会话

`app/butler.py`，只在开关开着、任务属于管家话题时起作用。

- **回复位置和说法**：对管家消息的回复进那条消息的话题串，开话题就用这个串；Bridge 自己写的“本话题”换成“私聊里”。
- **快照**：紧接规则，`snapshot_groups` 从 `core/board_read.py` 读（不调飞书，不持记录锁）。四组：等你（和汇总、看板、手上的事同一批）、有结果没看（看板的口径，见[看板与 Pin](#看板与-pin)）、在做、管家开的话题（快照和 `topics_list` 的说明里分组名还是旧写法，见[名词表 · 状态词](glossary.md#状态词)）；开了专项还有一栏“专项”。下一轮只列变了的行。
- **MCP 配置**：`butler_turn` 把 `mcp_config(...)` 放进 `ctx.options`，Claude 后端据此加 `--mcp-config`，不改 `runs/` 协议。
- **压缩**：一轮送达后上下文到了 `compact_tokens`（默认 20 万，0 不压），`compact_butler` 写压缩请求；空闲时由 `app/idle_compaction.py` 在后台压，主人不用等。
- **已下线的前台话题**：旧设置读到也按关；以前开的由 `core/migrate.py` 的 `desk-retire` 冻结。

每一项的做法（快照怎么存、MCP 参数、空闲压缩的标记和失败处理、前台话题的旧卡）见[实现细节 · 会话的细节](butler-internals.md#会话的细节)。

## 卡放在哪

### 放置表

`core/placement.py`：布局 × 角色 → 格子 `Row`。调用处只读格子；只有这一轮知道的事（开没开话题、多快、是不是主人自己停的）留在调用处。

- **布局**：管家开着是 `area`（话题挂在提问下面），否则 `topics`。
- **角色**：`butler`、`topic`；开了专项再有 `lead`（负责人）和 `project_member`（专项的话题）。
- `area` × `butler`：答案是聊天区新消息，开了或转了话题时写在任务卡上，这一轮不开串。
- `area` × `topic`：答案进话题串，结论和问题卡副本回到聊天区。
- `area` × `lead`（专项负责人）：和管家一样不开串，答案是聊天区新消息；任务卡哪一轮都不发（`task_card` 是 NONE）。
- `topics` 布局：都在话题串里，看板 Pin 话题的状态卡。

完整的格子表、每个字段的读者和负责人的唤醒轮见[实现细节 · 放置表](butler-internals.md#放置表)。

### 消息落在哪

- **管家的卡**在主人那句话的话题串里，跑过 90 秒才发，第一行是管家的头像行。专项负责人不发任务卡。
- **答案、结论、问题卡副本**都是聊天区新消息，不引用任何卡：主人那句话下面已有话题串，回复它会掉进串里。
- **“你问”块**（`cards/answer_card.py` 的 `ask_block`）：灰底两行“你问 · 时间 ›”和原话，整块可点，跳到这一轮在话题串或聊天区的位置；表单回答开的一轮是“你答”块。有说话人时，答案、回带和问题副本把它拆进头像行（话题、时间、原话前 18 字），整块可点的入口就是头像行本身：点头像行，话题的回带和问题副本进话题串里这一轮的卡，管家和负责人的回答回到你那句原话；卡尾不再放“看你那句 ›”“进话题 ›”。话题和负责人的头像行不引原话，下面一行灰字收着它（回答问题的一轮是问题和你的回答），点开看全文；转交给话题的一轮，这一行是管家引的你的原话，不是转交说明。没有说话人（管家关着）时仍是这个块。派发卡不用头像行，仍是这个块。链接的退路见[实现细节 · “你问”与“你答”块](butler-internals.md#你问与你答块)。

## 工具通道

```
管家会话 ── MCP（stdio）── bin/covey_butler_mcp.py
                                │ 写 <state>/main-thread/requests/<id>.json，等 <id>.answer.json
Bridge 进程 ── app/butler_tools.py：pending → claim → 核对 job_key → 处理函数 → answer
```

- MCP 服务（`core/butler_mcp.py`）只用标准库，等回答最多 120 秒。
- Bridge 里的后台线程 `main-tools` 一次执行一个请求；启动时认领了没回答的回 `UNCERTAIN`，不重跑（规则 1、6）。只接受管家正在跑的任务发来的调用。
- 处理函数是 `handler(env, request) -> dict`，各模块用 `TOOLS` 字典登记，`app/unified.py` 合起来。

请求和回答的格式、执行循环的规则见[实现细节 · 工具通道的细节](butler-internals.md#工具通道的细节)。

### 点名配置的依据

管家和专项负责人开话题（`topic_start`、`project_topic_start`）时填了 `harness`、`model` 或 `effort`，或者用 `topics_switch` 批量换配置，都要写 `basis`：主人这一轮原话里连续的一段，或记下的原则编号（`p1a2b3c`）、这一轮带的记忆编号（`M12`），也可以是原则或专项记忆里的一段原文。Bridge 在执行前核对（`app/config_basis.py` 的 `check`，比较时不计空格、标点和大小写，短于 3 个字的不算），对不上就拒绝这次调用、说明原因，模型改为不填（用设置里的默认）或问主人。开出来的话题卡在配置那一行末尾写“按「…」”，主人一眼能看出这个配置是照哪句话选的；没填这几项的话题卡和以前一样。

为什么要这样：主人说“监视进程这类给 Codex”，之后修代码、验收这类话题也被开到 Codex 上。原则只管它说的那一类事，工具说明、管家规则和记忆纠正规则里都写了这一条；Bridge 自己开话题（独立复核、网页开新话题）用的是设置卡里的配置，不经过这道核对。

### 按线索找话题

`topics_search`（`app/butler_search.py`）一次 1 到 `MAX_CLUES`（5）条线索（飞书链接、token、路径或关键词），搜主人私聊每个话题每一轮的主人原话、结果、状态行和检查点，按匹配程度排序、按话题分组列出。不读会话原文、不搜群聊、不加锁。匹配和排序的规则见[实现细节 · 按线索找话题的细节](butler-internals.md#按线索找话题的细节)。

## 开话题、转交、分叉

`app/butler_topics.py`，只在主人私聊里动作，飞书调用都在锁外（规则 1、2）。

- **`topic_start`**：工作区只认已登记的名字；Harness、模型、预算逐项取值（`app/butler_model_choice.py`：调用给的 > `topic_defaults` > 这个私聊上次开始任务的配置 > Bridge 默认）。开出来的话题总写明是哪个模型、哪档预算：哪一项都没写明模型时（Antigravity 的 Bridge 默认是空，让 agy 自己挑；Claude Code 目录里的 Default (recommended)），用这个 Harness 在菜单上的第一个具体模型；哪一项都没写明预算、或写的是模型原生默认时，用设置卡换模型时会存的那档（推荐档，没有就不带编排的最高档，`core/menu_choice.py` 的 `plain_budget`），没有档位的模型写“模型自动管理”。第一轮直接提交；运行方式是独立 worktree 时话题里出预填好的启动卡。
- **设备上的工作区**（开了[多设备](configuration.md#多设备开发中默认关)，工作区是 `别名:路径`）：开话题前照启动卡的规矩查一遍（`device_binding`）：设备在 `devices.json` 里、这个聊天在它的 `spaces` 里、声明了这个 Harness、设备答复目录在（最多 5 秒）；哪一条不过都不开话题，回复写明原因和怎么改（比如 `harness` 填设备声明的哪个）。开出来的话题 topic.json 存 `别名:路径`、话题卡配置行多“设备 <标题>”、只用原目录运行（设置里是独立 worktree 时出预选原目录的启动卡，等主人点）、不脱敏（新话题默认脱敏时先问主人）。`workspaces_list` 在设备工作区后面写设备标题和能用的 Harness。专项开在设备工作区时负责人留在 Bridge 本机（它的工具在本机），状态包写明专项的话题开在哪个设备工作区。多设备没开时，写成 `别名:路径` 的工作区也不开话题（回复说多设备没开），不会当成本机路径开一个跑不起来的话题。
- **`topic_send`**：话题有没结束的任务时作为补充交给它，已经停了就作为下一条消息。话题在等主人回答问题时，管家或负责人加的话只作为补充暂存，主人回答时一起带上，不当成回答；要替主人答，管家用 `question_answer`（主人说了答案时），负责人用 `project_answer` / `project_escalate`。话题串里出一张“管家转来你 HH:MM 的消息”的灰底卡。
- **完成标准**（`criteria`，`core/criteria.py`，#22）：`topic_start` 可带 1 到 4 条，存进话题的 topic.json；主人要改时管家用 `topic_send` 的 `criteria` 换掉（空数组去掉）。问答、查询、调研不带。有标准的话题每一轮的消息在检查点文件后面多一段“完成标准”（`criteria.note`），模型在检查点 `criteria` 里逐条写满足 / 没满足 / 没查；答案卡和回带卡只列没标满足的（没写的算没查）。专项负责人的 `project_topic_start` 也能带。
- **`topic_fork`**：从源话题最近一次结束的任务分叉（`app/forks.py` 的 `create_fork`），复制原生会话。
- **话题卡**（`cards/topic_card.py`）：“T12 · 标题”加一行灰字配置，没有按钮。
- **幂等**：每次调用在 `<state>/main-thread/opened/<请求>.json` 记做到哪一步（`core/butler_opened.py`），同一个请求再来返回存下的回答。

取值的退路、`origin` 字段、补充被拒的处理见[实现细节 · 开话题、转交、分叉的细节](butler-internals.md#开话题转交分叉的细节)。

### 交给话题的消息

`app/butler_handoff.py`。交给话题的每一轮（开、下一轮、补充、分叉），模型收到 `handoff_prompt`，卡、历史和串里显示主人原话（`shown`、`thread_line`）。

- **Bridge 的说明**（`note`，开头 `[Bridge 说明]`）：你在哪个话题；这件事是管家按主人哪条消息交来的；路由已经办完，直接做事；你的回复就是结论。
- **任务说明**：管家写的 `prompt`/`text`，后跟“管家补充：note”。不用写“别发问题卡”：话题每一轮的执行约定里有[什么时候问](architecture.md#什么时候问)，`topic_start` 的 `prompt` 说明也这样告诉管家；负责人交来的，说明里只点部署、删除、花钱、对外发送、占机器照常问。
- **主人原话**（`asked`）：管家这一轮记录的 `user_text` 加运行中收到的补充，按时间引用。
- **附件**（`carry`）：只认管家话题 `incoming_media/` 或 `<state>/incoming_media/` 下的文件（`core/attachments.py` 的 `parse_attachment_block`），按参数 `attachments`（`all`、`none`、序号）挑出，硬链接或复制到目标话题的 `incoming_media/`。补充只送文字。
- **负责人交来的**（`project_topic_start`、`project_topic_send`，`app/butler_topics.py` 的 `handed`）：Bridge 的说明、负责人写的任务说明，和负责人点名转的附件。不论负责人这一轮回的是不是你的消息，你对负责人说的原话、补充都不跟着转（负责人一轮常给几个话题派不同的活，或顺手提醒别的话题）；附件只转负责人在 `attachments` 里点名的（序号如 `["图片 1"]`，或 `["all"]`），不点名不转，这一轮有附件却没点名时，工具的回复会提醒负责人还没转、怎么补。卡、历史、串里那一行（“负责人转来消息/补充：”加任务说明和“附件：图片 N 张”，文字，不链回你的消息）显示的都是负责人的任务说明，网页标“负责人说”。负责人开的话题也不挂在你那条消息下面（`place`），那条消息仍归负责人。你在场时负责人派出去的活，结论照旧回到你那条消息下（[主人在等的结果](projects.md#主人在等的结果)）。

## 话题

管家派出去的每件事是一个话题：话题串挂在提出它的那条提问下面；同一件事用 `topic_send` 追加。

- **开**：管家开着、查得到提问、提问的别名还指向管家时（`core/topics.py` 的 `claim_area_root`），以这条提问为根：先把别名改给新话题（`move_topic_message`），再建上下文，不发话题卡。`opened/` 记 `area_root`、`area_taken`。
- **一条提问只挂一个串**：同一条提问的第二个话题、查不到提问时，提问的串里已挂着同一轮转交的[派发卡](#派发卡)时，根是顶层新发的话题卡；分叉挂不上时把源话题合并转发到私聊当根。第二个话题的“你问”仍写那条提问，链接打开它自己的串。
- **引用直达**：引用专项负责人的回答，交给负责人（`app/butler.py` 的 `app_for`；负责人算管家一家，`core/butler.py` 的 `is_lead`）。管家这一轮的卡只交给了一个话题时，卡的别名记上 `routes_to`。回带的结论、问题卡副本也记成话题的消息并带 `routes_to`。引用它们就是对那个话题说话（`context_for_topic` 先看 `routes_to`），不经管家。纯话题模式下串里不看 `routes_to`。这样说的话下面没有卡，表情跟着那个话题的这一轮走（[架构 · 引用卡片接着说的表情](architecture.md#引用卡片接着说的表情)）。

## 结论回到顶层

管家开的或转过去的那一轮结束时，Bridge 在聊天区发一条新消息，第一行头像行写谁在说（话题的 T 号头像、标题和状态，后面灰字写它对你哪句话做了什么），整行可点、进话题串里这一轮的卡；下面一行灰字收着你那句话（回答问题的一轮是问题和你的回答），点开看全文。再下面直接是回答全文，没有结论带、不折叠。只在管家开着时；不调模型。回带的是管家开的、转过去的轮次和它们的自动重试，以及话题里回答问题后接着跑的、主人在串里开的一轮；网页上开的话题和管家直接开工的一样在聊天区有话题卡，它的每一轮也这样回带，问题也有顶层副本（`app/relay_targets.py` 的 `web_root`）；管家没碰过的其他话题不回带。专项的话题只回带负责人在你在场的一轮里交出去的那一轮，和你在聊天区引用它的卡追问的那一轮（[主人在等的结果](projects.md#主人在等的结果)）。

| 完成，回答已送达 | 结论卡（`cards/relay_card.py`）：头像行是 T 号头像、标题和状态（整行进话题），下面一行收着你那句话，再是回答全文（开头只写“结论”的小标题不显示），后面跟这一轮较长的进展说明；要你看的提醒露在外面、不折（提交号对不上、没满足的完成标准），产物、改动、验收说明收进一个折叠（标题列出里面有什么），再是两行小字“输入”“输出”（内容和答案卡一样，末尾不接链接），改了代码的一轮再加一行“改动 提交号 ｜ 第 N 代 ｜ 已自检”，下面一行小按钮：开着独立复核时是「独立复核」，再是「换配置」（点了换配置卡就开在聊天区，在下面，确认后回复那张卡就按新配置接着做）；最后一行灰字“回复这张卡，就是接着跟 T12 说” |
| 等你回答 | 问题卡顶层副本，上方的输出同样跟着较长的进展说明；放不了时发带“要你定：”的回带卡 |
| 失败或停止，没排上自动重试 | 停住卡：头像行下面粗体一行原因、灰字一行下一步，没有结论带（`core/failure.py`，和任务卡、恢复卡、网页同一句话，不写记录的状态行），下面是任务卡的“检查并继续”（限流叫“现在重试”）和“看原因”（超时等是“拆小再试”），限流、额度用完、安全拒绝这类还有“换个模型”：换配置卡直接开在聊天区（预选一个现在能用的别的 Harness，没有就是原来的，你点“确认更换”才换），换好后这张卡改成一行“↪ 已换配置：…；回复这张卡说一句，就按新配置接着做”；点了别的按钮这张卡原地改成一行“↪ 已接着做 · 任务 #12”或没做的原因，再点、话题后来有了新的一轮、换过配置都不会再开一轮（`app/relay_stops.py`）。主人自己点的停止不发 |
| 没送达、排上了自动重试 | 不回带 |

- **较长的进展说明跟着回带**：一轮里写完一段话再调工具，这段话进了任务卡的「执行过程」（进展说明）。长任务边等边写的阶段汇报（“基线组已经补跑起来了……”“初步结果：……”）就是这样，只看最后的回答会漏掉。不少于 300 字的进展说明（`core/trace.py` 的 `stage_notes`、`STAGE_NOTE_CHARS`）按写的顺序、各带时间，放在回答后面一个默认收起的折叠里，标题是“这一轮中途的汇报 · 约 N 字”，点标题展开、再点标题收起；回带卡上展开后点正文任意处也能收起，不用回到顶上找标题（`cards/review.py` 的 `stages_fold`，`app/fold_close.py`：Bridge 记下发出的卡，点击后把卡改写成收起的样子，换一个新的折叠 ID，要一两秒；记录 7 天没动就清掉，之后只能点标题收起）。问题副本上只能点标题收起。回答长到分几张卡发时，汇报不跟着正文切：放得进一张卡就折叠在最后一张、产物前面（最后一张放不下就折叠在后面那张产物与详情小卡的最上面）；一张卡放不下就在正文那几张后面另发几张，每张一个默认收起的折叠，和正文一起编号，产物在最后一张下面（`cards/relay_card.py` 的 `stages_of`、`stage_drawer`，`cards/pages.py` 的 `paged_after`）。问题副本前的长输出同样处理，只能点标题收起。短的过程话不带。负责人转给你的、一轮结束时提的问题，副本也带（`app/triage.py` 的 `show`，从任务的过程记录读）。一轮中途提的实时问题，副本本来就带这一轮到提问为止的全部进展说明。
- **只发一次**（`app/relay_send.py` 的 `send_once`）：锁内写意图、锁外发，没确认记 `uncertain`，从不重发（规则 1）。
- 回带消息是话题的消息，看过它就算看过话题。
- **连着做完的合成一条**（`send_merged`，`COVEY_RELAY_MERGE_SECONDS`，默认 20 秒，0 关）：“完成”的回带发出时聊天里还有别的话题的任务在跑或排队、或者已有回带在等，就先记 `pending`（`main-thread/relays/waiting.json` 按聊天列着）等这么多秒，再把这期间等着的一起发：只有自己的照常是结论卡，两条以上发一张「N 个话题做完了」卡（`cards/relay_card.py` 的 `merged_card`：有头像行，每个话题一块，T 号、标题、回答第一句和“产物 N 个”，整块点开那个话题；最后一行灰字“回复这张卡是跟管家说；要接着跟某个话题说，点那一行进话题”）。哪条记录都只从 `pending` 被取走一次（锁内改成 `submitting`），仍然只发一次；合成的那条算顶层的消息，引用它交给管家。没有别的任务在做时照旧马上发。“等你”和“停住了”从不等、不合并；带提醒的“完成”（提交号对不上、完成标准没满足，`cards/answer_card.py` 的 `alerts`）也不等，照常一张结论卡，提醒不会被合并卡吞掉，回复它也照常交给那个话题。
- **任务进程没回带的，Bridge 补一次**（`app/butler_relay.py` 的 `settle_missing`，同样走 `send_once`，和任务进程自己的回带撞上也只发一次，从不合并）：任务进程半路没了、轮次标成中断且没有自动续跑、没有排上的检查并继续、没有还开着的问题卡、也没有等外发箱重投的结果（`app/task_controls.py` 的 `left_stopped`），任务进程结束时或 Bridge 启动时补一张“停住了”；首发失败的结果后来重投送到话题，补“完成”（正文就是重投的那份）或“等你”（问题已有顶层副本的不补）；外发箱放弃重投（转 `paused`，且确定没发出去）补“停住了 · 结果没送到话题”。没送到话题之前不提前回“停住了”：一个任务只有一条回带记录，先回了会挡住之后的“完成”。任务进程等合并时退出、留下的 `pending`，由 Bridge 在它退出后接手发出（`app/relay_send.py` 的 `take_left`，单独一条发成一行的「做完了」卡）。

记录文件、产物更新和维护见[实现细节 · 结论回到顶层的细节](butler-internals.md#结论回到顶层的细节)。

### 问题卡在顶层也放一份

话题的问题在顶层也放一份同样的表单（`app/question_display.py` 的 `mirror`），聊天区新消息、头像行写谁在问，题目和选项在最上，这一轮的输出放在最前面（整段），再是题目和表单；头像行整行可点、进话题，下面一行收着你那句话。答完以后题目也只露一截，点开是其余的题目和你的回答，下面一行写你选了什么、接着的任务在做还是做完；话题串里的那张也是这个样子。专项的话题：负责人派的那一轮头像行写“办负责人派的事，要你定”、不引你的话，你自己在那个话题里发的话或答的题开的那一轮照普通话题引你那句；两种都能点进话题。在哪张上答都一样，答了两张一起收起。只有一道有选项的单选题时，两张卡上都是每个选项一个按钮，点了就提交。

专项的话题也放：头像行写话题号和“办负责人派的事，要你定”，没有你的原话。交给负责人分流的问题这一轮结束时不放（还不归你）；负责人转给你时补放这一份（见[专项的问题分流](projects.md#专项的问题分流)）。副本的记录和收起见[实现细节 · 顶层问题卡副本的记录](butler-internals.md#顶层问题卡副本的记录)。

## 看板与 Pin

管家自己不进看板，它开的话题照常进。看板、手上的事、早晚汇总、管家的快照和 `topics_list` 都从 `core/board_read.py` 的 `read` 读，“等你”和“有结果未看”五处一个口径（以看板为准，经 `app/pins.py` 的 `board_results`）：话题最新一个跑过的任务完成、失败、中断或停止且主人在它结束后没读过，就是有结果未看，不论多久。使用者看到的样子和各组的规则见[使用指南 · 看板](usage.md#看板)和[手上的事](usage.md#手上的事)，开关见[配置 · 手上的事与话题看板](configuration.md#手上的事与话题看板)。

### 个人空间的管家与看板

`spaces.personal_groups` 里的群（和 `owner_accounts` 的私聊）各有自己的管家：话题 id 按 chat 算（`butler_topic_id(chat)`），记录不混；`Access.agent_chat` 判断哪个 chat 有管家，`ButlerEnv.chat()` 在工具调用里取这个管家的 chat。个人群没有已读回执，主人在群里发的消息算读过它的看板（`app/group_boards.py` 的 `owner_active`）。个人群各有一份手上的事、看板和早晚汇总，记录名带 chat_id（`pinned-topics.<chat_id>.json`、`pinned-overview.<chat_id>.json`、`digest.<chat_id>.json`）。设置见[配置的空间一节](configuration.md#空间spaces)。

## 主人的原则

Bridge 记一份主人的长期原则，所有 Harness 的话题和管家都带上。

- **存储**：`core/principles.py`，`<state>/principles.json`，分通用和各工作区两组；一条最多 200 字，每组最多 30 条。
- **工具**：管家用 `principle_save`、`principle_delete`、`principles_list` 记、删、列。
- **注入**（`app/runs.py` 的 `Runs.principles`，块由 `app/prompts.py` 的 `principles_block` 写）：工作区那组总带；通用那组只在主人自己的一轮带（`Runs.owner_turn`：管家总是，其余经 `Access.owner_turn`，规则 11）。新原则下一轮就生效，代答话题不带。
- **原则已授权的不再问**：原则块开头和记忆的规则都写着：要问主人之前先看原则，原则里已经同意的事照着做。部署也可以这样长期授权：记下“空闲时直接部署”就等于主人提前开了口。

文件格式和注入的长度上限见[实现细节 · 原则的存储与注入](butler-internals.md#原则的存储与注入)。

## 知识库

主人说“记一下”的东西集中存放，所有 Harness 的新会话都带上，管家能搜索和修改。默认开（`COVEY_KNOWLEDGE=0` 关，见[配置](configuration.md#知识条目与历史搜索)）；关着时不建目录、规则和提示词一字不变、工具清单里没有这些工具、汇总里没有这一节。

- **存储**（`core/knowledge.py`，只用标准库）：`<state>/knowledge/` 下通用一份、每个工作区一份，只追加的事件（新增、改写、作废），读时重放。条目分 decision、practice、pitfall、fact、question 五类，正文最多 200 字。
- **管家**：记一条、改、找都用记忆的工具 `memory_save`、`memory_revise`、`memory_search`（见下面「记忆」）；旧会话的 `knowledge_*` 照样转过去。查以前的事按 `memory_search` → `topics_search` → `history_search`。
- **话题里说“记一下”**：主人这一轮明确说了，模型才把要记的写进检查点的 `remember`；任务进程退出之后由 Bridge 里的 `app/knowledge_collect.py` 核对后写入。
- **注入**（`app/knowledge_turn.py`）：工作区那组谁的话题都带，通用那组只在主人自己的一轮带，总长 1500 字；代答话题不带。
- **查历史**：设了 `COVEY_HISTORY_CMD`（绝对路径）时，主人自己的话题多一行怎么用这个命令，管家多 `history_search`。
- **汇总**：汇总卡和菜单「看板」多一节“新记的知识”。
- **回退**：去掉两个变量重新注册；已经写下的 `knowledge/` 留着。

存储格式、收集的条件和注入的顺序见[实现细节 · 知识库的细节](butler-internals.md#知识库的细节)。

## 记忆

默认开（`COVEY_MEMORY=0` 关，见[配置](configuration.md#记忆)）；关着时规则、续接提醒、答案卡和任务记录逐字不变。原则、知识条目、专项记忆和话题记忆合成一种存储（`core/memstore.py`，存在哪、怎么迁移、回滚后再升级见[运维 · 记忆的存储与迁移](operations.md#记忆的存储与迁移)），对主人只说“记忆”。

- **三类、三个范围、一个短码**：规矩（`rule`，以后每次照做）、决定（`decision`，问题卡的回答和定下的事）、资料（`note`，事实、做法、坑）；管全局、管一个专项、管一个话题。每条有一个固定短码（R、D、N 加 4~6 位），旧编号 `p…`、`k…`、`M12` 照样认。
- **每轮怎么带**（`app/memory_turn.py`）：规矩放在系统规则里，话题内不变（能命中缓存），按范围有上限（全局 15 条或 1,200 字、专项 10 条或 1,000 字、话题 5 条或 400 字），名额先给你定的、再给新写的，超出的（最旧的非你定的）只列标题，一条不丢；带的那些仍按写入的顺序排，规矩一段不跟着变（`pick_rules`）。全局的只在主人自己的一轮带，负责人记的标“负责人记的”。不是主人自己的一轮（群里别人、协作者）只读本话题和本专项的，别的专项、别的话题的资料和决定连标题都不列（`core/memory_search.py` 的 `_allowed`）。在办的决定、和这一轮相关的资料前 5 条、相关但没带全文的标题放在消息末尾，每轮按话题标题、话题要点、用到的仓库和主人这一轮的话现查（`core/memory_search.py`）。代答话题什么都不带。
- **决定的在办期**：本话题自己的决定一直带，直到话题结束或同一道题有了新回答；同专项别的话题定的，14 天内、提问的话题此后没有交付提交，并且是 48 小时内定的或提问的话题 48 小时内有过一轮，才带给其他话题。网页记忆中心的“在办”用的是同一个判定。
- **查**：`covey memory search "<一句话>"`、`show <短码>`、`list`（`bin/covey_memory.py`，话题里也能用）；管家用 `memory_search`。查不到的不算命中：没有足够的共同词、分数低于阈值的都不返回。
- **写**（`core/memory_gate.py`）：带“今天、刚才、目前”这类时间指代或“现网第 N 代”这类现状的，拒绝或改写后再记；“这个、那类”只打标。自动学到的、晚间候选、负责人立的规矩、迁移时续带的负责人约束都先进**待审核**，主人在网页记忆中心或设置卡「记忆」点「采纳」才算他定的。
- **问前查重**（`app/question_dedup.py`）：一道题发给主人之前，先在本话题和本专项答过的决定里找同一道题（检索的单向相似度不低于 `DEFAULT_TAU_DUP`、两道题互相也像）。能在同一轮收回问题的后端（Claude Code），两题很像且不属于部署、删除、花钱、对外发送、占机器这五类时，直接把上次的回答还给模型，同一道题最多这样一次；其余情况照常发卡，题目下多一行灰字“上次你答过：…（话题号 · 日期）”。同一类题第三次答成一样时，卡上多问一句“以后这类还要问你吗？”，选“以后按这次的做”记成一条规矩；两个选项都让这一类 30 天不再追问（`memory/dedup.json`）。
- **管家的工具**：`memory_save`、`memory_revise`、`memory_search`（`app/butler_knowledge.py`）。旧会话里的 `principle_*`、`knowledge_*` 照样转到这三个，但不再列给模型。
- **在哪看、在哪改**：网页记忆中心（`app/web_memory.py`，[数据约定 v43](web.md#数据约定-v43记忆中心与仓库)：待审核、规矩、决定、资料、记录五个页签）；飞书设置卡「记忆」只剩各范围的计数、待审核的「采纳」「不要」和打开网页的链接（`app/memory_panel.py`）；答案卡“记下了”一行带「不对」。

字数上限、出处规则和纠正的核对见[实现细节 · 记忆的细节](butler-internals.md#记忆的细节)。

### 记忆自己长（开关默认关）

`COVEY_MEMORY_LEARN=1`（要 `COVEY_MEMORY` 开着，[配置](configuration.md#记忆)）才有；关着时上面写的一字不差。原来只有模型主动在检查点里写、主人说了“以后/别再”才记，实际几乎记不下；Harness 自己记的（Claude Code 的自动记忆、Codex 的记忆）各管各的，主人看不到。打开后：

- **每轮之后读一遍**（`app/memory_learn.py`）：主人自己的一轮正常结束、原话里有“以后、每次、别再、记住、一律、永远”这类明确说“往后都这样”的字眼（“先、不要、别、不是、应该”这种日常口语不算），Bridge 用小模型读他自己的话。只读主人真实发来的话（含他答问题卡的话）：定时回看、`[Bridge 叫醒]`、`[Bridge 说明]`、管家和负责人派的活、协作的轮次一律不读，以轮次来源为准。问题卡那一轮只读他答的和补充的，题面和选项只交给小模型弄清他答的指什么，不当他的话。小模型不记报 Bug、吐槽、纯提问，也不记里面带“上午、刚才、这一轮、这批、这类、上次、今天”这种离开当时情境就不成立的话（代码里再核对一次，命中就丢）。引用核对过的长期要求这样处理：只对这件事的，记到专项或话题，马上生效，答案卡上一行“记下了…”带“不对”；管全局或整个工作区的，先放进待审核（设置卡「记忆」页签或网页记忆中心，带他的原话），采纳才变成原则，答案卡上写“待审核”，“不对”把它撤掉。他这一轮的话和这一轮带的某条记忆直接矛盾时，话题或专项里的那条当场收起，答案卡上写“收起了 M123：…，因为你这轮说…”，点“不对”放回去；原则不自动动，他现在说的进待审核，卡上说明和哪条冲突。管家自己的一轮也读（管家转交的轮次不读，读的是管家那一轮）；主人直接发给负责人的话也读，只认管全局和工作区的长期规矩；代答话题、开了脱敏的话题不读。
- **辅助模型选了“不用模型”时**：每轮之后那一遍读不了，检查点里“以后/别再”的规则（`memory_turn.fix_rule`）照旧带上，主人的纠正还有这一条路径能记下。
- **用到才留**：这一轮照着哪几条做了，模型在检查点的 `memory_used` 里写编号，回复里提到的编号也算（`core/memory_usage.py`）。一轮带了全文或有用到的信号，就记下这条的最近使用时间（`memory/usage.json` 的 `last`）；每晚整理按它和旧用量文件里较晚的那个算闲置，只列了标题不算用到。
- **你反复说的进待审核**：晚间汇总时按规则（不调模型）找他在不同话题里说过不止一次的纠正，放进待审核，采纳才变成原则；汇总卡不再列它们，只留“记忆：待审核 N 条”一行。
- **整理记忆**（`app/memory_tidy.py`，要早晚汇总，只按规则、不调模型）：晚间汇总时把专项的“当前决定”理一遍：30 天没用过的、问的事已经办完的（比如对某一次部署的同意）、说的是别的专项的（比如在这个专项的话题里迁移、核对别的专项的记忆时答的题）收进历史记录，不再每轮带。只收起不删除，卡上「撤销」放回去。以前由模型判的“被新回答替代的”和提炼的“新约定”已经不做了：矛盾由记忆自己长在每一轮遇到时处理，旧卡上的「确认长期」「不对」只回一句已下线。
- **别处学到的**（`app/memory_harvest.py`，要早晚汇总）：晚间汇总时只读一遍 Codex 的记忆摘要和各工作区 Claude Code 自动记忆里关于你的偏好，有变化才问，提出的放进待审核（类型“导入”），采纳才变成所有 Harness 都带的原则。改写时人一律叫「主人」，「负责人」只指专项负责人，“回复负责人”“负责人拍板”这类会改成“主人”。
- **查记忆**（`core/memory_search.py`、`bin/covey_memory.py`）：记忆块末尾写着命令，放不下的、收起的、答过的题都能按一句话查；要问主人之前先查他答过没有。谁能查到什么和记忆块一样（全局的只在主人自己的一轮，脱敏话题的只给脱敏话题）。

Harness 自己的记忆在代答话题和脱敏的一轮里不读不写，开没开这个开关都一样：见[代答](proxy.md)和[架构 · 敏感词脱敏](architecture.md#敏感词脱敏)。细节见[实现细节 · 记忆自己长](butler-internals.md#记忆自己长)。

`<state>/main-thread.json`，字段见 `Settings`：`mode`/`enabled`；管家的 `model`、`effort`、`redaction`、`workspace`、`compact_tokens`；新话题的 `topic_defaults`（`harness`、`model`、`effort`、`run_mode`、`redaction`、`workspace`）；子 Agent 用什么模型 `subagents`；工作区用途 `workspace_notes`。缺的或坏的字段按默认值读。只经 `update` 写，只有设置卡（和网页的设置页，走同一处）能写。

### 换 Harness

管家的 Harness 和开新话题一样在设置卡上选（「配置」页“管家”一段的第一行），供应商、模型、思考预算跟着它走；换了 Harness，模型换成它列出的第一个，思考预算保留原来那一档（新模型没有这一档时换成它的次高档，没有次高档时换成不带编排的最高一档）。

- **什么时候生效**：管家手上没有在跑的一轮时（`app/butler.py` 的 `write_topic`，和换工作区一样）：`topic.json` 的 `harness_id` 换成新的，`binding_revision` 加一，新 Harness 的会话指针清掉（以前在它上面的会话落后于之后的对话）。有一轮在跑时新消息照旧进旧 Harness 的这一轮。新会话的第一轮带最近的对话（和换工作区一样），不做交接摘要。多路并行的各路也跟着换，各自等空闲。
- **工具**：MCP 服务还是 `bin/covey_butler_mcp.py`，`mcp_config` 由各后端自己接：Claude Code 是 `--mcp-config`，Codex 是线程配置的 `mcp_servers.bridge.*`，Antigravity 是这一轮私有主目录里的 `mcp_config.json`（[harnesses.md](harnesses.md#antigravity)）。规则和快照在每轮消息的正文里，和 Harness 无关。工具名 Claude Code、Codex 里是 `mcp__bridge__<工具名>`，Antigravity 里是 `mcp_bridge_<工具名>`，规则里两种都写。
- **压缩和快照**：Claude Code 和 Antigravity 由 Bridge 压缩（capability `compaction`；Antigravity 用 agy 自己的 `/compact`，见 [harnesses.md](harnesses.md#antigravity)）。Codex 自己压缩，Bridge 看不到，所以每一轮都给完整快照，不只给变了的行。
- **脱敏**：只有 Claude Code 能脱敏。开着脱敏时不能换到别的 Harness；换过去以后脱敏一行不显示。
- **专项负责人**：有自己的 Harness、模型和预算（[专项 · 负责人用哪个 Harness](projects.md#负责人用哪个-harness)）：新建时先看管家开专项时你点名的，再看设置卡「配置」页“专项负责人”一段，都没有才照管家的（`app/lead_harness.py` 的 `binding`；管家还没在这个私聊跑过一轮时，照它现在会用的，`app/butler_harness.py` 的 `unwritten_topic`）；之后管家换 Harness 不影响已有的负责人，要换点专项卡上的「换配置」。负责人在哪个 Harness 上都只读（[专项 · 负责人只读](projects.md#负责人只读)）。
- **后台活跟着管家换**：同时做几件事的分流、整理专项、记忆自己长都经[辅助模型](configuration.md#辅助模型)（`app/assist.py`）：默认“自动（跟随管家）”，管家换到 Codex，它们也跟到 Codex（连同供应商）；设置卡「配置」的「辅助模型」一节可以点名某一个 Harness（只用它，用不了就说明原因、不换别家）或选“不用模型”。管家关着时这一项照样在、照样生效。子 Agent 一项只对 Claude Code 生效。
- **新装没有 Claude Code 时**：`./install` 第 3 步 Claude Code 没调通、Codex 或 Antigravity 调通了时，在服务第一次启动前把 `harness` 写成调通的第一个（先 Codex 后 Antigravity；`core/butler_settings.py` 的 `preset_harness`，只写这一项，私聊模式照旧由第一次启动写成管家）；专项、整理专项照常开。之后装好 Claude Code 也不自动换回，在这一段换；见[安装 · 没有 Claude Code 时](install.md#没有-claude-code-时)。
- **回退旧版本**：旧版本不读 `harness`，管家回到 Claude Code，但模型还是新 Harness 的模型 id；回退前先在设置卡上把 Harness 换回 Claude Code。

## 话题链接

管家卡、回带卡上的 T 号是链接（`app/topic_links.py` 的 `linkify`），打开话题并停在一张卡上：回带卡上它自己的话题停在回带的那一轮的卡，别的停在最新的任务卡。

- 有话题串的用 applink `client/thread/open?…&thread_position=…`，读不到位置时只打开话题串。
- 位置由 `feishu/message_read.py` 的 `fetch_message_detail` 读一次，记在 `<state>/topic-links.json`，每个话题留 `KEPT`（8）条。
- 读不到保持纯文字；读消息在所有锁外（规则 1、2）；只改显示的文字，保存的回复（规则 5）不变。

### 派发卡

默认开（`COVEY_DISPATCH_CARD=0` 关，见[配置 · 派发卡](configuration.md#派发卡)）。管家用 `topic_send` 把事转给**已有话题**的那一刻，主人那条提问下面多一张**进度卡**：回复到提问、进提问的串，和新开的话题挂在提问下面一样；聊天区顶层只留管家的一个回答，提问在聊天区的预览就是“T12 在做 · 标题”。话题照旧在原处、有串、有自己的任务卡。关着时没有这个调用、没有后台线程。

- **串里的卡**：串根就是提问，卡上不再有“你问”块，卡头是话题的 T 号和标题，折叠面板是“进度 · 工作区”。
- **串里怎么回**：引用这张卡说话进那个话题（卡的别名带 `routes_to`）；在串里直接发、不引用卡的，串根是主人的提问、归管家，管家再决定交给谁（和管家跑久了挂进提问串的任务卡一样）。补充、停止用卡上的按钮。
- **带 `project` 的转交仍在顶层**：管家判断是长期的事（`topic_send` 带 `project`）时，卡可能直接变成专项卡，照旧是顶层一条消息、带“你问”块。
- **提问的串已是别的话题的**：同一轮里先 `topic_start` 开了话题、提问被它占了，再转给已有话题时不发派发卡（那个串是新话题的），由“→ T12”小卡指过去；反过来先转交再开话题，新话题不占这个串，根是顶层话题卡。

- **开新话题不发**：`topic_start`、`topic_fork` 开的话题在顶层已经有一处：话题串挂在主人那条提问下面，或者（同一条提问的第二个话题、查不到提问时）它自己的话题卡就在顶层，串在聊天区的预览就是它的最新进展。再发一张派发卡就是同一个话题在顶层出现两次，所以不发；停止、补充在话题串里的任务卡上。
- **补充进管家开的那一轮不发**：转话被当作补充，送进 `topic_start`、`topic_fork` 开的那一轮时，那一轮在自己的串里，也不发。
- **派发卡代替小卡**：转给已有话题、发了派发卡的，管家只做了交接时不再在主人那条消息下回“→ T12「标题」 ›”小卡（派发卡上已有去处和“打开话题”）。

卡上是状态、T 号和用时、当前步骤，以及补充、停止、打开话题三个按钮；Bridge 里一个后台线程（`app/dispatch_cards.py` 的 `DispatchCards`）跟着话题的任务记录刷新它，结论回带后整卡换成一行“✅ 做完 · 看结论 ›”（链到聊天区的结论；顶层的旧卡写“结论在下方 ›”）。卡的内容、记录、刷新节奏、按钮落在哪一轮见[实现细节 · 派发卡](butler-internals.md#派发卡)。
