# 网页工作台

网页工作台是 Covey 的一个配套网页应用：私聊里的专项、话题、每一轮和等你回答的问题都在网页上看得到，也能在网页上说话、答题、停话题、开新话题、改设置。网页是主工作台，飞书管提醒和快速回复；两边读写的是同一份记录。

前半篇给使用者（是什么、怎么开、网页上能做什么），后半篇是数据契约，给写网页前端的人。

## 怎么打开

默认关，飞书里的功能不靠它。网页的源码在仓库的 `web/`，有三种用法：

- **一键部署到飞书的全栈应用平台**：飞书企业开通了能建全栈应用的平台时用，网址、https 和飞书登录都由平台提供。一条命令建应用、建表、发布，并写好下面的 `web.json`；命令、步骤和出错处理见 [web/README.md 的「部署」](../web/README.md#部署)。
- **自托管**：没有这样的平台，或想让数据只留在自己机器上时用。网页是本机的一个 Node 进程，由 Manager 拉起；装机时加 `./install --web`（公网直连加 `./install --web-public ADDR`，见[安装](install.md#网页工作台可选)），或照下面的[自托管](#自托管本机上跑网页默认关)手动装。
- **自己写网页应用**：按下文的[数据契约](#数据契约)，另写一个实现 `/sync/upsert`、`/sync/inbox` 等接口的网页应用，每个主人一份，不和别人共用。

一键部署到全栈应用平台还会在你和机器人的私聊顶栏（和 Pin 同一排）自动建一个「工作台」标签，点开在飞书里内嵌打开网页，不跳外部浏览器：脚本以机器人身份调会话标签页接口，机器人的飞书应用要有 `im:chat.tabs:write_only`（已在默认权限清单里，升级后「飞书应用待补」卡会提示补）。还没和机器人私聊过或缺权限时只提示、不影响部署；老部署补建用部署脚本的 `--only-chat-tab`，命令和细节见 [web/README.md 的「部署」](../web/README.md#部署)。「工作台」排在「消息」后面（第 2 位）。想再固定到飞书左侧主导航，要在机器人的开发者后台手工开「网页应用」能力、主页填网页地址并发布版本，步骤见 [web/README.md 的「部署」](../web/README.md#部署)。自托管没有这一步，要的话在飞书里手动给私聊加一个网址标签。

前两种由部署脚本或安装器写好配置，只需照所在小节设开关。自己写的网页应用，要准备：

- **接口地址和密钥**：网页应用开放接口的根地址（形如 `https://<域名>/app/<应用 id>/openapi`）和调用它的密钥。
- **这台机器能访问那个地址**：Covey 不对外开端口，只主动去请求网页应用，所以机器上要能连上它（需要代理时和模型一样设在服务清单里）。
- **脱敏词表的原词会进网页应用的库**：这是有意的取舍，为的是能在网页设置页上批量编辑词表（替身词不推；飞书卡上只显示首字和字数），所以网页应用要部署在只有你能访问的地方，做不到就别开网页工作台。

步骤（一键部署和自托管已经做完第 1 步，从第 2 步开始）：

1. 把密钥写进一个只有你能读的文件，再在数据根里写一个 JSON（路径随意，例如 `/absolute/path/to/web.json`）：

   ```json
   {
     "base_url": "https://<域名>/app/<应用 id>/openapi",
     "key_file": "/absolute/path/to/web-openapi.key",
     "push_seconds": 1,
     "poll_seconds": 1
   }
   ```

   - `base_url` 不带末尾斜杠；`key_file` 是存密钥的文件，建议权限 600。
   - 密钥只从 `key_file` 读，不进日志、记录和报告；换了密钥文件，10 秒内自动读到。
   - `push_seconds` 默认 1，`poll_seconds` 默认 0.5。文件缺了或写错，只记一行失败、退避重试。
   - `direct`（可选，`true`）：连网页时不走环境变量里的 https 代理。机器能直连网页、代理又慢时打开（实测一台开发机经代理上传约 0.1 MB/s，直连 4–7 MB/s）；没写照环境变量走代理，和以前一样。改了 10 秒内读到。
   - 可选 `page_url`：你在浏览器里打开网页工作台的地址（`https://` 开头，例如 `https://<域名>/app/<应用 id>`）。写了它，菜单「看板」、置顶的「手上的事」和早晚汇总最后一行多一个「打开网页」；不写就没有，卡片和原来一样。
2. 服务清单里设 `COVEY_WEB=1` 和 `COVEY_WEB_CONFIG=<上面那个文件>`，重新注册服务（见[配置 · 改开关三步](configuration.md#改开关三步)）。
3. **确认连上了**：一两分钟内网页上出现你私聊里最近的话题，“最后同步”的时间在走；在网页上对一个话题说一句，飞书的话题里出现这一轮。`bridge.log` 里没有 `web sync … failed`。
4. 关掉：设 `COVEY_WEB=0` 重新注册。网页上已有的内容留着，只是不再更新。

开着时 Bridge 里多五条后台线程：`web-push`（快看：推在跑、等你、刚结束的话题）、`web-pass`（全量：一轮轮补读其余话题）、`web-inbox`（取网页上的操作，交给各自的车道执行）、`web-touch`（网页刚操作过的话题马上单独推）和 `web-reread`（快看读某个话题卡在网络盘上时，换个线程重读它）；没开时没有线程、没有请求，行为和没有这个功能时一样。

### 自托管（本机上跑网页，默认关）

不想依赖外面的网页应用时，网页也可以跑在同一台机器上：Manager 拉起一个只监听 `127.0.0.1` 的 Node 进程，Covey 通过回环地址（`http://127.0.0.1:端口/openapi`）和它说话。构建产物和部署说明在 `web/deploy/selfhost/README.md`。Covey 一侧：

1. 构建网页：`bash web/deploy/selfhost/build.sh /absolute/path/to/covey-web`（把 `web/` 拷到那个目录、`npm ci`、构建，打印 `dist-selfhost` 的路径；详见 `web/deploy/selfhost/README.md`）。
2. 备好密钥和配置：`python3 -B -m covey.service.web_selfhost --dir /absolute/path/to/covey-web/dist-selfhost`（可加 `--port`、`--data-root`、`--page-url`）。它在数据根的 `web/` 下生成开放接口密钥文件（权限 600，已存在不覆盖）和 `web.json`（`base_url` 为 `http://127.0.0.1:18650/openapi`，`page_url` 默认 `http://127.0.0.1:18650/`：飞书卡片「打开网页」打开的地址；从别的设备访问时用 `--page-url` 换成那边能打开的地址，已有的 `page_url` 不给参数时保留），并打印要设的开关。
3. 服务清单里设打印出来的 `COVEY_WEB=1`、`COVEY_WEB_CONFIG`、`COVEY_WEB_SELFHOST=1`、`COVEY_WEB_SELFHOST_DIR`（端口不是默认的再设 `COVEY_WEB_SELFHOST_PORT`），重新注册服务。
4. Manager 之后拉起 `node <COVEY_WEB_SELFHOST_DIR>/server/selfhost/main.js`（`node` 按服务清单的 `PATH` 找），环境变量 `COVEY_WEB_HOST=127.0.0.1`、`COVEY_WEB_PORT`、`COVEY_WEB_DB_DIR=<数据根>/web/db`、`COVEY_WEB_KEY_FILE=<数据根>/web/web-openapi.key`；挂了按服务的退避（5 秒到 5 分钟）重启，Manager 退出时整组回收（Manager 被强杀时，网页进程发现父进程不在了几秒内自己退出，不占着端口），日志在 `<数据根>/web/logs/selfhost.log`（超过 10 MB 轮转）。机器上要有 `node`，找不到只在 `manager.log` 记一次、之后照退避重试。

`base_url` 只接受 `https://`，唯一的例外是本机回环的 `http://127.0.0.1`、`http://localhost`、`http://[::1]`（可带端口）；其他 `http://` 一律拒绝，密钥不会走明文发到别的机器（早先的版本也收任意 `http://`；升级后这种配置读不进来，同步停住、日志里写明原因，改成 `https://` 即可）。要从别的设备访问，用下一节的公网直连，或在前面放自己的反向代理（也可以用 ssh 转发、Tailscale）并用 `https://`，写在 `page_url` 里；回环端口本身不要对外开。没设 `COVEY_WEB_SELFHOST` 时 Manager 不起线程、不起进程。

### 公网直连（自带 HTTPS）

要从别的设备直接打开，不想另搭反向代理时，网页进程可以自己在公网端口上听 HTTPS。本机回环的 HTTP 照旧一直开（Covey 同步靠它）。

1. 备好密钥和配置时加 `--public`：`python3 -B -m covey.service.web_selfhost --dir /absolute/path/to/covey-web/dist-selfhost --public 203.0.113.10`（地址可以是 IPv4、IPv6、域名，逗号分隔写几个；`--public auto` 在终端里用本机的公网地址问一次确认，非终端要写明；端口用 `--public-port`，默认 18443；监听地址 `--bind`，默认 `0.0.0.0`）。命令会多打印要设的开关 `COVEY_WEB_SELFHOST_PUBLIC`（端口、监听地址不是默认时另设 `COVEY_WEB_SELFHOST_PUBLIC_PORT`、`COVEY_WEB_SELFHOST_BIND`），把 `page_url` 写成 `https://<第一个地址>:<端口>/`（IPv6 自动加方括号）；`--page-url` 优先。
2. 在防火墙和云服务器的安全组里放行命令打印的 TCP 端口。
3. 证书：不给就用网页进程生成的自签证书（`<数据根>/web/tls/`，EC P-256，有效期 397 天，名字写进 SAN，30 天内到期或地址变了会重建）。命令在构建产物里有 `server/selfhost/tls-cli.js` 时会先生成并打印指纹。浏览器第一次会警告“不安全”：核对页面的证书指纹和命令打印的一致，点“高级”→“继续访问”。有域名和证书时用 `--tls-cert`、`--tls-key`（绝对路径，一起给）换成自己的，浏览器就不会警告。网页不发 HSTS，所以自签证书能点“继续访问”。
4. 重新注册服务，Manager 拉起带公网监听的网页进程（设置变了会重启它）。证书准备不了时只记日志、不开公网监听，回环照常，体检会说原因。

公网监听上的约束：`/openapi/*` 一律拒绝（不论密钥），`/healthz` 不开，会话和登录的 cookie 都带 `Secure`，响应带 `X-Frame-Options: DENY`、`Content-Security-Policy: frame-ancestors 'none'`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`。登录用飞书确认（见下一节）：浏览器打开网页地址，点“用飞书登录”，在飞书私聊里核对对照码、点「允许」。没设 `COVEY_WEB_SELFHOST_PUBLIC` 时不开公网监听、不生成证书。

### 体检

开了 `COVEY_WEB_SELFHOST=1` 的运行中的服务，`covey_doctor.py` 里多一行自托管网页（JSON 报告里是该服务的 `web_selfhost`；没开时没有这一项、不发请求）：构建产物在不在、`node` 在不在服务的 `PATH` 里、密钥文件在且权限 600、`web.json` 的 `base_url` 指向本机这个端口、回环的 `/healthz` 通不通；公网模式再看公网监听起没起来、证书和私钥在不在（私钥只看权限、不读内容）、证书 30 天内会不会过期、SAN 盖没盖住地址、公网端口连不连得上（从本机连，防火墙和安全组放行没有，只能从外面试）。正常时一行 `✓ 自托管网页在运行：本机 …，公网 https://…:18443/（自签证书到 YYYY-MM-DD）`，有问题每条一行 `✗` 或 `!` 加“下一步”。它不让服务变 degraded，也不影响退出码；设置卡的「诊断」标签不变。

### 备份与恢复

开了自托管时，每日备份（见[备份、归档与维护](operations.md#备份归档与维护)）多收网页数据库：成员 `selfhost-web/pglite.tar.gz`，结果记在 `maintenance-status.json` 的 `web_backup`。恢复：

```
python3 -B -m covey.service.web_selfhost --restore-db /absolute/path/to/backups/bridge-<时间>.tar.gz
```

也可以给 `pglite.tar.gz` 本身。命令安全地解到 `<数据根>/web/db.restore/`（拒绝 `..`、绝对路径、链接和设备文件），最后写标记，再给运行中的网页进程发 SIGTERM；Manager 几秒后拉起它，它把旧库改名为 `db.before-restore-<时间>`、换上恢复的库。网页进程没在跑时只放好，下次起来生效。外部 Postgres 用 `pg_dump` 和 `pg_restore`，不走这里。

### 网页登录确认

自托管的网页用飞书确认登录：在网页上点“用飞书登录”，网页往发件箱写一条 `login` 操作（`op_id` 是 `login-<request_id>`，`payload` 带 `request_id`、4 位对照码 `code`、`browser`、`os`、来源地址 `ip` 和发起时间 `at`，秒）。Covey 取到后在你的私聊发一张「网页登录确认」卡：写明浏览器、系统、来源（本机回环写“本机”，经 Tailscale 或反向代理来的写对方地址；旧网页不带 `ip` 时不写这一行）、对照码和发起时间，按钮「允许」「不是我」；这条操作的回执只说“已发出确认卡”，不代表你同意了。

- 只有主人能点。点了之后 Covey 向网页的 `POST /sync/upsert` 推一条 `login` 条目：`{"type": "login", "key": <request_id>, "rev": <唯一值>, "data": {"decision": "approved" 或 "denied", "decided_at": <秒>}}`，推成功后整卡换成“已允许 · 时间”或“已拒绝 · 时间”；推失败卡上写明原因、按钮还在，可以再点。
- 发起超过 5 分钟再点，卡显示“已过期”，什么也不推；同一个请求只处理一次，已决定后再点只是重画结果。对照码要和网页上显示的一致，不是你发起的就点「不是我」。
- 点击先应答飞书，推送在应答之后、记录锁之外发。网页回答了却没收下（`upserted` 为 0：网页上这次登录已过期、已处理，或不是自托管的网页）时，卡显示“已失效”，没有登录，也不再推。
- 确认卡的记录在 `<state>/web/logins.json`（最近 100 条）。

### 连不上时

| 现象 | 先看 |
| --- | --- |
| 网页上一直没有内容 | `bridge.log` 的 `web sync push failed (N): …`：地址、密钥文件或网络不对；改好后不用重启，下一次重试就会推上去 |
| 网页上能看，点了没反应 | `web sync inbox failed` 是取不到操作；`web op <操作> failed` 是取到了但执行失败，网页上那条操作会显示失败原因 |
| 有的话题不更新 | `web sync push leaves topic … while its read is stuck`（或 `web sync pass …`）：读这个话题的记录卡住了（多半是网络盘），卡住的读结束后会自己补上；`web sync … stuck … at: …` 写着卡在哪一步 |
| 状态整体慢半拍 | `web sync push waits: the jobs index is held …`：别的线程在读任务索引时卡在网络盘上，快看先跳过，索引放开后记一行 `goes on` 接着推；这期间飞书侧写任务记录也会慢 |
| 设置页是空的 | `web settings not built` / `not pushed`，其余同上 |

## 网页上能做什么

- **看**：每个专项（目标、话题、记忆、资料库、报告）、每个话题（状态、每一轮的你说和它答、执行过程、计划、用量、失败原因、图片），管家和专项负责人的对话也各是一个话题。状态色、“要你处理”“停住了”的算法和飞书的看板一致；Covey 推了 `asks`（v34）时，看板、侧栏和手机标签栏上“要你处理”的数就用它，和飞书看板、「手上的事」同一个数。
  - 管家、负责人和话题页的一轮画法一样：你说的话靠右、带浅色底（答题的那句是“问题 → 选择”的表），回答上面一行是谁和几点，再一颗“工具 N · 用时”点开看过程；回答下面一行是复制按钮和这一轮的输入（Harness、供应商、模型、思考、脱敏、工作区）、输出（用时、速度、token、缓存命中）；话题页没有单独的“第 N 轮”列表，上面只多一块总览。电脑上对话区左边有一列刻度，一句你说的话一条，鼠标停上去看那句和回答的开头，点一下跳到卡片上的那句（手抖挪过一两像素不换，按下松开不在同一条上也算数；鼠标在刻度上时来了新一轮，刻度也不整体挪），也能用上下键和回车；找话题里的话用左上角的搜索。
- **大厅**：你、管家和各专项的负责人在一条时间线上，和飞书私聊顶层一样：管家的回答、负责人对你说的话、话题做完发到私聊的结论（收成一行，点开看全文）、等你回答的问题、专项建好和结束。顶上一排是成员：管家一直在，每个没结束的专项多一位负责人。
  - 不 @ 时这句话交给管家，由它判断自己答、开话题还是转给负责人；输入 @ 选一位负责人就直接交给它。你那句话下面写着最后交给了谁（“→ 管家 → T12”）；交错了就 @ 对的人再说一句。
  - 每条消息旁有“引用”，选中一段文字也能只引用这段：引用话题的结论就是对那个话题说，引用负责人的话就是对负责人说；再 @ 一位就交给 @ 的那位，引用的内容一起带上。话题不能 @。
  - 专项页的负责人对话是大厅里只看这位负责人的那部分，在哪边说都一样。
- **两侧栏调宽**（电脑上）：左侧栏和话题页的进度栏、专项页和看板的右栏，拖分界线就能调宽（悬停时分界线亮起），双击分界线回到默认，聚焦后 ← → 也能微调；各自的宽度记在这台浏览器上，中间的对话区至少留 480 像素。
- **深色和浅色**：一个常驻的图标，哪一页都能点：电脑上在侧栏底部「设置」旁（侧栏收起时叠在设置上面），手机在顶栏最右。图标画的是点了换成的那一种（深色时太阳，浅色时月亮），选了哪种记在这台浏览器上，默认深色。

## 数据契约

这一节写给网页前端：Covey 推什么、怎么推，网页能发回哪些操作。字段后面的“v N”是数据约定的版本，前端按版本判断有没有这个字段；新字段都是可选的，旧网页不认就忽略。代码在 `core/web_sync.py`（配置、条目、操作账本）和 `app/web_*.py`。

### 推

`web-push`（快看）和 `web-pass`（全量）两条线程一起把四类条目推给网页：专项、话题、一轮、问题；另有几条设置条目（见下）。条目由快看发出，全量读到的排在它后面；网页刚操作过的话题由 `web-touch` 马上单独发（见下）。

- **只推变了的**：每条带内容哈希 `rev`。一批最多 500 条，字节数（按发出去的 UTF-8 字节算）看网页说它收多大（v44）：`/sync/upsert`、`/sync/images/have` 的响应带 `limits`，`body_bytes` ≥ 2,000,000 时一批按它的 0.6 倍、最多 5,000,000 字节（网页默认 8mb 时就是 5 MB 一批），否则照旧 1,000,000 字节（旧网页的请求体上限是 1 MiB，超了整批 500）。还没收到过 `limits`（刚启动的第一批）照 1 MB 发；`web.json` 的 `base_url` 或 `direct` 换了从 1 MB 重来。另按这条路实测的快慢收（`Client.rate`：每个 200 KB 以上的请求都计时，没回音的也算，取最近几次的平均）：一批不超过约 4 秒能传完的量、最少 250 KB，一张图不超过约 8 秒的量、最少 700 KB；还没测过时一批不超过 1 MB、一张图 700 KB。经慢代理时 5 MB 一批要传 50 多秒，快看会当它卡住。POST `/sync/upsert`。代码在 `core/web_sync.py` 的 `limits_of`、`batch_bytes`、`image_bytes` 和 `app/web_push_client.py` 的 `Client`。
- **节奏**：
  - **快看**（`web-push`）：每秒只看在跑的任务、等回答的问题、等你在启动卡上点开始的话题，以及刚停下或刚被网页操作过的话题，再加专项（只有记录、状态或记忆、资料库文件变了的才重读）。Bridge 自己写了任务或问题记录（比如你在飞书卡片上答了题），快看马上再看一次，两次之间至少隔 0.25 秒。快看推的也守下面“先后序号”的规矩：一个话题比网页已有的读数旧的，整份不推。日志每分钟一行 `web sync push steps=N p50=…ms p90=…ms max=…ms`，是这一分钟里每一步快看的耗时（在跑的话题多、网络盘上的读慢时一步要几秒，偶尔一次读卡几十秒，看这一行就知道）。
  - **刚操作过的话题**（`web-touch`）：网页上的一条操作回执之后，这个话题（开新话题时是新开的那个）马上由这条线程单独重建、推上去，不等快看把所有在跑的话题都看一遍；有回执后补做的事（答题之后的新一轮、它的任务卡），做完再推一次。用的看板读法是上一次快看留下的，“要你处理”的数由快看接着更新。快看或全量读这个话题时卡在网络盘上、被丢下的，它照样重读一遍（网络盘上挂住的是那一次调用，换个线程再读一般马上回来；它要是也跟着跳过，答完题要等那次读回来网页才变，可能好几分钟）；它自己读这个话题卡住 15 秒没进展，才把这个话题留给快看，那次读回来之前网页再操作它，日志写一行 `web sync touch leaves topic … to the quick look`。索引忙（`web sync touch waits: …`）或网页没收下这一批，话题放回去下次再推，不会悄悄丢掉。你这句话带的图（`say`、`launch` 的 `files` 里的图片）在操作执行完就登记为待传，这条线程先传它们再建这个话题，第一次推上去的你那一轮就带图，不用为了图把话题再建一遍；推完以后，建的时候才发现还没传的图（任务给你看的图等）由这条线程当场传（每次最多 9 张、8 秒，剩下的留给全量），传上了就把这个话题再推一次。全量正在传图时这边不抢，由全量传完再推。日志每分钟一行 `web sync touch steps=…`。
  - **卡住的话题换线程重读**（`web-reread`）：快看、全量读一个话题卡在网络盘上被丢下以后，那次读回来之前快看都跳过它（免得再卡一次），话题在网页上就停在原样，可能好几分钟。这条线程换个线程重读它：被丢下 5 秒后读一次；它还在跑、在等你、刚结束或网页刚操作过它时，每 10 秒再读一次；不再“热”了只再读一次。一次只读一个话题；重读它也卡住 15 秒的，那次读回来之前不再读它，之后还要等 60 秒（再卡就翻倍，最多 10 分钟）；同时有 2 个重读卡着时一个都不开，日志写 `web sync reread waits: …`，有一个回来了写 `goes on`。每个话题第一次重读成功写一行 `web sync reread topic … read again in … ms`，之后每分钟一行 `web sync reread steps=…`；那次卡住的读回来时写 `web sync <push|pass|touch|reread> read of topic … came back after N s; read again K times meanwhile`。
  - **全量**（`web-pass`，单独一条线程）：上一轮读完 60 秒后开始下一轮（最近 30 天有任务的话题、管家和负责人的对话），每步看 25 个话题、歇 1 秒；快看正在看的话题留给快看。全量这边哪个读卡在网络盘上，快看照常每秒推；一轮看完才知道哪些该删，每轮开始时设置、整理专项和全部专项也重读一遍，图片也由这条线程上传（网页刚操作过的话题的图由 `web-touch` 先传，见上）。
  - **全量只重建变了的话题**：看一个话题先读它的输入（`app/web_collect.py` 的 `inputs`：任务和问题记录，history.jsonl、topic.json、要点文件各一次 stat，这一轮读到的看板分组和“没看过”、加入的专项和时间、所在的协作、每轮回带到私聊的时间、到点回来看和代发草稿，开关和模型菜单），和上次建它时一样、网页也收下了上次建出的全部条目，就不重建、不读它别的文件，照样算这一轮看过，不会被删。任务没结束（排队、在跑、等回答、等开始）或有问题还开着的话题每轮都建；产物还在上传的，下一轮再读。不管输入变没变，每个话题最迟 15–30 分钟（按话题 id 错开，不挤在同一轮）重建一次兜底；进程重启、`sent` 每天清空、网页没收下、快看推过它别的读数，也都让它重建。管家和负责人的对话会读别的话题，每轮开头建一次。
  - 快看先推自己读到的变化（整份推），再推全量读到、还没推的，每次最多一批的字节数（同上，1 MB 或按 `limits` 放大），没推完的留到下一次。每个话题的每次读取都有先后序号：快看已经推过一个话题更新的读数，全量之前读到的旧读数就不再推（不然网页会被改回“等你”）。
- **网页收下了什么**：哪些条目、各是哪个 `rev`，存在 `<state>/web/sent.json`（最多每 30 秒写一次，一轮全量读完也写）。重启后接着用，只推这期间变了的；文件是推给别的网页地址的、或者从上次清空起已满一天，就全部再推一遍。进程不重启也每满一天清空一次，网页库被清空过也能补回来。
- **读法**：话题的状态和“做完没看”用看板的读法（`core/board_read.py`、`app/pins.py` 的 `board_results`），不每秒扫全部任务记录。在跑的一轮，正文是已落盘的进展说明，变了就推。每话题推最近 100 轮，单轮正文超过 64 KB 截断并写明。
- **失败**：请求失败按 2、4、8、16、30 秒退避重试，只记第一次和每第十次，不影响 Bridge 别的线程。
- **节流**（v44）：发往 https:// 网页（全栈应用平台，经飞书网关，实测每个密钥约 10 次/秒，超了回 429、没有 `Retry-After`）的请求，同一个 Bridge 里所有同步线程（快看、全量、刚操作过、重读、取件、各操作车道）共用一个令牌桶（`app/web_push_client.py` 的 `Gate`）：每秒 8 个、一下最多 10 个；拿不到令牌就等，一次最多等 2 秒，等不到也照发（只放慢，不让推送停住）。收到 429 时整个客户端 1.5 秒内不发，之后令牌从 0 开始攒，这次请求照样算失败、照上面退避。本机自托管（http:// 回环）没有网关，不节流。全量对时没有要推的，也发一批空的，网页的“最后同步”照样往前走。
- **卡住**：快看、全量、取的每一步在各自的工作线程里跑。
  - 快看一步 15 秒、全量一步 60 秒没有进展（网络盘上的 open、read 可能一直不返回），记一行 `web sync push stuck`（全量是 `web sync pass stuck`），写明卡在哪一步（`at: indexes`、`board`、`topic <话题>`、`projects`、`posting`…），丢下它，下一步换新线程。读过的缓存留着、不清空，已推过的记录（`sent`）也留着；全量这边从头开始一轮，快看不受影响。
  - 快看读任务和问题的索引最多等 5 秒：别的线程拿着索引锁卡在网络盘上时，快看这一步直接跳过（记一行 `web sync push waits`），不再一个个丢下线程。
  - 丢下的那一步后来返回了，读到的也是旧的，一条都不推（不然网页会被改回旧状态）。
  - 看完一个话题、走完一个阶段、网页收下一批都算进展，所以第一次全量推一个大私聊只要一直在动，就不算卡住；取这边按一步开始的时间算。
  - 缓存满了先丢最久没用的四分之一，不整份清空（以前一轮全量要把几百个话题的历史和过程文件反复重读）。
  - 卡在读某个话题上的，在那条旧线程结束前，推送不再读这个话题（网页上保留它原来的样子，不删），旧线程一结束就重新看它一次，日志记一行 `leaves topic`。
  - 还卡着的旧线程到 3 个就先不开新的，最多等 300 秒，到时照样换新线程接着推（记一行 `still stuck`）。

### 话题条目

- **普通话题**：`kind: topic`。另带 `round`（已有几轮）、`started_at`、`context`（最近一轮的）。
- **状态色**（v5）：`tone` 是 [UI 规范](ui.md#3-状态词表) 的状态 key（waiting、stopped、stuck、result、running、queued、done、cancelled、idle，`core/look.py` 的 `tone`）。网页按它上色、取词，不比较 `state` 的中文字；`state` 照旧。词和颜色由 `scripts/export_look.py` 导出成 `look.json` 给网页；`look.json` 另带 `retired`（v34）：`core/look.py` 的 `RETIRED`，每个状态 key 不再用的说法，网页的退役词单测（`web/scripts/words.test.mjs`）只读它，不照抄。
- **在看板的哪一组**（v6）：看板开着（`COVEY_PINNED_TOPICS` 和 `COVEY_PINNED_OVERVIEW` 都没关）时，普通话题另带 `board`：看板上的哪一组（waiting、running，结果的 stopped、result、done、cancelled），不在看板上（看过超过 12 小时的结果、点了“不管了”的、更早的）为空串。网页的“要你处理”“停住了”和侧栏红点按它算；没开看板时不带这个字段。`board` 是 stopped 的话题正好是 `asks`（v34）数进停住了的那些：专项成员在看板上折进专项的格子、格子显示的是别的话题，或者在看板起算以前停的，只要算进要你处理，`board` 就是 stopped；要你处理不算的停住（负责人会被叫醒去处理的专项成员，见[专项](projects.md)）不是 stopped，网页按“看板已放下”画灰（`app/web_collect.py` 的 `board_groups`）。
- **进度**（v4）：在跑的话题带 `progress`：`{phase, plan_done, plan_total, last_activity_at, last_activity, eta_seconds, slow_step, maybe_stuck}`，和任务卡、看板同一个函数（`core/progress.py`）。
  - `last_activity` 是“在跑测试”这样的人话。
  - `eta_seconds` 估不出来为 null，到分钟（按这一轮平均每步用时减去当前这步已做的时间）。
  - `slow_step`：当前这步已经比平均每步慢时是 `{number, since, seconds, usual}`，此时 `eta_seconds` 为 null，网页可写“第 3 步已做 35 分钟，此前平均每步约 6 分钟”；否则为 null。
  - `maybe_stuck`：超过 `COVEY_PROGRESS_STUCK_MINUTES` 分钟没有动静；最新一步是还在跑的命令时不算。
  - `command`：只在最新一步是还在跑的命令时才有这个键，`{since, seconds, long}`（开始的时刻、已跑的秒数到分钟、是否已跑满卡住的分钟数），网页可写“在等一条命令跑完 · 已 38 分钟”；旧网页不认识这个键，不受影响。
  - `next_step`、`waiting`（v41，都可选）：从这一轮的检查点读，网页的简报写“下一步”“在等你什么”。`next_step` 是检查点的下一步（至多 120 字，Bridge 垫的“检查任务要求与已有状态”和“无”不推）；`waiting` 是检查点 `requires_user` 为真时的 `question`（至多 160 字）。没有就不带键；任务卡、看板读的 `core/progress.py` 输出不变（`app/web_collect.py` 的 `checkpoint_fields` 加的）。
- **模型名**（v11）：`model_name` 是读得懂的名字（`core/model_names.py`：`router/claude-opus-5-5` → Opus 5.5，去掉路由前缀、预算后缀和 `[1m]`，`default` 为空串）；`model` 照旧是原值。
  - 话题的 `harness`、`workspace`、`model` 都是它现在绑的（topic.json，和 `config` 同一个来源），下一句话就用它们；网页输入框下沿那行“工作区 · Harness · 模型”和话题页页头照它写。绑定里没写模型的老话题，取最近一轮跑过的任务的模型；换配置以后还没跑过的，不取换配置前那个任务的（`app/web_collect.py` 的 `bound_model`）。每一轮实际用的配置看那一轮的 `ran_with`。
- **最后一轮的编号**（v12）：`last_seq` 是这次推的各轮里最大的 `seq`（没有轮次为 0）。网页收到后删掉这个话题 `seq` 比它大的轮次：在跑的一轮按“已有轮数 + 1”推，回答进来后编号可能落在更前面，原来那条“在跑”就再也不会被覆盖。收尾中的任务（回答已写进历史、记录还是“在跑”）不判“没发出去”，也不再画一条“在跑”的轮。
- **什么时候进的专项**（v13）：专项的成员话题带 `joined_at`（秒）。专项报告只算这个话题加入以后结束的轮次，和专项卡的 token 同一个口径。
- **话题要点**：开了[整理专项](projects.md#整理专项)时带 `gist`：`{essence, goal, involves, related, changed, updated_at}`，没有要点就没有这个字段。网页把 `goal` 当“目标”显示。
- **Covey 定时回看**（v34，v35 加字段，`app/web_collect.py` 的 `later_and_drafts`）：开了[到点回来看](usage.md#到点回来看)（`COVEY_REVISIT` 没关）、话题有一条预约时，普通话题带 `revisit`：`{at, what, set_at, running}`，`at` 是约定的时刻（秒），`what` 是到点要看什么（一行，最多 200 字），`set_at`（v35）是这条预约约下的时刻（秒，带小数，「取消」带着它，防止误删换过的新预约），`running`（v35）为 true 表示 Covey 已经排出回看那一轮、正在回看（这时取消不了），还没到点或已到点没排出去的是 false。只有普通话题有：话题归进了专项、成了专项负责人或管家的话题，旧的预约不再推（Covey 在话题归进专项时删掉它，存量的由 `revisits` 线程下一次看到时删）。取消了、回看那一轮结束了、开关关着时没有这个字段。
- **等你确认的代发草稿**（v34，同上）：部署有代答发送器、没关 `COVEY_OWNER_SEND` 时，普通话题带 `owner_send`：等你在飞书草稿卡上确认的草稿（`core/owner_send.py` 的 drafted，和发不出去、要在卡上再点一次的 unsent），最新的在前，最多 5 条，每条 `{id, to, state, preview, created_at}`：`to` 是发给谁（最多 60 字），`state` 是 `waiting`（等你确认）或 `failed`（没发出去），`preview` 是正文开头（一行，最多 120 字）。没有这样的草稿就没有这个字段。网页只读，「去飞书确认」打开飞书（`settings.feishu`）；**网页没有发送代发的操作**，确认和发出只在飞书原卡上。
- **当前配置**（v21）：普通话题带 `config`：`{model, effort, work_mode, workspace, run_mode, redaction}`，`model` 和 `settings.launch.models` 的 `key` 是同一套（绑的是预算预设的，换算成那个模型加预设的预算），`run_mode` 是 `direct` 或 `worktree`，`redaction` 是 `on`/`off`，`device` 是话题所在的设备（别名，本机是空串；旧 Covey 没有这个键，这时网页不写设备）（`app/web_switch.py` 的 `topic_config`，只读 topic.json）。网页的换配置面板从它开始选；`model` 不在目录里时要重选模型。专项负责人（`kind: lead`）也带（v36）：面板只列 `bridge_tools` 为 true 的模型，不画工作区和运行方式（照原样发回），换法同专项卡的「换配置」（[专项 · 负责人用哪个 Harness](projects.md#负责人用哪个-harness)）。管家不带。
- **从没开工的话题**：任务都没跑过、最后一个没开工就取消了（启动卡被停掉收起），推成“已停止”（`tone: cancelled`），全图归到折起来的做完组，不算空闲。
- **等你点开始的话题**：最新的任务在等你在启动卡上点开始（启动卡还能用）时，话题是“等你”（`tone: waiting`，开了看板时 `board` 也是 waiting），`harness`、`model`、`model_name`、`workspace` 是启动卡上现在选的（点开始就用它们），不是话题等开始时先占着的绑定（回复告警卡这类消息开的话题先绑默认的 Harness 和工作区）；不带 `config`，配置由启动卡定，点了开始才能在网页上换。

**管家**：私聊的管家话题推成一个话题条目（只推槽 0，[同时做几件事](butler.md#同时做几件事)的其余几路不推）。

- `kind: butler`，`number` 为 0，标题“管家”，不属于专项，`unseen` 恒为 false，状态照话题的算（有任务在跑是“在做”，在等你答题是“等你”）。
- 各轮来自它的历史：你在私聊顶层说的话（`owner`）和管家的回答（`agent`）；任务在跑时和话题一样推一条进行中的一轮。正文里照原样写 T 号，网页把 `T\d+` 链到那个话题。
- **交给了谁**（v23）：管家回答的那一轮（在跑的也算）带 `handed`：`[{key, kind, number, title, project_key, how}]`，这一轮成功开、转、分叉的话题（`kind: topic`，`how` 是 start、send、fork）和转给的负责人（`kind: lead`，`key` 是负责人话题，`title` 是专项名，`project_key` 是专项 id，`how` 是 send），最多 8 个，来自 `main-thread/opened/` 里这一轮的请求记录（`app/web_room.py`）。网页在你那句话下面写“→ 管家 → T12”。
- 管家不在看板里，所以单独看：任务在跑或在等你答题时每秒看一次，被网页操作碰过之后看一次，每 60 秒全量对时再看一次；没有历史也没有任务就不推。

**专项负责人**（专项开着且专项有负责人话题时）：

- `kind: lead`，`number` 为 0，标题“负责人”，`project_key` 是专项 id，`unseen` 恒为 false。
- 各轮来自负责人话题的历史：你在里面说的话（`owner`）、负责人的回答（`agent`）。Bridge 叫醒负责人的那一轮（回执，不是你说话）不推，它的回复只有负责人标了要告诉你时才算回答。
- 看得懂的回执变成一行 `role: event`：话题做完、失败、中断、停住（`T34 做完了`）；负责人在唤醒轮里派出话题时，也有一行 `负责人派出了 T31 …`。
- 每轮的 `started_topics`（`{key, number, title, harness}`）是这一轮派出去的话题：话题第一个任务进来时，哪一轮负责人最近开始过，就归哪一轮。
- 负责人在跑或有问题等你时每秒看一次，被网页碰过后看一次，每 60 秒全量对时再看一次。

### 一轮条目

- **配上它的任务**（`app/web_pairing.py` 的 `pair`）：回答那一轮带 `job_id`，过程、计划、用量、失败原因都从这条任务记录来。
  - 回答行写入历史时就带任务号；没带的旧行按顺序配：主人或负责人那条消息的 message_id、答题的 `answer-<token>`；送进正在跑的任务的补充没有自己的任务，回答仍归那个任务。
  - 连着的几条回答（限流自动重试、停止）和其余没配上的，按“这一轮开始之后、任务记录最后写入后 5 分钟以内”找没被别的回答占用的任务。
  - 还配不上的，`bridge.log` 记一行 `web sync topic <话题 id 前 12 位>: N of M answer turns have no task record`（数目变了才记）。
- **过程和用量**（可选字段，没有就不带）：
  - `steps`：最近 80 步 `{id, kind, label, started_at, ended_at, status}`，可带 `detail`。`kind` 按步骤标题归为 read、edit、command、search、subagent、web、think、other；进展说明不算步骤；在跑的一步 `ended_at` 为 null。
  - 子任务（v8）是一步：`kind` 为 subagent，`label` 是“子任务：”加它自己的描述，起止取子任务真正开始和结束的时间，这一轮结束时它还没结束的按这一轮结束算；启动它的那次“分配子任务”调用不再单列。
  - `label`（v18）是纯文本，不带卡片用的转义。模型说了这一步做什么的，`label` 只写“标题：目的”，命令放在 `detail`（最多 400 字）；`label` 超过 80 字被截断的，`detail` 是完整的那段。
  - `plan`：检查点里的 steps（`{title, state}`）；这一轮已结束时还停在 doing 的那步推成 todo。
  - `usage`（`input`、`output`、`cache_read`、`total`）、`seconds`、`speed`（token/s）、`context`（`{used, limit}`）、`notes`（记忆那一路写的 `memory_notes`，原样推）。
  - 在跑的一轮随每秒的推送更新：`seconds` 每 10 秒才变一次、`speed` 取整，没有实质变化时 `rev` 不变。已结束的轮：`usage`、`seconds`、`speed`、`context` 每轮都带，`steps`、`plan` 只带最近 20 轮的；结束超过 7 天的轮不再带 `steps`（执行过程，`app/web_collect.py` 的 `STEPS_SECONDS`；网页库里大半是旧轮次的执行过程），计划、用量、正文照旧。已推过的旧轮次在话题下次重建时（最迟 15–30 分钟）去掉 `steps` 再推一次。
  - 被 Bridge 重启打断、由自动重试接着做完的任务，它的 token 算进重试那一轮的 `usage`。
- **发到了私聊**（v23）：普通话题的回答那一轮，结论发到了私聊顶层（[结论回到顶层](butler.md#结论回到顶层)，`main-thread/relays/` 里这个任务的记录是 `sent`；合成一条发的也算）时带 `relayed_at`（发出的时刻，秒）。网页的大厅把这些轮收成一行放进时间线；负责人、管家的轮不带。
- **用的什么配置**（v27，`app/web_turns.py` 的 `ran_with`）：回答那一轮带 `ran_with`：`{harness, provider, model, effort, workspace, redaction}`，用启动卡上的叫法（Claude Code、自带、Opus 5.5），从这一轮的任务记录取；脱敏取话题现在的开关（任务记录不存）；菜单读不到时 `model` 是模型自己的名字、不带 `provider`。网页写在回答下面一行。
- **产物**（v32，`app/web_turns.py` 的 `artifacts_of`）：回答那一轮带 `artifacts`，就是它答案卡上「产物」里列的文件（`app/artifact_policy.py` 的 `drive_paths`：配置和凭据路径不列），每个 `{name}` 只有文件名，不带本机路径。传到云空间以后加 `link`（https）和 `size`（字节）；传不上的加 `error`（原因）；还在传的（上传账本 `status` 是 uploading，或者账本还没写、这一轮的任务记录 10 分钟内动过）加 `uploading: true`。上传在这一轮结束以后才做完，任务记录不跟着变：推送按任务记住读过的结果，有在传的 15 秒后整份再读，链接随下一次全量（每分钟）推上去；传完的，话题再建时离上次读满 5 分钟才看一眼上传账本，账本变了（卡片上点了重新上传）才整份再读。卡片上的重新上传不改任务记录，话题别的输入也没变时，新链接最迟随它 15–30 分钟一次的兜底重建推上去。网页在回答正文下面画一颗能点开的“产物 N 个 · 第一个 等”，顺序同答案卡：正文 → 产物 → 输入/输出。没有产物的一轮仍是空数组。
- **预计用时**：`estimate_seconds` 是这一轮第一次估出来的总用时（秒），写进任务记录后不改；专项报告的“预计 vs 实际用时”拿它比。没估出来过的轮次不带。
- **完成标准和改动**（v34，`app/web_turns.py` 的 `checked`）：结束了的回答那一轮（不在跑、不在等你）从它的检查点读，和它答案卡上“完成标准”“改动”两段同一个读法：
  - `criteria`：`[{item, state, evidence?}]`。话题有完成标准（`core/criteria.py`，管家开话题时写的那几条）时每条标准一行，`state` 是检查点标的“满足”“没满足”，没标的是“没查”；话题没定标准、检查点自己写了 `criteria` 时照检查点列。`evidence` 是检查点写的证据（最多 120 字），没写不带。
  - `delivery`：`{commit?, deployed?, verified?}`（`core/checkpoint.py` 的 `checkpoint_delivery`，空的那项不带）。只在答案卡会画“改动”时带（`shows_change`：写了提交号，或这一轮改了工作区的文件、检查点写了交付），调研、报告、问答这类轮次写了也不带。
  - 都没有就不带这两个字段。网页在输入、输出下面画“完成标准”（摘要一行，点开看每一条）和“改动”两行。
- **答题**（v4）：回答问题卡的那一轮带 `answers`：`[{question, choice}]`，只从问题记录取，不解析正文。答案作为新任务发出去的带在主人那一轮上，交回给还在跑的提问那一轮的带在那一轮的回答上；`choice` 是选中的选项或写的字，多选用“、”连起来，没答的写“没答”。
- **没开工就取消的一轮**：最后那句话的任务从没开工就取消了（启动卡被收起、排队时取消），补一行 `role: agent`、`status: stopped`，正文“没开工，已取消（原因）”。没有这一行时网页会一直写“排队中…”。
- **等你点开始的一轮**：最后那句话的任务在等你在启动卡上点开始，补一行 `role: agent`、`status: waiting`（`job_id` 是那个任务，`started_at` 是消息进来的时刻），正文第一句“在启动卡上点开始，这一轮才会开工。”，下面是点开始会用的配置和去飞书打开启动卡的链接（「手上的事」读到过那张卡在哪才有；推送不为它去读飞书）。没有这一行时网页写“排队中…”，而话题的 `round` 已经算上了这个任务，网页就把这句话编成下一轮、上面写“再早的 1 轮没有载入”。
- **没成功的一轮**（v4、v10）：带 `failure`（`{title, detail, actions}`，`core/failure.py` 的 `failure_view`，同任务卡上的那句话和按钮），只在失败、超时、重启打断、官方拒绝、任务进程没能启动时有；`actions` 取 continue、retry、diagnose、split、switch_model。带 `failure` 的回答一轮 `status` 是 `failed`，它的 `body` 是停下时的原话（任务卡的“技术详情”），网页折进技术详情，不当回答画。
  - `actions` 为空就是现在没有能点的（换旧模型重试、重启后的自动接着做已经排好，或者只能在话题里说一句），网页不补一个“检查并继续”。
  - **按钮怎么叫、怎么做**（v33，`app/web_turns.py` 的 `failure_of`）：`labels` 是 `{action: 按钮上的字}`，和任务卡一样（continue 是“检查并继续”，结果没发出去时是“重新投递结果”；retry 是“现在重试”）。`how` 是 `{action: recover | switch | feishu}`：`recover` 发 `recover` 操作（见下）；`switch` 打开网页自己的换配置（`switch` 操作，话题的 `config`；负责人的也是，v36）；`feishu` 只有飞书能做（管家的换个模型），这时才提示去飞书。网页不再用 `say` 替这些按钮发话。
  - **排好的自动重试**（v33）：`auto_retry` 只在排着时有，`{state: "pending", at, attempt, total, kind, now}`：`at` 是几点重试（秒），`attempt` 第几次，`total` 一共几次（限流那条有进展就重新数，为 null），`kind` 是 rate_limited、server_fault、incomplete、restarted，`now` 是现在就跑它的那个 action（retry 或 continue），`labels`、`how` 里另有 `now` 那一项和 `stop_auto_retry`（“停止自动重试”）。有 `auto_retry` 时网页只画这两颗（立即重试、停止自动重试）和 `actions` 里别的，不再另画 continue/retry；倒计时从 `at` 自己算（推的内容不按分钟变）。`title` 里已经写了几点、第几次。
- **谁说的、给人看的正文**（v11，`app/web_said.py`）：
  - `owner` 那一轮带 `by`：`owner`（你）、`lead`（负责人）、`butler`（管家）。负责人、管家交来的话（消息 `main-<请求>`）按请求记录找到发起的那一轮：管家那一轮是回你的一条消息，交来的就是你的原话，`by` 为 `owner`、`via` 为 `butler`；不是的，`by` 就是它。负责人交来的一律是它自己写的任务说明（请求记录带 `by: lead`），`by` 为 `lead`；更早的版本写的请求记录没有这一项，负责人那一轮回的是你的消息时那一行存的是你的原话，仍是 `by` 为 `owner`、`via` 为 `lead`。
  - 问题卡的回答：负责人分流替你答的是 `lead`，管家按你的话代答的是 `butler`，其余是你。
  - `display` 是去掉内部前缀的正文，和原文不同时才带：答题写成“答了 2 题：B；没答”；反馈问题写“没答，补充：…”；编辑过的消息只给改后的全文，另带 `edited: true`；撤回补充写“撤回了刚才那条补充：「…」”；纠正负责人的回答写“纠正负责人替你答的「…」：…”。
  - 答题那一轮另带 `note`（选项之外写的字）。`body` 仍是原文，旧网页照旧显示。
  - 编辑作为补充单独进了正在跑的任务的（消息 id `edit-<原消息 id>-<时刻>`），改后的全文放到原消息那一行，编辑这一行带 `merged: true`，网页不再单画（原消息那行不在推的轮次里时照旧单画）。
- **图片**（v19）：`images` 是 `[{id, w, h, kind, note?, gone?}]`。
  - `kind` 是 `sent`（你那一轮带的图，只认本状态目录 `topics/<话题>/incoming_media/` 下的文件）或 `shown`（任务检查点 `show_images` 推给你看的图，设备上的任务不推），`note` 是检查点里那句说明。
  - 图片只按编号给：`id` 是原图 SHA-256 的前 32 位，网页从自己的 `/api/images/<id>?v=thumb|full` 取（要登录、只有主人）。本机路径和公开直链都不给网页。
  - 传：每张一次，缩略图（长边 480）和大图（长边 2048）各一份 WebP，每份不超过 700 KB（网页的 `limits.image_bytes` 大于 760 KiB 时放大到它减 64 KiB、最多 3,000,000 字节，v44），POST `/sync/image`（`id`、`v`、`mime`、`w`、`h`、`expires_at`、`data` 是 base64）；传之前 POST `/sync/images/have` 问一次已有的。每轮最多 9 张，原图超过 20 MB 不传；全量线程每一步最多传 8 张、20 秒，网页刚操作过的话题由 `web-touch` 推完就传它的（最多 9 张、8 秒），两条线程同一时间只有一条在传。机器上没有 Pillow 时，这个上限以内的 PNG、JPEG、WebP、GIF 原样传，更大的不传。网页那边字节放平台的文件存储，见[数据约定 v44](#数据约定-v44上限文件存储与连接保护)。传过的记在 `<state>/web/images.json`。网页不收时只把图压后 5 分钟，条目照常推；网页拒收某一张（400、413）就不再传它。
  - 管家、负责人转给话题的那一行：历史里只存原话和“附件：图片 N 张”，图从它开的那个任务的提示词里取。
  - 留多久：消息之后 90 天（`expires_at`，网页每天清过期的）；更早的消息的图不传，条目里 `gone: true`、没有 `id`，网页写“已过期，飞书里还能看”。
  - 本机路径不进网页：你那一轮的正文（`body`、`display`）和问题的回答都先去掉路径（`app/web_images.py` 的 `scrub`）：“收到的附件”那块变成“附件：图片 N 张”，别处写出的路径写成“（图片）”。

### 问题条目

- 带 `asked_at`、`answered_at`（没答为 null）、`project_key`、`topic_number`。
- **题目不再等的时刻和方式**（v9）：`closed_at`（秒，还在等或不知道时为 null）、`closed_by`：`owner` 你答了、`feedback` 在旧卡的“问题不合适”上提了反馈、`skipped` 每题都没答（只交了补充说明、每题都选了不回答，飞书卡上点了“不处理”的也是）、`lead` 负责人替你答了、`superseded` 话题又问了新题、`stale` 每日维护关掉的过期题、`switched` 换配置、`rewound` 回退、`lead_stop` 负责人停了话题、`web_stop` 你在网页上停了话题、`cancelled` 别的取消；还在等或在负责人手上为空串。
- 时刻来自问题记录自己的 `answered_at`、`cancelled_at`；更早的记录没有，依次取答案续跑任务的创建时间、负责人代答的时刻、收起它的新题的提问时间、提问任务最后一次写入。专项报告按它画“等你”：只有 `open` 的题算还在等。
- 负责人先接手的题（[问题分流](projects.md#专项的问题分流)）`state` 是 `held`：还轮不到你答，网页不算“等你”；转给你后变回 `open`。
- **和问题卡对齐的几样**（v20，v29 改）：每道题带 `context`（卡上题目下面那行“背景”，没有为空串）；`extras` 说“不处理”能不能点（同卡片：话题自己的题，没有任务正停在原生提问上；v29 前还管“先问一句”）；点了“不处理”、话题下一轮还没带走时 `closed_by` 是 `set_aside`、`restorable` 为 true，网页显示“撤销”。v29 去掉了先问一句，也不再推 `asked`。

### 专项条目

- `avatar`（v30）是专项负责人已分配的头像文件名（不带 `.png`），和飞书卡片使用同一份分配，改专项名、排序或刷新页面不换头像。网页用自己的静态图片包按名取图，不接收任意图片路径；旧数据缺少或不认识这个名字时用中性图标。图片与来源说明在 `covey/assets/avatars/`；管家固定使用 `butler.png`。

- `goal`（v11）是负责人用 `project_goal` 写的目标，没写过为空串（开专项时的那句话常常只是安排，不当目标显示）。另带 `started_at`。
- `memory` 每条带 `id`、`said_by`（你说的、它总结的）、`origin`（`{at}`）；`library` 每条带 `kind`（file、link、image、video）、`size`（知道才给）、`topic_number`（知道才给）。
- `checklist`、`milestones`、`decisions`（v40，都可选，记录里没有就不带这个键）是「进度」（现在并进「简报」）的数据：
  - `checklist` 是负责人的目标检查表，每条 `{id, criterion, topic, needs, evidence, gap, state, at}`：`topic` 是交付话题的 key（还没派话题是空串），`needs` 是它等的条目 id，`state` 是 open、done、blocked、dropped 之一，`at` 是条目最后改动的时刻（不是完成时刻）。
  - `milestones` 是负责人记的 milestone 和收尾（finish）两种进展，`decisions` 是决定日志，各取最新 10 条、旧的在前，每条 `{id, at, kind, text}`。
  - 检查表或记录一改，这个专项条目就重推。
- `background`、`actions`、`gaps` 和检查表条目的几个新字段（v41，都可选，没有就不带键，旧网页照旧）是「简报」的数据：
  - `background`：负责人用 `project_goal` 的 `background` 写的背景（至多 300 字的一段话，不是对象）。
  - `actions`：负责人拆的动作，全部都推，含 `dropped` 的（页面不画它们），每个 `{id, title, note, items, topics, state, at}`：`id` 是 `a1`、`a2`……，`title` 至多 30 字，`note` 是负责人写的一句现状（至多 80 字），`items` 是检查表条目 id，`topics` 是话题的 key，`state` 是 `open` 或 `dropped`，`at` 是最后改动的时刻。动作的状态不推，页面按条目和话题现算。
  - `gaps`：没处理的协作缺口，每个 `{id, thread, text, at}`：`id` 是 `g` 加六位（负责人 `close_gaps` 用的那个），`thread` 是汇总方续接的话题的 key（可为空串），`text` 至多 200 字。开了协作才有；缺口一来、一关，这个专项条目就重推（Bridge 看收件箱目录的变动）。
  - `checklist` 的条目多四个可选键，写过才带：`title`（短标题，至多 24 字）、`waiting_on`（`owner`，或空串：负责人说下一步不在主人手上；没带这个键是没写过，页面照缺口文字推断）、`done_at`（条目转成 done 的时刻，不是 0 才带）、`topics`（也参与这一条的话题的 key，至多 6 个，非空才带；页面把 `topic` 和它去重合起来用）。
  - 动作、条目、背景或收件箱里的缺口一变，这个专项条目就重推（`web_sync.rev` 随记录变）。

### 设置条目

另推几条 `settings` 条目。设置条目由取操作的线程（`web-inbox`，每秒一次）单独推：网页改了一项设置，回执之前就推（网页看到“已保存”时读到的已是新值）；`main-thread.json`、工作区列表或脱敏词表一改，下一秒就推；推的线程全量对时也推一次（内容没变 `rev` 不变就不发）。

- **key `memory`**（v37，`app/web_memory.py` 的 `view`）：网页的「记忆」页读它。`COVEY_MEMORY` 开着才有内容，关着推 `{on: false}`（页面收起这一页）。
  - `knowledge`、`learn`：知识条目、候选开没开；`limits`：一条的字数（`text`）、一组最多几条（`group`）、常驻最多几条（`pinned`）、全局和工作区的字数上限（`global`、`workspace`）；`kinds`：知识条目的种类（`value`、`text`）；`default`、`workspaces`：默认工作区和全部工作区的名字（新建时选）。

- **key `asks`**（v34）：“要你处理”的几个数，`{waiting, stopped, stuck}`，和飞书看板、「手上的事」同一个算法（`core/board_read.py` 的 `Asks.counts`：等你含管家、负责人的题和整理专项要你定的建议，停住了含护栏停住的专项，点了“不管了”的不算）。
  - 推的线程每一步看完话题就算一次（`app/web_collect.py` 的 `counted`），变了就紧跟着这一步的话题单独一个请求推（`app/web_sync.py` 的 `push_asks`），所以和话题条目一起变；网页快照接口把它和话题一起给页面。
  - 网页有它就用它的数，没有（旧 Covey，或这几个数不全是非负整数）时照旧按条目自己数。比 v34 旧的网页拒收这个 key 时只记日志（第一次和每第十次），同样的数等下一次全量对时再试，不耽误话题。
- **key `upgrade`**（v39，`app/self_upgrade.py` 的 `view`）：网页的「版本与更新」读它，见[版本与更新](#版本与更新)。只有这台 Covey 配了升级器（数据根里有 `upgrade.json`）才推，`ops` 里也才有 `upgrade`；没配时什么都不推，网页不画这一块。
  - `live`：Bridge 现在跑的 release；`latest`：升级会部署的 release（没查过、查不到是空串）；`available`：升级会换东西（Bridge，或升级会更新、还不是这一版的网页）且没在升级；`bridge`：Bridge 会换。
  - `web`：`{kind, current, manual}`，`kind` 是网页的部署方式（自托管是 `selfhost`，部署到全栈应用平台的是安装器给的另一个值，核心只照着转给网页）；`current` 网页已是 `latest` 的；`manual` 网页不是部署脚本建的，升级不动它（网页上说照部署时的办法更新）。没有网页工作台时是 null。
  - `count`：新提交数（两个库合计，不含测试地图这类）；`changes`：最新的至多 20 个 `{repo, sha, subject, at}`，新的在前（`repo` 是 `covey` 或扩展的库名，`at` 秒）。
  - `checked_at`（秒，没查过是 0）、`checking`、`error`（上次查没成功的原因，成功是空串，旧的结果照留）、`blocked`（现在不能升级的原因，比如检出有没提交的改动；能升级是空串）。
  - `running`：在升级时 `{op_id, started_at, log}`，否则 null。`last`：上一次从网页点的升级 `{state, message, at, release, log, tail}`，`state` 是 `done`（Bridge 和网页都好了）、`partial`（Bridge 升好了、网页没更新上）、`failed`；`tail` 是升级输出的最后几行。没有是 null。
  - 单独一个请求推：查完、升级开始和结束（两个文件和升级进程变了，推的线程每一步看几个 stat）、全量对时、`upgrade` 操作回执之前。比 v39 旧的网页拒收这个 key 时只记日志。
- **key `quota`**（v42，`app/web_quota.py` 的 `view`）：网页的「账号与额度」读它，见[账号与额度](#账号与额度)。有额度快照（`<状态目录>/quota/`）才推；来源都没了（关了 `COVEY_QUOTA`、删了配置）就推一次 `sources: []`，网页收起这一页。`ops` 里有 `quota_refresh`（没有可读的来源时没有）。
  - `sources[]`：每个来源 `{id, kind, title, link?, collected_at, ttl, stale_after, read_at, failing, usable, total, next_available_at, low, dry, expand, relogin[], accounts[]}`。agy 的两份模型组快照（`agy.gemini`、`agy.3p`）并成一个来源 `agy`；别的来源一份一个。`failing`：上次读没成功，数字是更早的；`low`：这个来源整体见底（能用的号每个都有一个窗口剩不到 20%，或者一个都不能用）；`dry`：一个能用的号都没有、有的会自己恢复（`next_available_at` 是最早恢复时刻）；`expand`：网页默认展开（agy，或外接来源里有号要重新登录、用完）。`relogin`：要重新登录的号的显示名。
  - `accounts[]`：`{name, login?, state, available_at, pools[]}`。`login` 是 agy 这个号登录的 Google 邮箱（从它自己的 `cli.log` 读，快照格式的 `accounts[].login`；**唯一不脱敏的文字**，其余文字照旧过白名单）。`pools[]`：`{key, label, active, state, available_at, windows[]}`，agy 一个号一份额度，只列这个号近 7 天跑过的模型池（`turns.jsonl` 的 group，没跑过就取任何号跑过的，再没有就是 Gemini），别的来源一个号一个池（`key`、`label` 是空串）；`windows[]`：`{kind, label, left, resets_at?, checked_at?, ceiling?}`，`left` 是剩下的比例（读不到是 null，不是 0）。
  - `relogin[]`：`{source, name}`，所有要重新登录的号。`read_at`：最近一次读的时刻。`refresh`：`{at, busy, cooldown}`，页面上最近一次「刷新」开始的时刻、读完没有、冷却秒数（300）。`at`：这份条目生成的时刻，不算进 `rev`。
  - 页面自己算和时间有关的：`checked_at` 比 `stale_after` 早的数字变灰，窗口 `resets_at` 过了而读数在它之前就当读不到。
  - 单独一个请求推：快照文件和 `refresh.json` 变了（推的线程每一步看几个 stat）、全量对时、`quota_refresh` 回执之前。比 v42 旧的网页拒收这个 key 时只记日志。
### 网页发回的操作

`web-inbox` 线程 GET `/sync/inbox?after=<seq>&wait=8`（取到新操作就立刻再取一次）。认 `wait` 的网页（回的 JSON 带 `"waited": true`，见[更快的取数](#更快的取数可选参数)）没有新操作时把请求挂住，等到有了再回，Covey 拿到回音马上再问；不认的旧网页马上回，Covey 照旧隔 `poll_seconds`（默认 0.5 秒）再问。

- **先记账再做**：先把 seq 和 op_id 记进 `<state>/web/inbox.json`，再执行，按 op_id 去重。重启后也一样：记了没记结果的算“结果不确定”，回 failed，不重发。
- **车道**：每条操作交给它的车道做：同一个话题（或专项）的按先后一条条做，不同话题的同时做，没有话题的（设置、开新话题、整理、记忆）走同一条。一条卡在网络盘上只挡住它自己的话题。取操作的这一步最多等 5 秒，没做完的在车道里接着做，做完自己回执；之后再取到这条（网页上它还是 new），只要还在做就跳过，不当成“结果不确定”回 failed（那样网页会说“没办成”，其实可能已经办成）。
- **先回执、后补做**：一条做完马上 POST `/sync/ack`，不等别的。设置、开新话题、整理建议和记忆类操作回执之前先推设置、整理和记忆（网页看到“已保存”时读到的已是新值）。操作里留到回执之后的事（`app/card_lanes.py` 的 `after_ack`：答题之后的新一轮和它的任务卡、提示，和飞书里点卡片时一样）在回执之后、同一条车道里接着做；补做时出错写日志，问题卡上照旧写“送达状态未确认”，不重发。
- **日志**：每条操作一行 `web op <kind> seq=… wait=…ms queue=…ms run=…ms push=…ms ack=…ms`（不含内容）：`wait` 是网页写下这条到 Covey 取到（两边的钟）、`queue` 是在车道里排队、`run` 是执行、`push` 是回执前推设置、`ack` 是回执。

数据约定的字段不变，不加版本号。话题、专项必须属于主人的私聊；不认识的、已结束的回 failed 并写原因，网页按 op_id 显示。

| 操作 | 做什么 |

| `say` | 作为你的话进这个话题，见下 |
| `answer` | 交给问题自己的提交路径（`answer_fields`）：没有选项的题收 `answers` 里写的文字，不是选项原文的文字也当作写的回答（同卡上的回答框），`{"skip": true}` 是这道题“不回答此题”（v20）。带了 `note`（补充说明）时没写进 `answers` 的题算不回答，`answers` 可以为空或不带：同卡上的“提交回答”（v29）；没带 `note` 时每题都要答。`skip` 为 true 是只交补充说明（每题不回答，写了的答案也不算），`note` 必填；v29 前的网页发的 `ask`（“先问一句”）按它处理。`aside` 为 true 是“不处理”，`restore` 为 true 是它的“撤销”，走卡片同一处。管家自己的问题只能在飞书里答。问题已经不在等你时：和已存的回答一样是 `done`（多点了一次，没有再发）；否则 `failed`，消息说清是谁、怎么处理掉的（你在网页或飞书答过、负责人替你答了、后来的问题把它收起、每日维护关掉、话题停了或换了配置）和现在怎么办（`app/web_pairing.py` 的 `settled_words`） |
| `seen` | 把话题最新的结果记为看过，同在飞书里读到它；已经看过的回 done 且不写文件；管家回 done |
| `stop` | 停这个话题，见下 |

| `tidy_decide`（v16） | `proposal` 是提议 id，`choice` 是 `ok` 或 `decline`：走那张卡自己的点击，卡原地重画成一样的结果；已经定过的回 failed |

**`say`**：

- 话题有任务在跑就是补充，没在跑就开下一轮（消息 id `web-<op_id>`）。
- 话题在等你答题时，和在飞书话题里发一句话一样：只有一道题在等时这句话就是回答；几道题在等、或题还在负责人手上时拒绝，题不会因此关掉。
- `topic_key` 是管家时，当作你在私聊顶层发了这句话，走和飞书消息同一个入口（准入、去重、扩展、管家），管家照常直接答、开话题、交给专项。管家没开时回 failed，不会变成一个新话题。`web-<op_id>` 不是飞书里的消息：这一轮的回复不引用它、不加表情，作为私聊里新的顶层消息发出。
- `topic_key` 是负责人时，等于引用专项卡回复：负责人在跑就作为补充，没在跑就开它的下一轮；专项已结束、`COVEY_PROJECTS=0` 时回 failed。

**`say` 带附件**（v21）：`payload.files` 是 `[{id, name, mime, size}]`，有附件时 `text` 可以为空。

- 网页先把文件分段传进自己的库：`POST /api/uploads`（`{name, mime, size}`，回 `{id}`）、`POST /api/uploads/:id/parts`（`{n, data}`，每段原始字节不超过 512 KiB；v44 的服务端在 `POST /api/uploads` 的响应里回 `part_bytes`，默认 8mb 时 4 MiB，网页照它切，最后一段可以短，没有 `part_bytes` 或段数对不上照 512 KiB 切，`web/client/src/cv/uploadParts.ts`）、`POST /api/uploads/:id/done`。单个不超过 20 MB，一句最多 9 个，7 天后过期。
- Covey 执行 `say` 时经开放接口取回：`GET /sync/upload?id=<id>`（`{id, name, mime, size, parts, done}`，没有、过期、没传完是 404）、`GET /sync/upload/part?id=<id>&n=<n>`（`{n, data}`）。存进话题的 `incoming_media/`（文件名 `web-<id 前 16 位>-<净化过的原名>`），按飞书附件的格式列在话说完之后（`app/web_files.py`）：图片是“图片 N”并作为图片交给模型，其余是“文件 N（原名）”。
- 有一个取不到（过期、没传完、比说的大、超过 20 MB）整条 `say` 回 failed，写明哪个、为什么，不发半截。
- 这一轮推回网页时，图片照 v19 的 `images` 显示，正文里的附件块是“附件：图片 N 张”。开新话题（`launch`）也能带，见下（v25）。

**`switch`**（v21）：`topic_key`，`payload` 同 `launch` 去掉 `text`（`model`、`effort`、`work_mode`、`workspace`、`run_mode`、`redaction`）。

- 只认主人；管家回 failed（“管家的配置在设置的「配置」里改”）。换配置换不了机器：带了 `device` 且不是话题现在的设备时回 failed（`DEVICE_FIXED`），不带或空串不算改。模型这几项的校验同 `launch`；工作区或运行方式和现在一样就不动，不一样时同换配置卡的检查（设备、声明的 Harness）。
- `topic_key` 是专项负责人时（v36，`app/web_switch.py`）：模型要能当负责人（`bridge_tools`），否则 failed；工作区和运行方式必须是现在的，否则 failed“负责人的工作区和运行方式不能换”；负责人有一轮在排队或在做时 failed“负责人还有一轮在排队或在做，等它做完再换配置”。换成了：回复专项卡出一条“🔁 已换配置 · 专项「名」的负责人”，回执以“负责人下一轮起由新会话接着做”结尾。
- 同换配置卡的“确认更换”（`app/binding.py` 的 `switch_topic`）：有任务在排队或在做、什么都没变时回 failed；要新建独立 worktree 的回 failed“新建独立 worktree 要在飞书的换配置卡上做”（建 worktree 要几十秒，收操作的线程不等）。
- 换成了：飞书话题里出一条和换配置卡一样的“🔁 已换配置”，模型选择记进这个私聊的用量；回执“已换配置：<旧> → <新>；工作区 a → b，下一句话起由新会话接着做”，只改脱敏是“已打开脱敏，会话不变”。

**`recover`**（v33，`app/web_ops.py` 的 `recover`）：`topic_key`，`payload` 是 `{job_id, action}`，`job_id` 是那一轮的任务（一轮条目的 `job_id`），`action` 取 continue、retry、diagnose、split、stop_auto_retry。和飞书任务卡上点同名按钮是同一个调用，在自动重试用的同一个话题上下文里执行（话题、管家、负责人都行）：

- continue、retry：`TaskControls.retry_topic`。结果或问题保存了没发出去的，只重发保存的那份，不跑模型；其余带着检查点开一轮“检查并继续”。自动重试排着时立即重试，排好的那次随后作废，不会两次都跑。回 done，消息是卡片回的那句（“本话题任务已重新入队，任务 #22。”“保存的结果已重新投递……”）。
- diagnose、split：卡片的“看原因”“拆小再试”（`Submission.follow_up_job`），回 done“已开一轮只读排查……（任务 #23）”。
- stop_auto_retry：卡片的“停止自动重试”，回 done“已停止自动重试……”。
- 回 failed、什么都没做的情形：这一步这条记录现在不让做（不在 `failure.actions` 里，也没有排着的自动重试）、话题还有任务在跑或排队、这一轮已经接着做过（`retried_by`：卡上点过、自动重试跑过、网页点了两次）、话题之后换过配置（同飞书点旧卡）、任务或话题不认识、不在主人私聊里。消息说清为什么。
- 开出的那一轮消息 id 是 `recover-<op_id>`，不是 `web-`：和飞书点击一样，它不算主人说的话。

**`project_finish`、`project_stop`**（v34，`app/web_ops.py`）：发件行带 `project_key`，`payload` 是空的。只认主人（`app/access.py` 的 `is_owner`），专项要在主人私聊里。

- `project_stop`：在做的专项（`active`）同专项卡的“停止专项”：停住，原因是“主人停止”（看板上灰色“已停止”，不是红色“停住了”）。护栏停住、停住卡还在等你选的，同停住卡上点“停”（`project_loop.answer_pause`）。然后负责人和各成员话题排着、在跑的任务都请停（`project_clicks.stop_tasks`，停止来源是 `web`），回 done“已停住专项「X」，已请 N 个任务停下……要继续，点「继续」”。已经做完、停住（停住卡也选过了）的回 failed“……没有要停的”；刚被负责人、护栏或卡片改了状态的回 failed，请你刷新再看。
- `project_finish`：先过负责人收尾的两道闸，不过就回 failed、什么都不改，原因原样写出：还有成员话题在做或等你（`project_lead.live_members`，写出是哪几个话题）；目标检查表有没满足的项或没处理的协作缺口（`project_tools.checklist_gate`，去掉只说给负责人的那几步）。过了：护栏停住、停住卡在等你选的，同停住卡上点“收尾”（`answer_pause` 和给负责人的回执 `pause_receipt`）；其余（在做、你停的、收起的）当作你说了话（`owner_spoke`：收起的重新展开）并给负责人一条“主人在网页上选了收尾”的回执，由负责人总结做完了什么、还有什么没做完，再调它自己的 `project_finish`（它的闸照样管着）。回 done“已请负责人收尾专项「X」……”。已经做完或取消的回 failed。

**`memory_edit`**（v37 的写法，没有 `v`）：已下线。旧网页的设置页「记忆」只读，Covey 回 failed“这个页面版本太旧，刷新网页后到「记忆」里改”；改记忆走 v43 的写法。

**`revisit_cancel`**（v35，`app/web_ops.py`）：`topic_key` 是话题，`payload.set_at` 是话题的 `revisit.set_at`（这条预约约下的时刻）。只认主人（`app/access.py` 的 `is_owner`），话题要在主人私聊里。照 `core/revisits.py` 的 `cancel` 取消：时刻对得上才删，换了新预约不误删。回执：办好回 done“已取消定时回看”；已经没有了（回看过、取消过）回 done“这条定时回看已经没有了”；预约已换成新的回 failed“这条定时回看已经换成了新的，没有取消”，页面等下一次推送换上新的；Covey 已经在回看（`running`）回 failed“Covey 已经在回看了，这一次取消不了”。办完 Covey 马上重看这个话题（`Collector.touch`），页面不用等下一轮补扫。

**`memory_undo`**（v34）：`topic_key` 是那一轮的话题，`payload.job_id` 是那一轮的任务号（一轮条目的 `job_id`），`payload.entry_id` 是 `notes` 里那条“记下了”的 `entry_id`。和答案卡上点「不对」是同一个调用（`app/memory_collect.py` 的 `take_back`）：那条记忆作废，任务记录里那条 note 改成 `undone`，答案卡的那几行原地重画；回 done“已撤销：<前 40 字>”。已经撤销过的回 done“这条记忆已经撤销过了”，什么都不改。不是主人、话题里没有这个任务、这一轮没记下这条的回 failed。

**`stop`**：停这个话题在跑的任务，同卡片上的停止。话题在等你答题时，那道题一并收掉（原因 `web_stop`，卡上写“你在网页上停了这个话题”，看板上是“已停止”而不是“停住了”）；只有还没点开始的启动卡时把启动卡收掉；什么都没有时回 failed。

**`launch`**：`payload` 带 `text`（第一行当标题）、`model`（`launch.models` 的 `key`）、`effort`、`work_mode`、`redaction`（`on`/`off`）、`workspace`、`run_mode`。

- 只认主人；校验同启动卡的“开始任务”，不过回 failed 写原因。
- 开法同管家直接开工的话题：私聊顶层一张话题卡，第一轮就是你写的话；这次选择记成这个私聊的“上次开始任务”，下一张启动卡和网页的预选都跟着变。之后每一轮的结论、等你回答的问题和停住也和管家开的话题一样回到私聊顶层（[结论回到顶层](butler.md#结论回到顶层)）。
- 独立 worktree 只有启动卡能建：这样的话题出一张按网页选择填好的启动卡，在飞书话题里点开始任务。
- 每一步记在 `<state>/web/launches/<op_id>.json`，同一条操作再来不会开第二个话题。回执“已开 T23「标题」：直接开工”，网页按 T 号跳过去。
- 带附件（v25）：`payload.files` 同 `say`。开话题之前先全部取回，放在 `<state>/web/launches/<op_id>.files/`，有一个取不到就回 failed、什么都不开；开好后搬进新话题的 `incoming_media/`，第一轮的话按飞书附件的格式列出它们。

**`settings`**：只认主人（`app/access.py` 的 `is_owner`），写设置走和卡片同一处，回执也是卡片那句。`payload.what`：

- `row`：`kind` 是卡片那一行的 kind、`option` 是选项值。也收管家的脱敏和“私聊顶层的消息”（`kind` 为 MODE；改成“每条直接开一个话题”要带 `confirm: true`）。
- `untrust`（`key`）：已下线（v24），回 failed“记住的工作区已下线：管家开的话题一律直接开工”。
- `note`（`workspace`、`note`）：工作区用途，空串清掉。
- `redaction`（`name`、`on`）：脱敏的“不区分大小写”“回复还原”。
- `terms`（`add`、`remove` 是原词列表）：一次先删后加；删的按“不区分大小写”开关比、不在的跳过，加的已在词表里跳过；有一个加不进（太短、太长、控制字符、`=>`、超 1000 个）就一个都不存。回执只说个数，不写原词（回执存在网页的发件箱里）。
- `group`（`group`、`on`）：群的停用与启用。
- `free`（`group`、`mode`）：免@ 只能改成 `""`（关闭）或 `owner`（只有你），代答群不能免@。“你和选中的人”“群里所有人”留在飞书改。
- `workspace_add`（`path`，绝对路径或“设备别名:路径”，查目录最多 5 秒）、`workspace_remove`（`workspace`，只是不再登记，目录和已开的话题不动；默认的那个不能移除）、`workspace_prune`（移除目录确认不存在的）。目录浏览不做。
- `node_add`（`name`、`title`、`ssh`）：只能经 ssh（不用 ssh 的方式要显示一次性口令，口令不进网页的库）。ssh 在单独的线程里跑，最长 90 秒，结果写进 `<state>/web/node-joins.json`。`node_remove`（`alias`）：同卡片，本机不能移除。`refresh`：什么都不改，只让设置马上重推。
- `proxy`（`op`）：`enable`、`disable`、`row`（`kind`、`option`）、`pause`、`resume`、`remove`（`contact`），和代答卡同一处。按名字查找添加、去登录留在飞书。
- 其余回 failed“这一项网页上只读”。

### 版本与更新

网页上点一下就把这台 Covey 升到最新：Bridge 和网页工作台一起（只升 Bridge 时网页还是旧的，网页上的新功能看不到）。代码在 `app/self_upgrade.py`，网页读 `settings` 的 `upgrade` 条目。

- **谁会升级**：核心不知道一个部署该怎么升级（带扩展的 release 由扩展的安装器升级，见 [deploy.md 升级与回滚](deploy.md#升级与回滚)），由能升级它的安装器在数据根写 `upgrade.json`：`{"by", "status": [命令], "run": [命令]}`，两个命令的第一个词都是绝对路径。`status` 只查不改（取两个库的新提交，不拉、不换），最后一行输出 `{live, latest, bridge, web, count, changes, blocked}`；`run` 升级（拉代码、预检、换 Bridge、更新网页），退出码 0 全好、4 Bridge 好了网页没好、3 另一个部署在跑、别的是没做成。covey-internal 的 `./install` 装好、`./install upgrade` 升级好后写它（`./install status --json`、`./install upgrade`）。**没有这个文件时什么都不做**：不起线程、`ops` 里没有 `upgrade`、不推条目，只装核心的部署和以前一样。
- **查新版本**：有升级器时多一个 `web-upgrade` 线程，Bridge 起来 2 分钟后查一次，之后每 6 小时一次，网页点了升级、升级结束 30 秒后再查一次（网页不再提示刚装上的版本）；网页上的「检查更新」（`upgrade` 的 `check`）马上查。一次最多 180 秒、同时只查一次，升级在跑时不查（它在拉检出）。结果在 `<状态目录>/upgrade/status.json`，查不成时写 `error`、旧的结果照留。
- **升级**（`upgrade` 的 `run`）：先查一次；已经是最新、`blocked` 不空、已经在升级时回 failed 并写原因。否则在自己的会话里起升级进程（`start_new_session`，和任务进程一样，Bridge 重启停不到它）：外面包一层，输出写进 `<数据根>/deploy-runs/<时间>-page/upgrade.log`，结束时把退出码、结束时间和最后几行写进 `<状态目录>/upgrade/run.json`。回执马上回“开始升级…”。升级里的部署会重启 Bridge，在跑的任务不中断；新的 Bridge 从 `run.json` 读进度和结果，推给网页。升级进程不见了又没写结果时，网页说“结果不确定，看日志”。
- 这条操作走自己的车道，查的这一两分钟不挡设置、开新话题这些。
- 只有核心、在 git 检出里 `./install` 装的部署，安装器和 `scripts/upgrade.sh` 写一份用 `scripts/upgrade.sh --status --json` 和 `scripts/upgrade.sh` 的 `upgrade.json`（`by` 是 `covey`；不覆盖扩展写的），自托管网页跟着升级，见 [deploy.md 日常升级](deploy.md#日常升级)。
- 网页上的查和升级，与[定时自动升级](deploy.md#定时自动升级)（`COVEY_AUTO_UPGRADE`，`app/auto_upgrade.py`）用的是同一个升级器（`self_upgrade.shared`），同时只查一次；定时升级起的那次在 `run.json` 里 `by` 是 `auto`，日志在 `deploy-runs/<时间>-auto/`。

### 账号与额度

数据约定 v42。代码在 `app/web_quota.py`，快照的格式和来源见 [quota.md](quota.md)。页面只读 `settings` 的 `quota` 条目，只发一种操作 `quota_refresh`。

- **页面**：照挑定的样张。标题行右边是最近一次读的时刻和「刷新」；有号要重新登录时下面一行红条（只有事实，没有按钮）；再下面一张表，列是账号、5 小时剩余、周剩余。`5h` 和 `7d` 以外的窗口（`day`、`other`）表里不画；同一种窗口有几个（网关的“Fable 周”和“周”）取剩得最少的那个。
- **颜色和字**：剩余不到 20% 红色；用完写“用完”，后面写恢复时刻（“11月27日 03:30 恢复”）；标题行右边的读数时刻、侧栏那一行的恢复时刻也这样写；读不到写“—”、不画条；读数时刻比 `stale_after` 早的数字灰色（悬停看读数时刻），比 `ttl` 的两倍还旧的来源整份写“—”。
- **侧栏**：只在某个来源 `low`（见底）或有号要重新登录时，侧栏搜索框下多一行，点了到这一页；否则不出现。侧栏收起成窄条时，同样的条件下同一位置是一个带红点的小图标（悬停是那一行的字，点了也到这一页），不占底部「设置」和深浅色图标的位置。设置里的「账号与额度」标签只在 `ops` 有 `quota_refresh`、条目里有来源时出现。
- **刷新**：Bridge 收到后先看 `<状态目录>/quota/refresh.json`：5 分钟内刚开始过一次就回“刚查过（HH:MM）…”，什么都不重读（回执之前仍重新推一次条目）；否则记下开始时刻，在 `quota-refresh` 线程里 `quota_sources.refresh(force=True)`、`probe_accounts(which="all")`、再写 agy 的快照，回执立刻回“开始重新读取…”，读完 `refresh.json` 记结束时刻、条目的 `refresh.busy` 变回 false。读的时候页面按钮锁着。同一个 Covey 只有一份冷却。agy 的 `/usage` 是唯一会去问备用号的，所以只在主人点的时候问。
- **飞书提醒**（`app/quota_notice.py`，`quota_watch` 线程每分钟看一次）：一个来源一个能用的号都没有了（带最早恢复时刻）、有号要重新登录，两种，各说一次，一两句加「去网页看」的链接（`page_url` 加 `/settings/quota`）。说过的记在 `<状态目录>/quota/notices.json`，那件事不成立了就忘掉，再出现算新的；一个状态目录的第一次只记下现状、不说；夜里按 `COVEY_QUIET_HOURS` 不发也不记，早上把还成立的合成一条发。

### 数据约定 v43：记忆中心与仓库

记忆那一半 v45 做了减法（体检、下一轮预览、导入、名额条、五个页签都去掉了），见[数据约定 v45](#数据约定-v45记忆一页式)；下面是 v43 当时的样子。契约冻结稿在改造计划的 `web-contract-v43.md`。v42 已被「账号与额度」占用，所以记忆中心与仓库记作 v43。A0 只加类型和服务端校验，不改现有行为：旧 Covey 不推新键，网页和服务端与 v42 完全相同。类型和常量在 `web/shared/api.interface.ts`，校验在 `web/server/modules/workbench/workbench.memory-edit.ts`，样例在 `tests/golden/web_memory_v43.json`（合成数据，Bridge 侧推送要能逐键对上它的形状），单测 `npm run test:memv43`。

- **设置键**：`SETTINGS_KEYS` 仍是原来 7 个（含 `quota`），不动。新增 `MEMORY_KEY_RE`，`isSettingsKey` 在 7 个键之外也认它。键共 6 种：`memory:index`（小键，侧栏角标只轮询它：总数、待审核数、各范围摘要与每键 rev、体检非 0 项、导入摘要、⌘K 用的标题表）、`memory:global`（全局条目、待审核列表、最近 100 条变更记录）、`memory:topics`（近 30 天有记忆的话题的话题范围条目）、`memory:p:<专项 id>`（专项 id 是 `[0-9a-z]{6,32}`）、`memory:import:<页>`（导入候选，每页 ≤200 条，页号 0~999）、`memory:previews`（下一轮预览：最近 20 个话题加“新的普通话题”）。旧键 `memory`（v37 形状）继续推给旧网页。
- **大小和推送**：最长键 41 字符，`sync_state.name` 是 `varchar(64)`，放得下；每键的值 ≤256 KB，带 `rev`（内容哈希），Bridge 侧 rev 没变不推；用量数字不进条目，只进 `memory:index` 的汇总。专项归档、导入页缩减时，Bridge 对不再存在的键发 `SyncDeleted{type:'settings', key}`，服务端只用 `isSettingsKey` 放行。Bridge 任何记忆写入 touch 一个哨兵 `<状态目录>/memory/.rev`，`web_memory.stamps()` 只 stat 它。
- **Bridge 侧推送**（`app/web_memory.py` 的 `Center`、`app/web_sync.py` 的 `push_memory_center`）：数据都从统一存储 `core/memstore.py` 读。pass 线程每步只 stat 哨兵 `memory/.rev`（第一次看时没有就建上，旧存储从此也会 touch 它）；哨兵动了、网页改了记忆（回执前）、或全量补扫时距上次构建满 5 分钟，才重建各键。数据键先推、`memory:index` 最后推（它的 `revs` 指向前面的键），和旧键 `memory` 分开请求，旧网页不受影响。规矩按范围配额（全局 15 条/1,200 字、专项 10 条/1,000 字、话题 5 条/400 字）判 `carried_next`，超额的只标 `over_cap`、不丢；决定的 `in_progress` 现在按“仍是 active”判，M2 合入后以 `app/memory_turn.py` 为准；`memory:previews` 和体检在 M2 有 `memory_turn.preview`、`memory_review.health` 时用它们，没有时 Bridge 自己给基线（预览只带规矩和在办决定，资料留给检索）。Harness 自带记忆的扫描最多 10 分钟一次。服务端拒收新键（旧服务端）时记日志、隔 1 分钟起加倍重试（最长 30 分钟）。记忆关掉时推一份 `on: false` 的 index 并撤回其余键。
- **`memory_edit` v43 在 Bridge 的落点**（`web_memory.edit_v43`）：add→`memstore.add`/`add_decision`（`by=web`、`said=owner`），edit→`change`，move、promote、archive、restore、void 同名，accept、reject、keep_*、*_all→`core/memory_review.py` 的 `decide`/`decide_all`（M2 合入前走 `web_memory` 的基线：采纳写成主人定的条目、迁移护栏项确认或降成资料、整理组收起、冲突三选一），import→`harness_memory.take`，ignore→`harness_memory.ignore`，undo→`memstore.undo`（基线处理过的待审核会回到待审核）。操作号写成 `w-<op_id>` 当撤销号，网页从 `memory:global.log` 里按条目找到它。
- **类型**：`MemoryEntry`（`code` 短码 R/D/N 加 4~6 位 base32；`kind` rule|decision|note；`scope` global|project|topic；`status` active|pending|done|archived|void；`by` 来源；`rev` 是 `memory_edit` 的乐观锁 base）、`MemoryReviewItem`（`type` 8 种：learn、candidate、lead、import、conflict、tidy、class3、migrate）、`MemoryHealth`（只放非 0 项，全 0 是 `{}`）、`MemoryLogItem`（带 `undo_token`）、`MemoryIndex`、`MemoryGlobalData`、`MemoryProjectData`、`MemoryTopicsData`、`MemoryImportPage`、`MemoryPreviewsData`。页签 `MEMORY_TABS` 是 review、rules、decisions、notes、log；「导入」是顶栏入口，不是页签。

### 更快的取数（可选参数）

数据约定 v38。下面都是请求里可选的参数和响应里可选的字段：不带参数的旧调用、认不得新字段的旧页面，行为和以前完全一样；新网页遇到不认参数的旧服务端，退回整份、马上返回的老办法。

- **取件挂着等**：`GET /sync/inbox?after=<seq>&wait=<秒>`。`wait` 上限 10，没有新操作时服务端每约 200 毫秒查一次库，最多等 `wait` 秒，有了马上返回；同一个进程里网页 `POST /api/outbox` 写入会提前叫醒它（多实例时靠查库兜底），Covey 断开了就不再等。带了 `wait` 的响应多一个 `"waited": true`（不管这次有没有真的等），Covey 靠它认出服务端是新的；不带 `wait` 的响应没有这个字段，和以前一样。旧服务端不认 `wait`、马上返回且没有 `waited`，Covey 照 0.5 秒一取的老办法。
- **快照增量**：`GET /api/snapshot?since=<cursor>`。每次响应都带 `cursor`（这次查询开始时数据库的时间往前留 5 秒）。带了 `since` 时 `topics` 只有这个游标之后变过的话题（话题行或它的轮次的 `_updated_at` 晚于它；快照里的最新一轮、在跑状态都来自轮次表），另有 `keys`（现在所有话题的 key，按 `updated_at` 倒序，管家只留最新那个；不在里面的话题已经没了）和 `"partial": true`；`projects`、`questions`、`asks` 照旧整份，专项卡上的话题计数也照所有话题算。网页按 key 并进上一份。整份只在要校准时取（`web/client/src/cv/snapshotMerge.ts` 的 `planSnapshot`，单测 `web/scripts/calib.test.mjs`，v44）：第一次（缓存里没有，或服务端从没给过游标）；增量并不进去（keys 里有缓存和响应都没有的话题，当场再取一份整份）；上一次取快照失败后的第一次成功（断线重连、网关 429、5xx 之后）；浏览器报网络恢复（`online`）；页面在后台待满 30 秒又切回前台。另留 30 分钟一次的长兜底（`FULL_BACKSTOP_MS`），兜住游标照不到的边角（同一个 key 删了又建回、改了数据没动 `_updated_at`），要去掉就改成 `Infinity`。其余时候每秒一次都是增量，操作回执后的那次快照也是增量。（v44 之前写的是“每分钟也回整份一次兜底”，但每次增量合并后都刷新了上次整份的时刻，前台一直开着时其实不触发；真正取整份的是首屏、断档和后台待了 60 秒以上回来的那次。）没有 `partial` 就是整份，直接替换；旧服务端不认 `since`、响应里没有 `cursor`，网页永远取整份。
- **话题轮次增量**：`GET /api/topics/:key/turns?after=<seq>&since=<cursor>`。`after` 照旧：只回这个 seq 之后的和在跑的（网页从最近还在跑、在等的那一轮的前一轮算起，`use-workbench.ts` 的 `afterOf`）。每次响应都带 `cursor`（同快照：数据库的时间往前留 5 秒），网页下次把它当 `since` 带回来，这之后改过的轮次也一起回来、按 key 并进上一份：排在在跑那一轮前面、后来才补全的行（你那一行的图后传上来、编辑并进原消息）不用刷新页面就换成新的。只按 `after` 取时，那一行先取到没图的版本以后就一直停在“附件：图片 N 张”，要刷新才出图。`since` 不合法当没带；旧服务端不认 `since`、不带 `cursor`，和以前一样。
- **回执挂着等**：`GET /api/outbox/:opId?wait=<秒>`。`wait` 上限 8，这条发件还是 `new` 时服务端每约 250 毫秒查一次库（同进程里 Covey 的回执会提前叫醒），不是 `new` 了马上返回；没有这条发件仍是 404。旧服务端不认 `wait`、马上返回，网页照 250 毫秒起的间隔再问。

**标签页在后台**：定时取数（快照 1 秒、话题轮次 1–2 秒、大厅 2 秒，以及统计、设置、记忆角标等）在标签页不可见时本来就停（react-query 的 `refetchIntervalInBackground` 默认关，平台的 QueryProvider 关了 `refetchOnWindowFocus`）。切回前台时马上取一次快照、开着的话题轮次和大厅（`hooks/use-workbench.ts` 的 `watchPage`，监听只挂一份；取数不取消在途请求），在后台待满 30 秒的这次快照取整份校准，不满取增量。发出的操作在后台照样等回执、回执后照样取数。

网页上每个操作发出去以后只有一个跟踪器等结果（`web/client/src/cv/opTrack.ts`、`sendOp.ts`）：问回执，回执一到取这个话题的轮次（大厅取大厅）和快照各一次，之后约 3 秒内每 0.5 秒只取这个话题的轮次，直到看到预期的新状态；取数一律“上一次还没回来就跳过”，不取消在途的请求。问题卡交过以后到新状态推来之前一直锁着、写“已执行，等页面更新”：锁不锁看这个话题的发件行里这道题最新的那条 answer（在等 Covey 或办成了就锁；最新的是撤销不处理或没办成就不锁，`opTrack.ts` 的 `priorAnswer`），所以刷新、换页面回来、另一个窗口打开都不会让人再点一次。

**乐观更新**（v44，`opTrack.ts` 的 `optimisticTopic`、`sendOp.ts` 的 `trackOp`）：写进发件箱以后、Covey 回执之前，先在快照缓存里改掉这个话题，只做网页自己就知道新状态的两种：`seen`（记为看过：`unseen` 置 false，侧栏、看板马上变）和 `dismiss`（不管了：从看板拿掉）。回执没办成、或等满一分钟没回音，缓存里这个话题还是放进去的那份就改回去；这期间 Covey 推来了它的新状态或取过整份，以推来的为准。`seen` 以前发了就不管，现在也交给跟踪器（`sendQuiet`：回执后不取数，服务端挂着等回执，一般问一两次）。其余操作不改缓存：`say` 有输入框自己的回显，`answer` 有题面的锁，`stop`、`recover`、`launch` 的新状态只有 Covey 知道。Covey 这边回执之后只单独推受影响的那个话题（`web-touch`），网页回执后也只取这个话题的轮次（大厅取大厅）和一份增量快照。

### 数据约定 v44：上限、文件存储与连接保护

按对全栈应用平台的实测（单实例 0.5 核、1 GiB 内存，Node 却设了 `--max-old-space-size=3072`；请求体平台硬顶 12 MB、框架默认只收 1mb；开放接口每个密钥约 10 次/秒；连接池 7 条）做的四件事。新字段都可选，旧 Covey、旧网页照旧。

- **请求体上限**：`web/server/main.ts` 把 `bodyLimit` 交给平台的 `configureApp`：环境变量 `BODY_SIZE_LIMIT` 认得出就用它，没设是 `8mb`（平台的硬顶是 12 MB；`workbench.limits.ts`；自托管入口用同一个数）。由它推出一张图（`image_bytes`）和附件一段（`part_bytes`）各最多多少：base64 后整个请求还在上限里，各封顶 4 MiB；上限不超过 1 MiB 时和以前一样（760 KiB、512 KiB）。`/sync/upsert` 和 `/sync/images/have` 的响应带 `limits: {body_bytes, image_bytes, store, heap_limit_mb, rss_mb, mem_limit_mb}`，Covey 照它放大一批和一张图（见[推](#推)）；后三个是 V8 堆上限、此刻常驻、容器上限（MB），看 `NODE_OPTIONS` 的 `--max-old-space-size` 生效没有。
- **图片和附件放平台的文件存储**（`workbench.blobs.ts`）：新的图片（缩略图、大图各一份）和附件的每段，字节经平台的 `FileService` 存进应用的文件存储（路径 `covey/images/<id>-<thumb|full>.<ext>`、`covey/uploads/<id>/<n>.part`，id 是内容哈希或随机编号），`images` 表只存 `thumb_path`、`full_path`，`upload_parts` 只存 `path`、`bytes`。鉴权和以前一样：不给页面发直链，页面仍只经 `/api/images/:id`（要登录、只有主人）取图，Covey 仍只经 `/sync/upload/part` 取附件；服务端用短时签名地址（签 10 分钟、进程里用 8 分钟，不出进程、不进库）自己去取字节再回出去。文件存储用不了（自托管没有它、平台报错、库里还没有路径列）时照旧存 bytea，连着失败 3 次歇 10 分钟再试，第一次失败记一行日志；`limits.store` 是 `file` 还是 `db`。老的 bytea 行照常读；有路径也有 bytea 的先读文件存储，取不到再读 bytea。
  - 已有的库要先加列：部署脚本目录下的 `migrations/20261127-t876-blobs.sql`（见 [web/README.md 的「部署」](../web/README.md#部署)）（只加列和两个 `_updated_at` 索引、`upload_parts.data` 改可空，不动数据；多环境应用在 dev 执行再 `+db-env-migrate` 到 online）。没加列的库上新网页自动退回 bytea。新建的库 `schema.sql` 里已经有。
  - **历史回迁**（不自动跑）：`POST /openapi/sync/blobs/backfill {limit≤50, drop}`。`drop` 不是 true 时只复制：把还只在 bytea 里的图存进文件存储、写上路径，bytea 留着（不丢，先读文件存储、取不到读 bytea）；`drop: true` 才在读回核对大小以后清掉 bytea。回 `{copied, dropped, left, errors, store}`。开放接口密钥按路由放行的（不是放开全部 `/openapi/**`），要另外放行这条路由才调得到，Covey 自己从不调它。清 bytea 是改线上已有数据，先备份、问过主人再跑。
  - **冷热清理**：图片消息之后 90 天过期、附件传完 7 天过期，和以前一样每小时跟着上传清一次；现在先删文件存储里的对象，删掉了才删行（删不掉的行留到下一轮，不留下没人引用的文件）。
- **内存水位**（`workbench.guard.ts` 的 `MemoryGuard`）：常驻占容器上限（读不到用堆上限）70% 以上是 high：取件、回执不再挂着等（马上按库里的回），新图片和新附件回 503 让对方稍后重传；85% 以上是 critical：页面的整份快照、统计、报告、搜索、取图、传附件也回 503（`Retry-After: 5`），增量快照、轮次、发件、回执和 Covey 的推送照常。水位变了记一行 `[workbench] memory …`。平台允许时另在应用环境变量里设 `NODE_OPTIONS=--max-old-space-size=640`，堆先回收、不等被 cgroup 杀；生效没有看 `limits.heap_limit_mb`。
- **连接池**（`workbench.guard.ts` 的 `Gate`、`gated`）：每条库查询先过闸门，按车道限并发：页面（`/api`）4 条、Covey（`/openapi`）2 条，加起来 6 条，比平台包的 7 条池少一条，谁都占不满、Covey 的推送和回执不会排在几个标签页的整份快照后面；排队每条车道最多 400 个、最久 15 秒，超了回 503。车道由 workbench 模块的中间件按路径设（AsyncLocalStorage）。Covey 一批里同时写 4 条（以前 25 条）。挂着等的请求睡着时不占连接；每条通道各自限挂起数（取件 4、回执 16）；同一时刻挂着等回执的合成一条 `op_id in (...)` 查询（`Batcher`）。`topics`、`turns` 加了 `_updated_at` 索引，快照增量每秒按它找变过的话题，不再全表扫轮次。

### 数据约定 v45：记忆一页式

网页「记忆」（`/memory`）从 v43 的五个页签改成一页，推的键和 `memory_edit` 跟着做减法，不加新键、新动作、新字段（决定在原有的 `origin.topic_number` 里补上问的话题的 T 号）。代码在 `app/web_memory.py`（`Center`、`keys`、`edit_v43`）和 `web/client/src/cv/MemoryCenter.tsx`（纯函数 `memoryCenter.ts`，单测 `npm run test:memcenter`），样例仍是 `tests/golden/web_memory_v43.json`（已改成 v45 的形状）。

- **推的键**：`memory:index`（`version` 是 45；去掉了体检 `health`、导入摘要 `imports`、各范围的名额 `scopes[].rules`）、`memory:global`、`memory:topics`、`memory:p:<专项 id>`。`memory:previews`（下一轮带什么）和 `memory:import:<页>`（导入）不再推，库里旧版推过的由 Bridge 发 `SyncDeleted` 撤掉；`MEMORY_KEY_RE` 仍认这两种，好让撤的那一下通过。
- **条目**：去掉 `carried_next`；超出所在范围名额的规矩照旧带 `over_cap`（下一轮只带标题），页面只在那一组标题后写“N 条只带标题”。决定（`kind` decision）的 `origin.topic_number` 尽量补上：Bridge 按 `origin.topic_key` 读那个话题的 T 号（一次构建里同一个话题只读一次，跨构建记着）。
- **记录**：`memory:global.log` 不再列 Bridge 自己记下的问题卡回答（引用全是 `decision:` 的改动，且撤销号不是网页操作的 `w-` 开头），网页上作废一道题照旧在里面。
- **`memory_edit`**：payload 仍是 `v: 43`，动作少了 `import`、`ignore`，剩 15 个；服务端照 `MEMORY_EDIT_ACTIONS_V43` 校验，旧网页发来这两个会被拒。
- **页面**：第一屏只有标题、搜索框、「＋ 记一条」和分组列表。有待审核时页顶一块（迁移带过来的按专项并成一行）；下面全局一组，再是有规矩的专项（按快照里专项的最近活跃排，只展开前两个），有话题范围的规矩时多一组“话题 · N 条”（每条带 T 号）。组里你定的在前，负责人记的、资料（相关时才带）、已收起折叠；全局组分“每一轮都带”（规矩）和“相关时才带”（资料，管家和负责人看得到，派活时挑给话题，默认展开）两段。规矩、资料按条目的 `kind` 分，标题表 `memory:index.titles` 每行是 `[短码, 标题, ref, kind]`（`kind` 后加的，旧 Covey 只有前三项，网页这时才按短码首字母猜）。点一条就地展开正文、原话、出处话题，能改、换管哪儿、删（5 秒内能撤销），已收起的能放回；页底“记录”（`?view=log`）。搜索在规矩、资料和答过的题里找，答过的题写成“上次你答过：…（T 号 · 日期）”，点开能作废。`/memory?code=<短码>` 打开那一条，`/memory?scope=global|topics|p:<id>` 展开并滚到那一组；旧的 `/memory/<页签>` 照样画这一页。
- **一轮的记忆行**：一轮的 `notes` 多推 `superseded`（收起了）和 `pending`（待审核）两种，网页对话里这两种和“记下了”一样带「不对」（`memory_undo`，同答案卡）。一轮的 `memory.used` 从结束那一轮的检查点 `memory_used` 读（以前读的任务记录字段早就不写了，所以“用到 n 条”一直是 0）。
- **兼容**：新网页遇到 v43 的 Covey，多出来的字段不读，照样画一页；旧网页遇到 v45 的 Covey，体检、预览、导入那几块是空的。

### 协作与三层记忆（契约，开发中）

本节已实现（数据约定 v31），开关 `COVEY_COLLAB`（规则见[多参与者协作](architecture.md#多参与者协作开发中默认关)）。旧网页不认的字段和条目忽略；没带这些字段的操作和 v30 一样。**开关没开时**：不读 `collab/`，不推 `collab` 条目，一轮不带 `collab`，已推过的 `collab` 条目在下一次全量对时删掉；`say` 带了新字段也照单目标处理，要多选或引用协作的回 failed“协作没有打开（COVEY_COLLAB）”，`stop` 带了 `collab` 回 failed，**绝不**退成普通停止（那会停掉汇总方在跑的任务）。

- **`say` 的三个可选字段**：
  - `payload.to`：点到的参与者（管家、负责人、话题的 `key`）的列表，按点的顺序；网页不从正文里的 @ 或 T 号猜收件人。
  - `payload.integrator`：主人选的汇总方，是 `to` 里的一位或当前话题；只在和默认不同时带。
  - `payload.quote`：`{topic_key, seq, collab}`，引用的是哪个话题的哪一轮、属于哪次协作。
  - `payload.room` 为真是大厅发的（`topic_key` 是 `route` 的交付归属：交给管家，归口时是管家），否则是话题页（`topic_key` 是这个话题）。
- **`say` 怎么走**（`app/web_ops.py`，交给谁、谁汇总按 `core/collab.py` 的 `route` 定，和飞书一样；`where` 是 `payload.room` 的真假，话题页的 `here` 是 `topic_key`）：
  - 没有 `to`、没有 `quote.collab`，或 `to` 只有一位且就是 `topic_key`（大厅里只点一位也是）：一字不改，按 `topic_key` 直达，可以是普通话题。
  - 话题页里 `to` 只有一位且不是这个话题，而且开关开着、Bridge 有 `collab` 部件：请这一位协助，这个话题汇总。开关没开时仍照 `topic_key` 直达。
  - 多位，或带 `quote.collab`：开关没开或 Bridge 没有 `collab` 部件，failed。开着时 `route`：`DESK`、`DIRECT` 照原来交给管家或那一位；`ROUTER`（只点了负责人）交给管家，正文前加一句点了谁、请管家先找出归谁；`REFUSED`（协助方超过 3 位）failed，写 `route.reason`，什么都不发；`COLLAB` 且不是引用协作：`Collaboration.start`，根请求的消息 id 是 `web-<op_id>`，来源是主人（`asserted_by` 为 `owner`），`to` 里的人都算主人点名，回执“已发起协作：T3 汇总，问 T5、T7”（同一句话同一组人再来一次说已经发起过）；预检不过（`refused`）原样 failed。
  - 引用协作（`route.collab`）：点了人就对每位 `clarify`（每位最多 2 次，上一次没答复前不能再问，不过的那位写原因，全不过则 failed）；没点人就把话作为主人的话交给那次协作的汇总方话题（照原来的 `say`）。找不到那次协作，或它不在主人私聊里，failed。
- **由谁汇总**：点了多位时输入框写“这件事由 T3 汇总 [更换]”。默认是 `route` 给的那位（引用了话题就是它，否则是第一个点到的普通话题），主人换了就带 `integrator`；后面再加人不偷偷改它。只点了负责人又没选时写“由管家归口”。协助方超过 3 位时发起前就提示，不发。
- **`stop` 的 `payload.collab`**：`topic_key` 是汇总方；只停这次协作排队和在跑的咨询轮和汇总方还没开跑的续接轮（`Collaboration.stop(by="web")`），汇总方自己的任务和各协助方别的工作不动，迟到的答复只留档。回执写停了几次咨询。已经做完或停过的回“没有要停的”（done）；找不到的 failed。不带 `collab` 的 `stop` 和从前一样。
- **`memory_fix`**（v31）：已下线，Covey 不再认这个操作（回 failed“不认识的操作”）；专项记忆在网页的「记忆」里改。旧版记下的纠正（`fixes`、`applies`、确认）照常读。
- **协作条目** `collab`（`key` 是协作 id；`app/web_collect.py`，只推主人私聊里的，和别的条目一样按 `rev` 只推变了的，全量对时可删）：

  ```text
  {key, root: {message_id, job?, words}, integrator: <话题 id>, helpers: [<话题 id>],
   state: open|done|cancelled, goal_rev: <字符串>, created_at, updated_at（秒）,
   asks: [{id, from: <话题 id>, to: <话题 id>, number: 1|2, state, words, reason, text,
           reply: {text, at, topic_key: <协助方话题 id>, seq?, evidence: [{text, topic_key, seq?}]} | null,
           late: {text, at} | null}]}
  ```

  - `state`、`words`（`ASK_WORDS` 的词）、`reason`（未接手、失败、到期、已取消时的原因）取 `core/collab.py` 和 `collab_records.view`；`from` 为空时填汇总方；`root.words` 是主人发起这次协作的那句话（截 600 字）。
  - `reply.evidence` 是一条 `{text: 证据级别的词（EVIDENCE_WORDS：原会话分叉、话题记录（无原会话））, topic_key: 协助方, seq?}`；`seq`（`reply.seq` 同）是协助方话题里那一轮的 `seq`，按证据里的任务号（`evidence.job_id`，没有就 `base.job_id`）对到那一轮，对不上（那个话题还没读到、那一轮不在最近 100 轮里）就省略，读到后下一次推补上。
  - 协作记录有变化时，汇总方和协助方的话题在下一次看时重建（标记和回执行才跟上）。
- **一轮的 `collab`**（`{key, role}`）：
  - 汇总方续接轮（消息 id `collab-<协作 id>-reply-<n>`，`core/collab.py` 的 `reply_message`）的主人行和回答行带 `role: "integrator"`。主人行是 Bridge 拼的长提示，`body` 和 `display` 都只推“（协作的答复到齐，接着汇总）”。正在跑、停了的续接轮也带。
  - 协助方话题多一行 `role: "event"`、`collab: {key, role: "helper"}` 的回执，“已协助 T3（看这次协作）”；咨询还排着队或在跑时是“正在协助 T3（…）”、`status` 为 `running`，没有一次答复时是“没能协助 T3（…）”；协助方没接手的（未接手）没有这一行。它的 `key` 是 `<话题>:collab-<协作 id>`，`seq` 是那时（这次协作发起或最后一次咨询结束时）协助方最近一轮的 `seq`，不超过这次推的 `last_seq`，所以不会被“删掉 `seq > last_seq` 的轮次”收走，也不和真实轮次的 key 冲突。它不改协助方的 `unseen`、`tone`、`board`、`round`、`last_seq` 和最近交付。管家的话题没有这一行。
- **回复这次协作**：引用协作里的一句、或点回执上的“回复这次协作”时带 `quote.collab`，话进那次协作，由它的汇总方接；在协助方的话题里不带引用另说一句，仍是对那个话题自己工作的话。
- **三层记忆**（专项条目的 `memory` 每条，`memory_version` 是一轮读到的记忆的版本，没有记忆时是空串）：
  - `layer`：`rule`（长期约定）、`decision`（当前决定）、`history`（历史记录；风格行是 `rule`、`kind` 为 `style`）。面板按这三层分组。
  - `part`：一轮带它的那一段，`rule`、`decision`、`reference`（待核对参考）；历史记录和风格行是 `null`。
  - `asserted_by`、`recorded_by`、`level`，含义同[来源](architecture.md#参与者交付与来源)；`said_by`（你说的、它总结的）和 `by`（`owner` 或 `lead`）只作来源标签。
  - `applies`：适用范围和条件（一句话，没写是空串）；`valid`：`active`、`done`、`superseded`（另带 `superseded_by`）、`void`。
  - `ref`：`project:<专项 id>:<条目 id>`，和一轮的 `memory_ids` 对得上；`carried`：成员话题的下一轮会不会带它（脱敏的话题只带开了脱敏的话题记下的）；`redacted`：这条在开了脱敏的话题里记下。
  - `origin`：`at`（记下的时刻），知道的另带 `message_id`（那条消息）或 `question`（那道题的记录）和它的 `item`、`index`，`topic` 和它的 `topic_number`，`job`，主人的原话 `quote`。
  - 话题记忆还没有推。
